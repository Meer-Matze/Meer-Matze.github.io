# Write CSAPP Notes Skill

写 CSAPP 笔记时保持跨章节的文风一致性和内容准确性。本 skill 提供固定的工作流程，覆盖结构设计、审查、修订三个阶段。

## 何时使用

- 把一份平铺的初稿改写成分层结构
- 审查笔记中的事实性错误
- 统一多个章节的术语和格式
- 把审查发现的问题修订进正文（而非另开一节列出）

## 写作风格（硬性约束）

以下规则优先于任何"看起来更完整"的冲动。写完后逐条自检。

1. **句子要短**。一句话只表达一个判断。避免三个以上分句用"因为/所以/但是/而"层层嵌套的长句；能拆成两句就拆开。
2. **段落要短**。每段 1–3 行。一段只讲一件事，讲完就换段，不要为了"过渡自然"硬凑连接句。
3. **能列表就不用散文**。出现以下信号时改成列表或表格，不要写成一段夹叙夹议的话：
   - 3 个以上并列项（"包括 A、B、C"）
   - 有序步骤（"首先…然后…最后"）
   - 参数/指令/寄存器的对比或枚举
4. **先结论后细节**。每个小节开头一句话给出结论或定义，随后再展开推导、示例、边界情况。
5. **提醒框用 Obsidian 风格 Admonitions（`> [!type]`），不要把它们埋进正文段落**。格式：

   ```
   > [!type] 可选标题
   > 说明文字，一句话说清楚，不展开论证。
   ```

   按内容选类型，不要统一用 `[!note]`：

   | 类型         | 用于                                     |
   | ------------ | ---------------------------------------- |
   | `[!note]`    | 中性补充说明、术语来历、历史沿革         |
   | `[!tip]`     | 记忆技巧、快捷做法                       |
   | `[!warning]` | 容易踩的坑（弱符号覆盖、栈对齐惯例这类） |
   | `[!fail]`    | 报错示例、失败的命令输出                 |
   | `[!example]` | 独立于正文的完整示例                     |

   四类触发场景：容易踩的坑、与主线无关但值得一提的背景、需要单独强调的边界条件（小端序字节顺序、ASLR 影响布局）、与其他章节的显式关联提示。

6. **表格优先于对比性描述**。凡是"A 是 X，B 是 Y，二者的区别在于…"这种结构，直接列表格。

## 核心原则

1. **分层结构**：每章拆成"第一部分/第二部分…"，部分内用编号小节（如 8.1、8.2），需要时再加三级子标题
2. **术语统一**：全文同一概念只用一个中文译名，首次出现时括注英文原词
3. **原文内容零丢失**：重组结构、修正错误、精简表达，但不删减原有的知识点
4. **修订即改写**：发现的错误直接改进对应段落，不设"勘误"或"errata"专节——读者读到的应该是修正后的干净版本

## 工作流程

### 第一步：分析原稿

- 列出原稿现有的标题层级，判断是否需要重新分层
- 标记内容密度不均的小节（某处过简、某处过繁）
- 标记术语不一致的地方（同一概念多个叫法）
- 通读一遍，凭经验/常识标出"可能有问题"的具体断言（数值、公式、因果关系），留到第三步核实

### 第二步：设计分层结构

按主题把原有小节归入几个"部分"，部分数量和粒度参考本书其他已完成章节，保持跨章节的层级深度一致（例如都是"第几部分 → X.Y 节 → X.Y.Z 小节"三层）。

```
第一部分 [主题]
  X.1 [小节]
  X.2 [小节]
    X.2.1 [子节]
第二部分 [主题]
  X.3 [小节]
  ...
```

标题要能直接说明内容（"8.1 逻辑控制流"而非"8.1 概述"）。

### 第三步：三级审查

这是保证准确性的核心步骤。把第一步标出的可疑断言，以及通读中发现的新问题，按置信度分成三类：

| 类别         | 判定标准                                                                             | 处理方式                                                                |
| ------------ | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| **错误**     | 能独立验证——算术推导、内部逻辑矛盾（笔记前后两处数字互相矛盾）、明确违反已确认的规则 | 直接改写为正确内容                                                      |
| **需确认**   | 具体数值/型号/版本细节，记忆置信度不够高，无法独立验证对错                           | 改写时给出更保守/更明确来源的表述，或提示"建议核对原书"，不臆造确定数字 |
| **建议补充** | 原书有但笔记未覆盖的重点内容                                                         | 判断价值后决定是否并入正文                                              |

审查时对每一条给出：出处（哪一节）、问题描述、修正依据。不要笼统地说"这里可能不对"。

### 第四步：修订并整合

- 把三级审查的结果**直接改写进对应正文位置**，不新增"勘误"或"改动记录"章节
- 错误类：改写事实，必要时补一句因果解释（为什么原表述会误导）
- 需确认类：措辞更严谨，或注明"因型号/版本而异"，不用确定语气断言不确定的数字
- 建议补充类：并入对应小节，或独立成新的一节/一个子部分，标题要能体现内容
- 全文过一遍，按"写作风格"六条自查：长句拆短、散文改列表、该用提醒框的地方改成 `[!type]` admonition

### 第五步：术语与格式统一

- 全文搜索同一概念的不同译法，统一成一个，首次出现括注英文
- 代码块标注语言（\`\`\`c、\`\`\`asm、\`\`\`bash）
- 表格对齐、列头一致
- 检查标题层级没有跳级（不能 `#` 直接跳到 `###`）

### 第六步：跨章节一致性核对

- 与已完成章节对照：部分/小节的层级深度是否一致
- 术语是否与其他章节冲突（例如某术语在第 3 章和第 7 章译法不同）
- 交叉引用的章节号是否准确

## 常见反模式（明确禁止）

- ❌ 单独开一节列"勘误"或"errata"——错误直接改在原处
- ❌ 用不确定的具体数字冒充确定事实（"需确认"类问题应改写措辞而非硬编造答案）
- ❌ 三个以上并列项还写成一句话夹带顿号
- ❌ 提醒性内容写成正文段落里的插入语，而不是独立的 `[!type]` admonition
- ❌ 提醒框全用 `[!note]`，不区分警示/示例/报错等类型
- ❌ 一段话里塞两个以上转折/因果关系

## 示例：三级审查的实际产出格式

```
错误 — §6.1.1：SRAM 断电后数据描述有误
SRAM 和 DRAM 都是易失性存储器，断电后数据均丢失。
区别在于 DRAM 需要周期性刷新，SRAM 不需要。
→ 表格该行标题由"断电后数据"改为"是否需要刷新"。

需确认 — §6.10：L3 缓存 8MB/16路 参数因具体型号而异
→ 括注"以 CSAPP 书中所用型号为例"，不作为通用参数陈述。

建议补充 — §6.13：矩阵乘法分块（blocking）优化
原书用整节讲这个，笔记未覆盖，是本章最重要的代码级优化案例。
→ 新增小节，包含朴素实现瓶颈分析 + 分块效果的定量推导。
```
