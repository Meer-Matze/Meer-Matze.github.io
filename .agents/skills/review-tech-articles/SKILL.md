# Review Tech Articles Skill

审查、修订计算机技术类文章（教材笔记、课程讲义、技术博客），保证内容准确、行文风格统一。这是从反复处理 CSAPP 笔记的实践中提炼出的通用方法，不绑定任何一本具体教材。

## 何时使用

- 用户贴出一篇技术文章/笔记，要求检查错误
- 要求把平铺的初稿改写成分层结构
- 要求审查后给出"最终版"/"完善版"
- 要求统一多篇笔记的术语和格式

## 写作风格（硬性约束）

1. **句子要短**。一句话一个判断，三个以上分句层层嵌套的长句拆开。
2. **段落要短**。1–3 行一段，一段一件事。
3. **能列表/表格就不用散文**。触发信号：3 个以上并列项、有序步骤、参数或指令的对比枚举。
4. **先结论后细节**。每个小节开头一句话给结论或定义，再展开推导、示例、边界情况。
5. **提醒框用 Obsidian 风格 `[!type]`**，不要埋进正文段落。格式：

   ```
   > [!type] 可选标题
   > 说明文字，一句话说清楚。
   ```

   按内容选类型：`[!note]`（中性补充、历史背景）、`[!tip]`（记忆技巧）、`[!warning]`（易踩的坑）、`[!fail]`（报错示例）、`[!example]`（独立示例）。标题只写在 `[!type]` 里，不要在它前面再加一个同名的正文小标题（常见冗余：`#### GNU 项目` 紧跟 `> [!note] GNU 项目`）。

6. **数学和证明优先于类比**，涉及公式推导时给出完整步骤而非"大致意思是……"。
7. **代码块**：语言标签必须标注；超过原文本身长度不必要地展开的示例，按需精简，保留能说明问题的最小片段。
8. **术语**：中文译名统一，首次出现括注英文原词。

## 核心原则

1. **分层结构**：长文拆成"第一部分/第二部分…"，部分内用编号小节，需要时加三级子标题。部分数量参照内容自然分野，不强行凑数；同一系列的多篇文章保持层级深度一致（如都是"部分 → X.Y → X.Y.Z"三层）。
2. **原文内容零丢失**：重组结构、修正错误、精简表达，但不删减原有知识点。
3. **修订即改写，不设改动记录**：发现的问题直接改在正文对应位置。不新增"勘误""改动记录""Errata"这类独立小节——读者应该读到的是修正后的干净版本，不是"这里改过"的标注。如果用户明确要求保留修改痕迹，才按其要求处理。
4. **原文的既有格式约定，若已确认可用，直接沿用**：不要凭空更换用户已在用的提醒框语法、代码围栏风格等。

## 三级审查方法

这是保证准确性的核心步骤，把审查中发现的问题按置信度分类：

| 类别                | 判定标准                                                                                 | 处理方式                                                        |
| ------------------- | ---------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| **错误**            | 能独立验证——算术推导、内部前后矛盾、同一文档内两处函数原型不一致、引用的历史文献原文有误 | 直接改写为正确内容                                              |
| **需验证 / 需确认** | 具体数值、型号、版本细节，记忆置信度不够，无法独立验证对错                               | 改写措辞更保守，或注明"因版本/型号而异"，不臆造确定数字冒充事实 |
| **建议补充**        | 源材料本身覆盖但笔记未涉及的重点内容，或能强化理解的过渡/连接段落                        | 判断价值后决定是否并入正文                                      |

审查时对每一条给出：出处（哪一节/哪一行）、问题描述、修正依据（能验证的说出理由，不能验证的说明为什么存疑）。

### 一个常被忽略的情况：原文本身如此，但仍值得处理

审查中经常遇到"这处写法很怪，但一核对，作者/教材原文确实就是这么写的"——例如：

- 反复出现的自引用赋值（`sprintf(buf, "%s...", buf)`）——技术上是未定义行为，但原书就是这样写，且在目标实现下能正常工作
- 简化过的函数原型（把恒定不变的实参直接写进函数签名占位符，而非用规范的形参占位）
- 抄书时明显是死代码、但不影响最终行为的语句

这种情况**不是要不要改**的问题，而是"改不改"取决于用户是否要求"不必严格遵照原文"。若用户明确表示可以不严格遵照原文，就按更规范的写法改写，同时在旁边留一句提醒说明原因（这是坑、为什么原文这样写也能跑、正确做法是什么）。若用户没有表态或要求保留原文，就保留原文写法，但仍然在 `[!warning]`/`[!note]` 里点出这一点，帮读者识别，而不是悄悄放过。

## 常见格式污染（尤其是从别处复制粘贴的原始材料）

审查时专门过一遍，这类问题不需要技术判断，纯粹是文本层面的清理：

- 转义星号 `\*\*文字\*\*`——反斜杠会阻止 Markdown 正常渲染加粗，批量去除
- HTML 实体残留，如 `&#x5220;`（本该是"删"）——多半是网页复制粘贴留下的编码污染，逐条替换回汉字
- OCR/扫描识别错误——上下文读不通的占位符（如某个变量名被识别成不相关的字）、多余的异形符号
- 失效的图片链接——绝对 URL 能访问的保留；相对路径（脱离原笔记软件资料库后必然失效的）直接删除，用文字描述替代，而不是留着一个必然打不开的链接

## 工作流程

### 1. 通读标注

列出原稿现有标题层级；标出可疑的具体断言（数值、公式、因果关系）留到审查阶段核实；标出术语不一致的地方；扫一遍格式污染。

### 2. 设计/核对分层结构

按主题把内容归入"第几部分"，标题要能直接说明内容（"8.1 逻辑控制流"而非"8.1 概述"）。若这是系列文章的一篇，对照已完成的其他篇目，保持层级深度和常见小节命名习惯一致。

### 3. 三级审查

按上面的方法逐条给出错误/需验证/建议补充，附出处和依据。

### 4. 修订整合

把审查结果直接改写进对应正文位置。改写后通读一遍，按"写作风格"八条自查：长句拆短、散文改列表、该用提醒框的地方改成 `[!type]`、代码块精简且标注语言。

### 5. 术语与跨篇一致性

统一同一概念的译名；若是系列文章，和已完成篇目对照检查术语、结构深度、交叉引用是否一致。

## 常见反模式（明确禁止）

- ❌ 单独开一节列"勘误"或"errata"——错误直接改在原处
- ❌ 用不确定的具体数字冒充确定事实——"需验证"类问题应改写措辞而非硬编造答案
- ❌ 三个以上并列项还写成一句话夹带顿号
- ❌ 提醒性内容写成正文段落里的插入语，而不是独立的 `[!type]` admonition
- ❌ 提醒框全用 `[!note]`，不区分警示/示例/报错等类型
- ❌ 发现"原文确实如此"就直接放过不提——哪怕不改写法，也该留一句提醒
- ❌ 正文标题和紧跟着的提醒框标题重复一遍

## 输出交付

- 使用 edit 工具改写原文，而非使用命令行工具删除文章在重新生成
- 聊天回复本身只需简要说明本次改了什么、为什么改（对应三级审查的条目），不需要在回复里重复整篇内容
- 若只是"检测是否有误"而非"给出最终版"，先用结构化审查列表（错误/需验证/建议补充分类展示）呈现，等用户确认后再产出完整改写稿

## 示例：三级审查的实际产出格式

```
错误 — §6.1.1：SRAM 断电后数据描述有误
SRAM 和 DRAM 都是易失性存储器，断电后数据均丢失。
区别在于 DRAM 需要周期性刷新，SRAM 不需要。
→ 表格该行标题由"断电后数据"改为"是否需要刷新"。

需验证 — §6.10：L3 缓存 8MB/16路 参数因具体型号而异
→ 括注"以某具体型号为例"，不作为通用参数陈述。

建议补充 — §6.13：矩阵乘法分块（blocking）优化
原书用整节讲这个，笔记未覆盖，是该主题最重要的代码级优化案例。
→ 新增小节，包含朴素实现瓶颈分析 + 分块效果的定量推导。
```
