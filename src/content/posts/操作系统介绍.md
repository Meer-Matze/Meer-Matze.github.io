# 第一部分 操作系统是什么

## 2.0 引子：程序运行时会发生什么

一个运行中的程序只做一件事：**执行指令**。处理器从内存**取指**（fetch），**译码**（decode）以弄清是哪条指令，然后**执行**（execute）——两数相加、访问内存、检查条件、跳转到函数等。完成后处理器取下一条指令，直到程序结束。这就是**冯·诺依曼**（Von Neumann）计算模型。

> [!tip] CSAPP 回顾
>
> - 取指、译码、执行、访存、写回、更新 PC 六个阶段：4.1、4.3
> - 现代处理器实际上用流水线、乱序执行等手段并行执行指令（4.4、5.5），但对软件始终保持"指令按序逐条执行"的抽象（1.8.3，指令集架构）
>
> OSTEP 只关心这个简单模型。

模型看起来简单，但程序运行时，背后还有大量工作在同步进行，目的是让系统**易于使用**：允许同时运行多个程序、让程序共享内存、让程序与设备交互。负责这些事的软件称为**操作系统**（Operating System，OS）。

## 2.1 操作系统的三种角色

| 角色                               | 含义                                                                                     | CSAPP 对应                        |
| ---------------------------------- | ---------------------------------------------------------------------------------------- | --------------------------------- |
| **虚拟机**（virtual machine）      | 把物理资源（CPU、内存、磁盘）转换成更通用、更强大、更易用的虚拟形式                      | 1.6：进程、虚拟内存、文件三个抽象 |
| **标准库**（standard library）     | 以接口（API）形式提供**系统调用**（system call），用于运行程序、访问内存和设备           | 8.4.2 陷阱与系统调用；8.5.2       |
| **资源管理器**（resource manager） | 虚拟化使多个程序共享 CPU、内存、磁盘，操作系统负责管理这些资源，目标是高效、公平，或其他 | 1.6                               |

> [!note] "虚拟机"一词的两种用法
> OSTEP 说操作系统是"虚拟机"，指的是**操作系统本身就是对硬件的虚拟化**。CSAPP 1.8.3 的"虚拟机"则指对**整台计算机**（含操作系统）的抽象，如 VMware 一类。两者层次不同，阅读时注意区分。

> [!question] 关键问题：如何将资源虚拟化
> 为什么要虚拟化，答案显而易见：让系统更易用。真正的问题是**怎么做**：
>
> - 操作系统通过哪些**机制**和**策略**实现虚拟化？
> - 如何高效地实现？
> - 需要哪些硬件支持？

**机制与策略**是贯穿全书的一对概念：

|      | 机制（mechanism）                 | 策略（policy）                      |
| ---- | --------------------------------- | ----------------------------------- |
| 回答 | **如何**做（how）                 | **做哪个 / 何时做**（which / when） |
| 层次 | 低层的方法或协议                  | 在机制之上做决策                    |
| 例   | 上下文切换：保存、恢复寄存器与 PC | 调度：下一个运行哪个进程            |

# 第二部分 三个主题

## 2.2 虚拟化 CPU

下面的程序什么也不做，只是反复"忙等一秒、打印字符串"：

```c
#include <stdio.h>
#include <stdlib.h>
#include "common.h"            /* 提供 Spin(n)：忙等 n 秒 */

int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "usage: cpu <string>\n");
        exit(1);
    }
    char *str = argv[1];
    while (1) {
        Spin(1);               /* 反复检查时间，满 1 秒返回 */
        printf("%s\n", str);
    }
    return 0;
}
```

单独运行，每秒打印一次 `A`，按 Ctrl-C 终止。同时运行四个实例：

```bash
❯./cpu A & ./cpu B & ./cpu C & ./cpu D &
A
B
D
C
A
C
D
B
...
```

虽然只有一个 CPU，四个程序却**似乎同时在运行**。这是操作系统借助硬件制造的假象——把一个 CPU（或其一小部分）转换成看似无限多个虚拟 CPU，称为**虚拟化 CPU**（virtualizing the CPU）。

> [!tip] CSAPP 回顾
>
> - 进程 = 独立的逻辑控制流 + 私有地址空间：8.6、8.7
> - 单核上的并发是时间片交错，多核上才是并行：8.7
> - 用户模式与内核模式：8.9；上下文切换（保存 / 恢复 / 传递控制）：8.10
> - 创建、回收、替换进程的 API：`fork`、`waitpid`、`execve`（8.12）
> - 定时器中断可让内核抢占当前进程：8.4.1、8.10

这些 CSAPP 已讲清"是什么"，OSTEP 要追问"怎么实现"：

- **机制**：怎样切换进程才既高效、又不让进程失去对 CPU 的控制？→ 受限直接执行
- **策略**：两个程序都想运行时，该运行哪个？这由操作系统的**调度策略**（scheduling policy）回答，OSTEP 将研究多种调度算法

运行、停止程序，以及告诉操作系统运行哪些程序，都需要接口，即系统调用，它们是用户与操作系统交互的主要方式。

## 2.3 虚拟化内存

**物理内存**模型很简单：内存就是字节数组。读内存要指定**地址**；写内存要指定地址和要写入的数据。程序的数据结构、指令都放在内存里，因此每次取指也是一次内存访问。

下面的程序分配一个 `int`，打印它的地址，然后每秒递增一次：

```c
#include <stdio.h>
#include <stdlib.h>
#include <assert.h>
#include <unistd.h>
#include "common.h"

int main(int argc, char *argv[]) {
    int *p = malloc(sizeof(int));
    assert(p != NULL);
    printf("(%d) address of p: %p\n", getpid(), (void *)p);   /* 虚拟地址 */
    *p = 0;
    while (1) {
        Spin(1);
        *p = *p + 1;                          /* 递增 p 所指向的值 */
        printf("(%d) p: %d\n", getpid(), *p);
    }
    return 0;
}
```

同时运行两个实例，两个进程**打印出相同的地址**，但各自独立地递增各自的值，互不影响——每个进程都像拥有私有内存。

形式化地说：设进程 $i$ 的地址翻译函数为 $\text{MAP}_i: \text{VAS} \to \text{PAS} \cup \varnothing$（见 CSAPP 9.6）。实验现象即存在虚拟地址 $va$，使 $\text{MAP}_1(va) \ne \text{MAP}_2(va)$。程序中看到的地址都是**虚拟地址**，这就是操作系统对内存的虚拟化：每个进程访问私有的**虚拟地址空间**，操作系统将其映射到物理内存上；一个进程的内存引用不影响其他进程或操作系统本身，而物理内存其实是由操作系统管理的共享资源。

> [!warning] 复现这个实验的两个前提
>
> - 需要**关闭地址空间随机化**（ASLR），否则每次运行地址本身就不同。Linux 上常用 `setarch $(uname -m) -R ./mem`
> - 原书用 `%08x` 配 `(unsigned)p` 打印地址，在 64 位机上会截断指针，这里改用 `%p`

> [!tip] CSAPP 回顾
>
> - 地址空间、虚拟地址与物理地址：9.1、9.2
> - 虚拟内存作为内存管理和保护的工具（每个进程独立页表、PTE 权限位）：9.4、9.5
> - 地址翻译、TLB、多级页表、缺页：9.6；Core i7 / Linux 案例：9.7
> - ASLR（栈、堆、共享库地址随机）：3.6.1、7.7
>
> OSTEP 追问的是操作系统一侧的**机制演化**与**策略**：地址翻译如何从简单方案逐步演进到分页和 TLB；物理内存不够时用什么策略换出页面。

## 2.4 并发

**并发**（concurrency）指一系列在**同时处理很多事情**时出现、且必须解决的问题。它首先出现在操作系统本身中（一会儿运行这个进程，一会儿运行那个），之后也出现在**多线程**（multi-threaded）程序中。

线程可以看作与其他函数在同一内存空间中运行的函数，且同一时刻有多个处于活动状态。下面的程序创建两个线程，各自把共享计数器递增 `loops` 次：

```c
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>
volatile int counter = 0;
int loops;
void *worker(void *arg) {
    for (int i = 0; i < loops; i++)
        counter++;                      /* 非原子：load / add / store */
    return NULL;
}
int main(int argc, char *argv[]) {
    loops = atoi(argv[1]);
    pthread_t p1, p2;
    pthread_create(&p1, NULL, worker, NULL);
    pthread_create(&p2, NULL, worker, NULL);
    pthread_join(p1, NULL);
    pthread_join(p2, NULL);
    printf("Final value: %d\n", counter);
    return 0;
}
```

预期最终值是 $2 \times loops$。运行结果：

| `loops` | 最终值                     |
| ------- | -------------------------- |
| 1000    | 2000                       |
| 100000  | 143012、137298（每次不同） |

原因在于 `counter++` 被编译成三条指令：$L$（把 `counter` 从内存加载到寄存器）、$U$（寄存器加 1）、$S$（存回内存）。这三条指令不是**原子的**（atomically，即不可分割地一次执行完），线程交错执行时更新会丢失：

| 步骤 | 线程 1            | 线程 2            | `counter` |
| :--: | ----------------- | ----------------- | :-------: |
|  1   | $L_1$：读到 0     |                   |     0     |
|  2   |                   | $L_2$：读到 0     |     0     |
|  3   | $U_1$：寄存器 = 1 |                   |     0     |
|  4   |                   | $U_2$：寄存器 = 1 |     0     |
|  5   | $S_1$：写入 1     |                   |     1     |
|  6   |                   | $S_2$：写入 1     |     1     |

两次递增只生效一次。每次 $S$ 写入的是"它读到的值加 1"，因此最终值不会超过 $2 \times loops$。最小值是多少？这是一道经典思考题。

> [!warning] `volatile` 不能保证原子性
> `volatile` 只阻止编译器把变量缓存在寄存器里，不提供原子性，也不提供同步。上面的程序加了 `volatile` 依然是错的。

> [!question] 关键问题：如何构建正确的并发程序
> 同一内存空间中有许多并发执行的线程时：
>
> - 操作系统需要提供什么**原语**（primitive）？
> - 硬件应该提供哪些机制？
> - 如何用它们解决并发问题？

> [!tip] CSAPP 回顾
> 这正是 CSAPP 12.5 的 `badcnt.c`：
>
> - 进度图、临界区、不安全区、互斥：12.5.1
> - 信号量 P / V 与互斥锁：12.5.2、12.5.3
> - 生产者-消费者、读者-写者：12.5.4
> - 线程安全、可重入、竞争、死锁：12.7；并行与性能：12.6
>
> OSTEP 从实现者一侧补充：**锁本身怎么实现**（含硬件的原子指令，如 test-and-set、compare-and-swap）、条件变量、信号量的实现、常见并发 bug、基于事件的并发。

## 2.5 持久性

内存中的数据是**易失的**（volatile）：DRAM 以易失方式存储数值，断电或系统崩溃后数据全部丢失（6.1.1）。因此需要硬件和软件**持久地**（persistently）存储数据。

- **硬件**：**输入/输出**（I/O）设备。**硬盘驱动器**（hard drive）是长期信息的通用存储库，**固态硬盘**（SSD）已成为广泛使用的非易失性存储设备
- **软件**：管理磁盘的那部分操作系统称为**文件系统**（file system），负责可靠、高效地把用户创建的**文件**存到磁盘上

与通常为每个进程提供私有虚拟地址空间不同，传统 Unix 文件模型并不会自动为每个进程复制一套私有文件系统，而是允许不同进程根据权限访问和共享文件。例如：编辑器创建 `main.c`，编译器读它并生成可执行文件，再运行该文件——文件在多个进程间流转。

下面的程序创建文件 `/tmp/file` 并写入一行文本：

```c
#include <fcntl.h>
#include <sys/stat.h>
#include <unistd.h>
#include <string.h>
#include <assert.h>

int main(void) {
    const char *msg = "hello world\n";
    int fd = open("/tmp/file", O_WRONLY | O_CREAT | O_TRUNC, S_IRWXU);
    assert(fd > -1);
    ssize_t rc = write(fd, msg, 13);
    assert(rc == 13);
    close(fd);
    return 0;
}
```

三个系统调用依次打开并创建文件、写入数据、关闭文件；它们被转交给操作系统的**文件系统**部分处理，之后向用户返回错误码。`S_IRWXU` 表示拥有者可读可写可执行，权限位的含义见 CSAPP 10.2。

实际写盘并不简单。文件系统必须决定新数据驻留在磁盘的哪个位置，并在文件系统维护的各种结构中记录，这需要向存储设备发出 I/O 请求以读取或更新这些结构。设备驱动程序（知道如何与特定设备打交道的内核代码）需要深入了解低级设备接口，而操作系统通过系统调用为此提供了标准而简单的访问方式。

文件系统还要处理两类问题：

| 问题                                 | 常见做法                                                                                                              |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| **性能**                             | 延迟写操作一段时间，把写入批量分组为较大的组；用不同数据结构（从简单列表到 B 树）加速常见操作                         |
| **崩溃一致性**（写入过程中系统崩溃） | 复杂的写入协议，如**日志**（journaling）、**写时复制**（copy-on-write），仔细排序写盘操作，保证故障后能恢复到合理状态 |

> [!question] 关键问题：如何持久地存储数据
>
> - 正确实现持久性需要哪些技术？
> - 高性能需要哪些机制和策略？
> - 面对硬件和软件故障，如何保证可靠性？

> [!tip] CSAPP 回顾
>
> - Unix I/O：`open`、`read`、`write`、`close`，文件描述符，短计数：10.1~10.4
> - 打开文件的三张表与文件共享：10.7；I/O 重定向：10.8
> - 磁盘访问时间（寻道 + 旋转 + 传输）：6.2.1；SSD、FTL、磨损均衡：6.2.2
>

# 第三部分 设计目标与历史

## 2.6 设计目标

构建操作系统需要明确目标来指导设计和折中，**找到合适的折中是构建系统的关键**。

| 目标                              | 含义                                                                                                           |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **抽象**（abstraction）           | 让系统方便易用；把大程序拆成小而易懂的部分                                                                     |
| **高性能**（performance）         | 最小化操作系统的开销，包括额外时间（更多指令）和额外空间（内存或磁盘）                                         |
| **保护**（protection）            | 应用之间、应用与操作系统之间互不损害；核心原则是**隔离**（isolation）                                          |
| **可靠性**（reliability）         | 尽可能减少系统失效，并在发生故障时限制影响、支持恢复<br>操作系统内核的故障可能影响大量应用，必须保证其稳定运行 |
| **能源效率**（energy-efficiency） | 在节能的趋势下日益重要                                                                                         |
| **安全性**（security）            | 保护的扩展，针对恶意应用，联网时代尤其重要                                                                     |
| **移动性**（mobility）            | 随着操作系统运行在越来越小的设备上而变得重要                                                                   |

> [!tip] CSAPP 回顾
>
> - 抽象：指令集架构、文件、虚拟内存、进程、虚拟机，层层隐藏实现复杂性（1.8.3）。用 C 写程序不必考虑汇编，写汇编不必考虑逻辑门，造处理器不必考虑晶体管——整个抽象链条在第三、四章已走过
> - 保护：用户 / 内核模式（8.9）、PTE 权限位（9.5、9.7）
> - 性能：Amdahl 定律（1.8.1）、局部性（6.4）、程序优化（第五章）

抽象与性能经常冲突：抽象越厚，开销通常越大。后续各章几乎每个机制都要在这两者之间权衡。

## 2.7 简单历史

| 阶段                 | 特点                                                                                               | 引入的操作系统概念                                                                |
| -------------------- | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **早期：只是一些库** | 操作系统只是常用函数库；大型机一次运行一个程序，由操作员控制（决定作业顺序）                       | **批处理**（batch）：作业先准备好，再成批运行。不交互，因为让昂贵的机器等人太浪费 |
| **超越库：保护**     | 代表操作系统运行的代码是特殊的，不能当普通库函数对待（否则任何程序可读任意磁盘位置，隐私无从谈起） | **系统调用**、硬件特权级别、**陷阱**（trap）                                      |
| **多道程序**         | 小型机（如 DEC PDP 系列）降低成本；多个作业同时加载进内存，I/O 等待时切换到别的作业                | **多道程序**（multiprogramming）；随之而来的内存保护、并发、中断下的正确性问题    |
| **摩登时代**         | 个人计算机起初是倒退：DOS 无内存保护；早期 Mac OS 用协作式调度。之后小型机时代的功能回流到桌面     | 回归保护与抢占；今天的手机操作系统更像 20 世纪 70 年代的小型机系统                |

### 2.7.1 系统调用 vs 过程调用

系统调用的概念据原书介绍由 Atlas 计算系统率先采用。它与普通过程调用的区别：

|          | 过程调用       | 系统调用                                                               |
| -------- | -------------- | ---------------------------------------------------------------------- |
| 特权级   | 不变           | 提升到**内核模式**（kernel mode）                                      |
| 跳转目标 | 调用者自己指定 | **预先指定**的陷阱处理程序（trap handler），调用者不能自选             |
| 返回     | 普通返回指令   | **陷阱返回**（return-from-trap）指令：降回用户模式，回到应用离开的地方 |

跳转目标预先指定非常关键：若应用能自选入口，就能在内核模式下执行任意代码，保护也就无从谈起。

流程：用户态应用执行 trap 指令 → 硬件把特权级提升到内核模式，跳转到预先设置的陷阱处理程序 → 操作系统在内核模式下完成请求 → 执行 return-from-trap 返回用户模式。

> [!tip] CSAPP 回顾
>
> - 陷阱是有意的同步异常，用 `syscall` 指令进入内核：8.4.2、8.5.2
> - 异常表（跳转表）在系统启动时由操作系统初始化：8.3
> - 用户模式不能执行特权指令，只能经中断、故障或系统调用进入内核模式：8.9

### 2.7.2 抢占与协作

早期 Mac OS（V9 及更早）采用**协作式**（cooperative）调度：进程需自愿让出 CPU，因此意外陷入无限循环的线程能占用整个系统，只能重启。**抢占式**（preemptive）调度则由操作系统借助定时器中断强行收回 CPU（8.4.1、8.10）。

### 2.7.3 UNIX 与 Linux

> [!note] UNIX 的影响
> UNIX 由 Ken Thompson 和 Dennis Ritchie 主导，吸收了 Multics 等系统的思想并使之更简单。其基础原则是**构建小而强大的程序，再把它们连接成更大的工作流**，shell 的**管道**（pipe）是典型原语，如 `grep foo file.txt | wc -l` 统计含 `foo` 的行数。用 C 写成的小内核易读易改，加上近乎免费的源码分发（早期的开放源码形式），使 UNIX 迅速传播；伯克利的 BSD 在此基础上增加了先进的虚拟内存、文件系统和网络子系统。
>
> 之后各厂商（SunOS、AIX、HPUX、IRIX）各有变种，加上 AT&T 与厂商之间的法律纠纷，UNIX 一度放缓。Linus Torvalds 随后编写了不借用原代码的 UNIX 类系统 Linux，它因免费可改而被谷歌、亚马逊等公司广泛采用，并通过 Android 进入手机；macOS 的 Darwin/XNU 体系包含 Mach 与 BSD 成分，并继承了 Unix 的许多设计传统。
>
> UNIX、POSIX、Linux 的起源与时间线见 CSAPP 1.6 的两个旁注，这里不再重复。

# 第四部分 小结

## 2.8 小结

操作系统通过**虚拟化**CPU 和内存让系统易于使用，处理与**并发**相关的棘手问题，**持久地**存储文件。设计时要在抽象、性能、保护、可靠性等目标之间折中。

#### CSAPP → OSTEP 知识地图

| OSTEP 主题     | CSAPP 已覆盖                                                        | OSTEP 将补充的问题                                           |
| -------------- | ------------------------------------------------------------------- | ------------------------------------------------------------ |
| **虚拟化 CPU** | 进程抽象、上下文切换、信号、`fork` / `execve` / `waitpid`（第八章） | 如何高效又安全地切换进程；调度策略；多核调度                 |
| **虚拟化内存** | 虚拟地址空间、页表、TLB、多级页表、缺页、内存映射（第九章）         | 地址翻译机制的演化；页面换出策略；交换空间                   |
| **并发**       | 线程、信号量、竞争、死锁、线程安全（第十二章）                      | 锁与条件变量的实现；硬件原子指令；常见并发 bug；事件驱动并发 |
| **持久性**     | Unix I/O、磁盘与 SSD 的访问特性（第六、十章）                       | 文件系统实现；崩溃一致性；磁盘调度与 RAID                    |
