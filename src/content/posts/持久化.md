# 第一部分 I/O、磁盘与 RAID

前面的进程与地址空间建立在 CPU 与内存的抽象之上，而一个真正有用的系统还必须与外部世界交互：读取输入、显示图像、访问网络、保存文件。这些工作都离不开 **I/O 设备**。本部分先介绍操作系统与设备通信的机制，再以硬盘为例分析持久存储设备的性能，最后讨论 RAID。

## 5.1 I/O 设备：操作系统如何与硬件交互

> [!question] 关键问题：如何将 I/O 集成到系统中
> 操作系统如何与不同类型的 I/O 设备交互？需要什么通用机制？如何减少设备交互对 CPU 的占用？

### 5.1.1 系统架构

典型系统用分层总线连接 CPU、内存与设备：

| 层次         | 连接方式            | 典型设备               |
| ------------ | ------------------- | ---------------------- |
| 处理器与内存 | 内存总线 / 高速互连 | 主存                   |
| 高速 I/O     | PCI / PCIe          | 显卡、高性能存储、网卡 |
| 外围设备     | SATA、USB、SCSI 等  | 硬盘、键盘、鼠标       |

分层是**性能与成本的权衡**：高速总线要求更短的物理连接、成本更高，高性能设备需靠近 CPU；低速设备带宽要求低，可挂在远端外围总线上，且外围总线能连接大量设备。现代系统还使用专用芯片组与点对点互连（如 DMI），但分层思想不变。

### 5.1.2 设备的组成与交互协议

一个设备由两部分组成：

| 组成         | 作用                                               |
| ------------ | -------------------------------------------------- |
| **硬件接口** | 向操作系统提供一组可操作的寄存器与交互协议         |
| **内部实现** | 实际完成功能的硬件与固件（复杂设备含处理器、内存） |

考虑一个抽象设备，接口含三个寄存器：**状态**（Status）、**命令**（Command）、**数据**（Data）。一次典型交互：

```c
while (STATUS == BUSY) ;      // 1. 轮询：等待设备就绪
Write(DATA, data);            // 2. 传输数据
Write(COMMAND, cmd);          // 3. 发送命令，启动操作
while (STATUS == BUSY) ;      // 4. 轮询：等待完成
```

CPU 亲自搬运数据的方式称为**程序控制 I/O**（Programmed I/O，PIO）。它有两个问题：CPU 必须不断检查状态，等待期间无法做别的事；CPU 还要亲自搬运数据，时间浪费在重复复制上。

### 5.1.3 中断：降低轮询开销

> [!question] 关键问题：如何避免轮询的代价
> 设备操作可能很慢，操作系统能否不频繁检查状态，也能及时知道操作已完成？

解决方案是**中断**（interrupt）：

1. 操作系统发出 I/O 请求，当前进程睡眠，切换到其他就绪进程；
2. 设备在后台执行；
3. 完成后产生硬件中断，CPU 转入预先注册的**中断服务程序**（Interrupt Service Routine，ISR）；
4. ISR 完成后续工作，并唤醒等待 I/O 的进程。

**中断的核心价值是让 CPU 计算与设备 I/O 重叠。** 例如 P1 发出磁盘请求后，磁盘工作期间 CPU 可以执行 P2，I/O 完成后再处理中断、唤醒 P1。

**中断并不总是优于轮询。** 设备很快时，第一次轮询就能发现完成，中断反而多付出切换、处理、唤醒的开销：

| 设备情况       | 更合适的方式                         |
| -------------- | ------------------------------------ |
| 操作很快       | 轮询                                 |
| 操作较慢       | 中断                                 |
| 操作时间不确定 | 混合策略：先轮询一段时间，再改用中断 |

高频中断还可能引起**活锁**（livelock）：CPU 全部时间用于处理中断，没有时间运行用户进程（如网络流量突增）。常见优化是**中断合并**（interrupt coalescing）：设备等待一段时间、让多个请求完成后再发一次中断。代价是等待过长会增加 I/O 延迟。

### 5.1.4 DMA：降低数据传输开销

> [!question] 关键问题：如何降低 PIO 的开销
> 即使用了中断，CPU 仍要亲自搬运数据。能否把数据传输交给专门的硬件？

**直接内存访问**（Direct Memory Access，DMA）控制器在设备与主存之间直接搬运数据：

1. 操作系统告诉 DMA 控制器数据在内存中的位置、长度及目标设备；
2. DMA 控制器执行传输，CPU 转而运行其他进程；
3. 传输完成后，DMA 控制器产生中断。

| 方式 | 数据传输       | CPU 的工作             |
| ---- | -------------- | ---------------------- |
| PIO  | CPU 逐字搬运   | 参与整个传输过程       |
| DMA  | DMA 控制器搬运 | 配置传输并处理完成通知 |

### 5.1.5 设备交互的两种方式

> [!question] 关键问题：CPU 如何访问设备寄存器
> 通过专门的 I/O 指令，还是直接利用普通内存访问指令？

| 方式                 | 访问方法                             | 特点                                                       |
| -------------------- | ------------------------------------ | ---------------------------------------------------------- |
| 显式 I/O 指令        | x86 的 `in` / `out`（访问 I/O 端口） | 通常是特权指令，只有内核能执行，防止用户程序控制硬件       |
| 内存映射 I/O（MMIO） | 普通 `load` / `store`                | 设备寄存器映射到物理地址空间，硬件识别这些地址并转发给设备 |

两种方式在现代系统中都存在。

### 5.1.6 设备驱动：隐藏硬件差异

> [!question] 关键问题：如何构建与设备无关的操作系统
> 不同设备的寄存器、命令和协议各不相同，如何避免文件系统等上层模块依赖这些细节？

**设备驱动程序**（device driver）封装特定设备的细节，向上提供统一接口。Linux 文件系统软件栈：

| 层次                            | 职责                           |
| ------------------------------- | ------------------------------ |
| 应用程序                        | 发起 `open` / `read` / `write` |
| 文件系统                        | 向通用块层提交块读写请求       |
| 通用块层（Generic Block Layer） | 统一的块设备接口               |
| 设备驱动程序                    | 与具体设备交互                 |
| 存储设备                        | SCSI、IDE、USB 等              |

文件系统不必知道底层是哪种设备。某些特殊程序（如 `fsck`、磁盘整理工具）还可经原始设备接口直接读写磁盘块。

**抽象的代价**：通用接口可能隐藏设备特有的能力。例如 SCSI 能提供丰富的错误信息，但通用块层可能只向上返回一个泛化的 `EIO`。另外，驱动由不同厂商编写、质量参差，在内核代码中占很大比例，是内核错误的重要来源（原书指出驱动代码占 Linux 内核的大部分，具体比例需验证）。

### 5.1.7 实例：IDE 磁盘驱动

IDE 磁盘通过 I/O 端口提供四类寄存器：控制、命令块、状态、错误。一次访问的流程：

| 步骤 | 动作                                          |
| ---- | --------------------------------------------- |
| 1    | 读状态寄存器，等待设备 READY 且不 BUSY        |
| 2    | 写入扇区数、逻辑块地址（LBA）与设备编号       |
| 3    | 向命令寄存器写入 READ 或 WRITE                |
| 4    | 写操作：等待设备就绪后向数据端口写入数据      |
| 5    | 设备完成后产生中断                            |
| 6    | 读状态寄存器；若 ERROR 位置位，再读错误寄存器 |

xv6 的驱动把它封装为 `ide_rw()`（提交请求并等待）、`ide_start_request()`（发送请求）、`ide_wait_ready()`（确认就绪）、`ide_intr()`（处理中断、读数据、唤醒进程并启动下一个请求）。

### 5.1.8 小结

| 机制            | 解决的问题                |
| --------------- | ------------------------- |
| 中断            | 避免 CPU 长时间轮询设备   |
| DMA             | 避免 CPU 亲自搬运大量数据 |
| I/O 指令 / MMIO | 提供访问设备寄存器的方式  |
| 设备驱动        | 隐藏不同设备的硬件差异    |

## 5.2 硬盘驱动器：磁盘如何存储和访问数据

> [!question] 关键问题：如何在磁盘上存储和访问数据
> 磁盘如何组织数据？一次读写要经过哪些步骤？操作系统如何通过调度提高性能？

### 5.2.1 磁盘接口

现代磁盘向操作系统呈现一个**扇区数组**：扇区通常为 512 B，从 $0$ 到 $n-1$ 编号，构成线性地址空间。文件系统常以 4 KB 或更大的块组织读写，但磁盘最基本的访问单位是扇区。

**原子性**：磁盘通常只保证单个 512 B 扇区写入的原子性。多扇区写入若中途断电，可能只完成一部分，称为**撕裂写入**（torn write）。

接口背后还有隐含的性能假设：相邻扇区比远距离扇区访问更快；连续访问比随机访问快得多。这是文件系统布局优化的基础。

### 5.2.2 磁盘的物理结构

| 组成              | 作用                       |
| ----------------- | -------------------------- |
| 盘片（platter）   | 存储磁性数据的圆形盘面     |
| 主轴（spindle）   | 固定盘片并带动其旋转       |
| 磁头（disk head） | 读取或写入盘面上的磁性数据 |
| 磁臂（disk arm）  | 带动磁头在盘面上移动       |

每个盘片有两个表面，每个表面通常一个磁头。表面划分为同心圆**磁道**（track），每条磁道再分为**扇区**（sector）。盘片以固定转速旋转（如 7200、15000 RPM）。

转速 $r$ RPM 时，每圈用时 $R = 60/r$ 秒。例如 10000 RPM：

$$
R=\frac{60\ \text{s}}{10000}=6\ \text{ms}
$$

### 5.2.3 磁盘访问过程

**单磁道**：磁头已在正确磁道上，只需等待目标扇区转到磁头下，称为**旋转延迟**（rotational delay）。从随机位置出发，平均约为 $R/2$，最坏接近 $R$。

**多磁道**：目标不在当前磁道时，磁头必须先**寻道**（seek），包括加速、滑行、减速、稳定四个阶段。稳定时间较长（约 0.5～2 ms），因为磁头必须精确定位。一次寻道之后，还要等扇区转到磁头下，最后才传输数据：

$$
T_{\text{I/O}} = T_{\text{seek}} + T_{\text{rotation}} + T_{\text{transfer}}
$$

I/O 速率定义为 $R_{\text{I/O}} = \dfrac{\text{Size}_{\text{transfer}}}{T_{\text{I/O}}}$。平均寻道时间通常约为全程寻道时间的 1/3（需验证）。

### 5.2.4 磁盘的其他结构特征

| 特征                         | 说明                                                                                                                           |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **磁道偏斜**（track skew）   | 相邻磁道的扇区错位排列，使磁头切换磁道后下一个连续扇区尚未转过，避免多等一整圈                                                 |
| **多区记录**（multi-zoned）  | 外侧磁道周长更长，容纳更多扇区；同一区域内各磁道扇区数相同                                                                     |
| **磁盘缓存**（track buffer） | 读某个扇区时可能顺带读入整条磁道。写缓存分**写回**（进入缓存即返回，快但断电可丢数据）与**写穿**（写入磁盘后才返回，安全但慢） |

> [!warning] 写回缓存会打乱写入顺序
> 磁盘可能不按文件系统发出的顺序真正落盘，会破坏文件系统依赖的写入顺序（见 5.7）。

### 5.2.5 磁盘 I/O 时间计算

10000 RPM 磁盘的平均旋转延迟为 $6/2 = 3$ ms。若传输速率 100 MB/s，读取 512 KB：

$$
T_{\text{transfer}} = \frac{512\ \text{KB}}{100\ \text{MB/s}} \approx 5\ \text{ms}
$$

平均寻道 5 ms 时，$T_{\text{I/O}} = 5 + 3 + 5 = 13$ ms。随机访问时，寻道与旋转延迟占很大比例。

**随机与顺序工作负载对比**（原书用两种磁盘举例，参数与数值需验证）：

| 磁盘                                            | 4 KB 随机读                                 | 顺序读   |
| ----------------------------------------------- | ------------------------------------------- | -------- |
| Cheetah 15K.5（寻道 4 ms，15000 RPM，125 MB/s） | $T_{\text{I/O}}\approx 6$ ms，约 0.66 MB/s  | 125 MB/s |
| Barracuda（寻道 9 ms，7200 RPM，105 MB/s）      | $T_{\text{I/O}}\approx 13$ ms，约 0.31 MB/s | 105 MB/s |

随机与顺序的速率相差两个数量级以上，这也是文件系统要追求顺序访问的原因。

### 5.2.6 磁盘调度

> [!question] 关键问题：如何提高磁盘请求的处理效率
> 多个进程同时提交请求时，应按什么顺序处理，才能减少磁头移动和平均访问时间？

磁盘调度的目标是减少寻道时间，兼顾公平与延迟。磁头在 50，请求序列为 $98, 183, 37, 122, 14, 124, 65, 67$。

| 算法                     | 核心思想                               | 本例移动距离 | 主要问题                             |
| ------------------------ | -------------------------------------- | ------------ | ------------------------------------ |
| **FCFS**                 | 按到达顺序                             | 643          | 磁头移动距离可能很大                 |
| **SSTF**（最短寻道优先） | 先处理离磁头最近的磁道                 | 205          | **饥饿**：远处请求可能长期得不到处理 |
| **SCAN**（电梯算法）     | 沿一个方向扫描，到磁盘一端后反向       | —            | 两端请求等待时间不同                 |
| **C-SCAN**（循环扫描）   | 只沿一个方向服务，到端点后快速返回起点 | —            | 返回过程产生额外移动                 |
| **LOOK / C-LOOK**        | SCAN / C-SCAN 只走到最远请求           | —            | 仍需扫描；两者非 OSTEP 内容，为补充  |

SSTF 的序列为 $50\to37\to14\to65\to67\to98\to122\to124\to183$。

**SSTF 的实际问题**：它假设操作系统知道磁盘几何，而现代磁盘不向 OS 暴露柱面与磁头信息，所以 OS 常用**最近块优先**（Nearest-Block-First，NBF）：选择块号最近的请求。更根本的是，SSTF 与 SCAN 都只考虑寻道，而**忽略旋转**。**最短定位时间优先**（Shortest Positioning Time First，SPTF）同时考虑寻道与旋转，但需要精确知道磁头位置与磁盘几何，这通常只有磁盘内部才知道，所以现代磁盘自己实现 SPTF，OS 只需发出一批请求。

OS 调度器还负责：

- **I/O 合并**（merging）：把对相邻块的多个请求合并为一个，减少请求数；
- **工作保存**（work-conserving）与**非工作保存**：前者只要有请求就工作；后者可能故意等待一小会儿，期待更好的请求出现，称为**预期式调度**（anticipatory scheduling），适用于同一进程连续发出相邻读请求的场景。

> [!note] 现代 HDD 也有内部调度
> OS 的磁盘调度器不一定能直接控制最终的物理访问顺序。

### 5.2.7 小结

寻道和旋转延迟远大于连续传输时间，因此：连续访问比随机访问高效；合理的磁盘布局能减少寻道；磁盘调度能减少请求之间的磁头移动。这些性质直接影响后面的文件系统设计。

## 5.3 RAID：利用冗余提高存储可靠性

**RAID**（Redundant Array of Inexpensive Disks，廉价磁盘冗余阵列）把多块磁盘组合成一个更大、更快、更可靠的逻辑设备。

> [!question] 关键问题：如何利用多块磁盘构建可靠存储
> 如何把多个磁盘组合成一个逻辑设备？磁盘故障后如何继续服务？不同 RAID 级别如何在性能、容量与可靠性之间权衡？

### 5.3.1 接口、故障模型与评价指标

RAID 对上层呈现一个逻辑磁盘：上层请求逻辑块 10，RAID 控制器负责确定它在哪块物理盘的什么位置。RAID 通常含多块物理盘、RAID 控制器或软件层、数据布局映射机制，以及用于恢复的冗余信息。

**故障模型**：本章假设 **fail-stop** 模型，即磁盘要么正常工作，要么完全失效，且失效很容易被检测到。（更复杂的故障见 5.10。）

RAID 并不能解决所有问题：误删除、恶意软件、文件系统逻辑错误、多盘同时故障、静默数据损坏都不在它的保护范围内，**RAID 不能代替备份**。

评价指标：

| 指标       | 含义                                                 |
| ---------- | ---------------------------------------------------- |
| **容量**   | 能提供多少可用存储空间                               |
| **可靠性** | 能容忍多少块磁盘故障                                 |
| **性能**   | 吞吐量与延迟，随工作负载（顺序 / 随机、读 / 写）不同 |

### 5.3.2 RAID 0：条带化

**条带化**（striping）把块轮流分布在各盘上，不保存冗余。四盘时，逻辑块 $0,1,2,3$ 依次落在 Disk 0～3，块 4 回到 Disk 0。

块 $A$ 在 $N$ 块盘阵列中（每个**块**为一个条带单位，即 chunk size 为 1 块）的位置：

$$
\text{盘号}=A \bmod N,\qquad \text{盘内偏移}=\lfloor A/N \rfloor
$$

容量 $C=NS$（$S$ 为单盘容量）。优点：所有空间可用，多盘并行，连续大块读写吞吐高。缺点：无冗余，任一盘损坏都会使阵列数据不完整。条带大小（chunk size）影响性能：小条带使单个文件被分散到更多盘上，并行度高，但定位时间取各盘中最长者；大条带则减少文件内部并行度。

### 5.3.3 RAID 1：镜像

**镜像**（mirroring）把相同数据写入两块或多块盘。读取可选任一副本，写入必须更新所有副本。$N$ 块盘（成对镜像）的容量为 $NS/2$，两盘时为 $S$。可容忍至少一块盘故障（若恰好坏在不同的镜像对中，可容忍更多）。

| 缺点                     |
| ------------------------ |
| 可用容量只有总容量的一半 |
| 写入需更新多个副本       |

### 5.3.4 RAID 4：奇偶校验

镜像的空间开销太大。RAID 4 用**奇偶校验**（parity）保存冗余。三块数据盘加一块校验盘，每个条带上：

$$
P = D_0 \oplus D_1 \oplus D_2
$$

任一块丢失，都可由其余块恢复，例如 $D_0 = P \oplus D_1 \oplus D_2$，因为 $x \oplus x = 0$ 且 $x \oplus 0 = x$。容量 $C=(N-1)S$。

**小写入问题**：只改 $D_0$ 为 $D_0'$ 时，不必读其他数据盘，用旧数据与旧校验即可更新：

$$
P' = P \oplus D_0 \oplus D_0'
$$

> [!important] 正确性
> 由 $P=D_0\oplus D_1\oplus D_2$ 有 $P\oplus D_0 = D_1\oplus D_2$，故 $P\oplus D_0\oplus D_0' = D_0'\oplus D_1\oplus D_2 = P'$。$\square$

一次小写入需要**读-修改-写**：读旧数据、读旧校验、写新数据、写新校验，共 2 次读 + 2 次写。而且所有写入都要访问同一块校验盘，形成**校验盘瓶颈**（parity-disk bottleneck）。

### 5.3.5 RAID 5：旋转奇偶校验

RAID 5 把校验块**轮流**放在各盘上，使写入负载分散，消除瓶颈。

| 条带 | Disk 0 | Disk 1 | Disk 2 | Disk 3 |
| ---- | ------ | ------ | ------ | ------ |
| 0    | P      | D0     | D1     | D2     |
| 1    | D3     | P      | D4     | D5     |
| 2    | D6     | D7     | P      | D8     |
| 3    | D9     | D10    | D11    | P      |

容量与 RAID 4 相同，$C=(N-1)S$，可容忍任意一块盘故障。

### 5.3.6 RAID 级别比较

设单盘顺序吞吐为 $S$（此处沿用原书记号，表示 sequential），随机吞吐为 $R$，盘数为 $N$（吞吐数值来自原书，需验证）。

| 项目        | RAID 0 | RAID 1        | RAID 4     | RAID 5     |
| ----------- | ------ | ------------- | ---------- | ---------- |
| 可用容量    | $N$ 盘 | $N/2$ 盘      | $N-1$ 盘   | $N-1$ 盘   |
| 可容忍故障  | 0      | 1（最坏情形） | 1          | 1          |
| 顺序读 / 写 | $N S$  | $(N/2)\,S$    | $(N-1)\,S$ | $(N-1)\,S$ |
| 随机读      | $N R$  | $N R$         | $(N-1)\,R$ | $N R$      |
| 随机写      | $N R$  | $(N/2)\,R$    | $R/2$      | $(N/4)\,R$ |

RAID 4 随机写受校验盘瓶颈限制：每次小写要读写校验盘各一次，所以为 $R/2$。RAID 5 每次小写共 4 次 I/O，分散在 $N$ 块盘上，所以为 $(N/4)R$。

### 5.3.7 RAID 的其他问题

- **写入一致性**：数据块与校验块更新中途崩溃会造成不一致，称为**一致更新问题**（consistent-update problem）；
- **重建**：磁盘故障后利用冗余恢复，可能耗时很长；
- **潜在扇区错误**：重建时可能遇到其他盘不可读的扇区；
- **写入缓存**：控制器缓存写操作，需要考虑断电保护；
- **故障相关性**：多盘可能因同一电源、控制器或环境同时失效。

#### 关键术语

- **PIO**（Programmed I/O）：CPU 逐字在设备与内存之间搬运数据。
- **中断**（interrupt）：设备完成后通知 CPU，使计算与 I/O 重叠。
- **中断合并**（interrupt coalescing）：把多个完成事件合并为一次中断。
- **DMA**（Direct Memory Access）：专用控制器在设备与主存之间搬运数据。
- **MMIO**（Memory-Mapped I/O）：设备寄存器映射到物理地址空间。
- **寻道时间**（seek time）、**旋转延迟**（rotational delay）。
- **条带化**（striping）、**镜像**（mirroring）、**奇偶校验**（parity）。

# 第二部分 文件系统接口

文件系统在原始磁盘之上提供**文件与目录**抽象。本部分只讨论接口及其语义，程序员视角的用法见 [[csapp10|CSAPP 第十章]]（节号为自定编号，需验证）。

## 5.4 文件与目录：持久化数据的抽象

> [!question] 关键问题：如何让程序方便地使用持久存储
> 如何把磁盘上的原始块组织成文件和目录？程序如何创建、读取、写入、删除文件？

### 5.4.1 文件与目录

**文件**（file）是一个字节数组，每个文件有一个底层标识符 **inode number**。**目录**（directory）是一种特殊文件，内容是"用户可读名字 → inode number"的映射表。目录把文件组织成以 `/` 为根的树。

### 5.4.2 文件系统接口

| 系统调用               | 作用                           |
| ---------------------- | ------------------------------ |
| `open()`               | 打开文件，返回文件描述符       |
| `read()` / `write()`   | 读取 / 写入文件内容            |
| `close()`              | 关闭文件描述符                 |
| `lseek()`              | 修改文件读写偏移量             |
| `fsync()`              | 强制将文件的脏数据写入持久存储 |
| `stat()` / `fstat()`   | 获取文件元数据                 |
| `rename()`             | 重命名文件                     |
| `unlink()`             | 删除目录项                     |
| `mkdir()` / `rmdir()`  | 创建目录 / 删除空目录          |
| `link()` / `symlink()` | 创建硬链接 / 符号链接          |

### 5.4.3 创建、读取与写入

```c
int fd = open("foo", O_CREAT | O_WRONLY | O_TRUNC, S_IRUSR | S_IWUSR);
```

`O_CREAT`：不存在则创建；`O_WRONLY`：只写；`O_TRUNC`：已存在则截断为 0。成功返回**文件描述符**（fd），它是进程私有的整数，用于引用已打开文件；每个进程有自己的描述符表，0、1、2 通常对应标准输入、输出、错误。

`read()` 从当前偏移量读取，返回实际读取的字节数并推进偏移量；`write()` 同理。返回值**不一定等于请求的字节数**（可能因信号等原因只完成一部分），程序必须据实际返回值处理剩余数据。

### 5.4.4 随机访问：lseek()

默认访问是顺序的。`lseek(fd, offset, whence)` 修改偏移量，`whence` 取 `SEEK_SET`（文件开头）、`SEEK_CUR`（当前位置）、`SEEK_END`（文件末尾）。

> [!note] `lseek()` 只修改内存中的文件偏移量，与磁盘寻道无关。

### 5.4.5 fork() 与 dup()：共享文件表项

文件描述符是进程私有的，但多个描述符可以引用同一个**打开文件表项**，该表项保存偏移量、状态标志与对应的打开文件对象。

- **`fork()`**：子进程继承父进程的描述符，两者引用同一表项，因此**共享偏移量**；
- **`dup()`**：创建新描述符，指向同一表项，两者交替使用共享偏移量。这是 Shell I/O 重定向的基础。

### 5.4.6 fsync()：保证数据持久化

`write()` 成功**不意味着**数据已持久化，文件系统会先缓冲写入、之后批量落盘。数据库等程序需要调用 `fsync(fd)`，使文件的脏数据强制写出并在完成后返回。

```c
write(fd, buffer, size);
fsync(fd);               // 强制落盘
```

对**新创建**的文件，仅对文件自身 `fsync` 不一定能保证目录项也已持久化；需要时还应对父目录 `fsync`。

### 5.4.7 rename()：原子更新文件

`rename()` 通常保证相对于崩溃的原子性：崩溃后表现为旧名或新名，不会出现中间状态。可用它安全地更新文件：

```c
fd = open("foo.txt.tmp", O_WRONLY | O_CREAT | O_TRUNC, S_IRUSR | S_IWUSR);
write(fd, buffer, size);
fsync(fd);                        // 新内容先落盘
close(fd);
rename("foo.txt.tmp", "foo.txt"); // 原子替换
```

若还要保证重命名本身持久，则需同步相关目录。

### 5.4.8 文件元数据与 unlink()

文件系统除内容外还保存**元数据**（metadata），通常放在 inode 中，通过 `stat()` / `fstat()` 获取：inode 编号、类型与权限（`st_mode`）、链接数（`st_nlink`）、所有者、大小、已分配块数、访问 / 修改 / 状态修改时间等。

`unlink()` 删除的是目录中的**名字**，而不是文件本身：当 inode 的**链接计数**降为 0 且没有进程仍打开该文件时，文件系统才回收 inode 与数据块。

### 5.4.9 目录操作

- `mkdir()` 创建的空目录含两个特殊项：`.`（自身）与 `..`（父目录）；
- 读取目录用 `opendir()` / `readdir()` / `closedir()`，目录项含文件名与 inode 编号，要大小、权限等需进一步 `stat()`；
- `rmdir()` 要求目录为空（只含 `.` 和 `..`）。

### 5.4.10 硬链接与符号链接

| 比较           | 硬链接                 | 符号链接                                   |
| -------------- | ---------------------- | ------------------------------------------ |
| 指向对象       | inode                  | 路径名                                     |
| 本质           | 多个名字指向同一 inode | 一个特殊类型的文件，内容为目标路径         |
| 能否跨文件系统 | 通常不能               | 能                                         |
| 能否指向目录   | 通常不能               | 能                                         |
| 原文件删除后   | 其他硬链接仍有效       | 可能成为**悬空引用**（dangling reference） |

### 5.4.11 权限位与访问控制列表

权限位分三组：所有者、所属组、其他用户，每组 `r`（读，4）、`w`（写，2）、`x`（执行，1）。例如 `chmod 600` 表示只有所有者可读写（$6=4+2$）。

目录的含义略有不同：`r` 允许列出内容，`w` 允许创建或删除其中的项，`x` 允许进入（搜索）该目录。更精细的控制用**访问控制列表**（ACL），针对具体用户或组设置权限。

### 5.4.12 创建与挂载文件系统

`mkfs` 在某个分区上创建文件系统（含根目录等必要结构）；`mount` 把它接入统一目录树，例如 `mount -t ext3 /dev/sda1 /home/users`，之后该文件系统的根目录出现在 `/home/users`。

> [!warning] TOCTTOU：检查与使用之间的竞争
> **TOCTTOU**（Time Of Check To Time Of Use）：检查某个对象与真正使用它之间，对象可能被其他执行流改变。
>
> 例：具有 root 权限的邮件服务先用 `lstat()` 确认收件箱是普通文件，再向其追加。攻击者在两步之间把收件箱换成指向 `/etc/passwd` 的符号链接，服务就会把内容写进敏感文件。
>
> 对策：减少特权程序；用 `O_NOFOLLOW` 等机制；避免把检查与使用拆成有竞争窗口的两个操作。

### 5.4.13 小结

- 文件是字节数组，目录把名字映射到 inode；
- 描述符引用打开文件表项，偏移量决定下一次读写位置；
- `fsync()` 强制持久化，`rename()` 提供原子替换；
- `unlink()` 删除的是目录项，而不一定立即回收文件数据。

#### 关键术语

- **文件**（file）、**目录**（directory）、**inode**（index node）。
- **文件描述符**（fd）：进程引用已打开文件的整数。
- **打开文件表项**（open file entry）：保存偏移量与状态标志，可由多个描述符共享。
- **硬链接**（hard link）、**符号链接**（symbolic link）。
- **TOCTTOU**：检查与使用之间对象被改动的竞争。

# 第三部分 文件系统的组织与实现

## 5.5 文件系统实现：从抽象到磁盘布局

> [!question] 关键问题：如何实现文件系统
> 文件和目录在磁盘上以什么形式保存？如何记录数据块位置？如何分配和回收空间？一次读写要访问哪些数据结构？

### 5.5.1 整体组织

实现要考虑两方面：**数据结构**（内容、元数据、目录、空闲空间如何组织）与**访问路径**（`open` / `read` / `write` 如何访问这些结构）。以 vsfs（Very Simple File System）为例，假设磁盘由 64 个 4 KB 块（编号 $0\sim63$）组成：

| 区域       | 块数 | 内容                                                          |
| ---------- | ---- | ------------------------------------------------------------- |
| 超级块     | 1    | 文件系统全局信息（inode、数据块数量，inode 表起始位置等）     |
| inode 位图 | 1    | 记录 inode 是否已分配（0 空闲，1 已分配）                     |
| 数据位图   | 1    | 记录数据块是否已分配                                          |
| inode 表   | 5    | 每个 inode 256 B，每块 $4096/256=16$ 个，共 $5\times16=80$ 个 |
| 数据区域   | 56   | 文件内容                                                      |

挂载时操作系统先读超级块，据此定位其他结构。

### 5.5.2 inode：文件的元数据

每个 inode 有唯一编号 **i-number**，保存：文件类型、大小、权限、时间信息、链接计数、数据块指针。

**由 i-number 定位 inode**：设 inode 表起始于 12 KB，inode 大小 256 B，i-number 为 32：

$$
\text{偏移}=32\times256=8\ \text{KB},\quad \text{地址}=12+8=20\ \text{KB},\quad \text{扇区}=\frac{20\times1024}{512}=40
$$

一般地：`blk = (inumber * sizeof(inode_t)) / blockSize; sector = (blk * blockSize + inodeStartAddr) / sectorSize;`。

### 5.5.3 多级索引与 extent

inode 若含 12 个直接指针，只能直接定位 $12\times4\ \text{KB}=48\ \text{KB}$，所以引入**间接指针**：一级间接指针指向一个存放块地址的索引块。块大小 4 KB、地址 4 B 时，一个间接块含 $4096/4=1024$ 个指针，故最大文件为

$$
(12+1024)\times4\ \text{KB}=4144\ \text{KB}
$$

继续增加二级、三级间接指针，可再增加 $1024^2$、$1024^3$ 个数据块。这种**多级索引**（multi-level index）是一棵不平衡的树，因为文件系统中小文件远多于大文件：小文件只用直接指针，无需额外访问间接块。

| 方案           | 描述                                       | 优点                     | 缺点                                 |
| -------------- | ------------------------------------------ | ------------------------ | ------------------------------------ |
| 多级索引       | 逐块保存指针（ext2 / ext3）                | 灵活，随机访问方便       | 元数据开销较大                       |
| **extent**     | 用"起始块 + 长度"描述连续区间（ext4）      | 元数据紧凑，连续访问高效 | 需要寻找连续空间                     |
| 链表（如 FAT） | 每个块末尾指向下一块；FAT 把链表集中到表中 | 结构简单                 | 随机访问慢（FAT 通过内存中的表缓解） |

### 5.5.4 目录与空闲空间管理

**目录**本质上是特殊文件，数据由一系列目录项组成，每项含 inode 号、记录长度（`reclen`）、名字长度（`strlen`）与名字。`reclen` 帮助管理删除目录项后留下的空闲空间。

空闲空间用位图管理：创建文件时在 inode 位图中找空闲 inode，写入新数据时在数据位图中找空闲块。文件系统还可**预分配**（例如一次找 8 个连续空闲块），提高连续性。

### 5.5.5 文件访问路径

**打开文件** `open("/foo/bar", O_RDONLY)`：

1. 读根目录 inode。**根目录的 i-number 是约定好的**（UNIX 文件系统中为 2），因此文件系统知道从哪里开始；
2. 读根目录数据，查找 `foo`，得到其 inode 号；
3. 读 `foo` 的 inode，再读其目录数据，查找 `bar`；
4. 读 `bar` 的 inode，检查权限，在进程的打开文件表中分配表项，返回描述符。

所以打开文件的 I/O 开销与**路径长度**成正比。

**读文件** `read(fd, buf, 4096)`：按偏移量结合 inode 的指针找到数据块并读取，之后更新访问时间 atime——这在逻辑上是一次**额外的写 I/O**（读也会触发写）。读文件通常不需要访问位图，只有分配新空间时才查询位图。

**写文件**：写入已有数据块只需更新该块；若需要分配新块，则必须：读数据位图、写回位图、读 inode、写回 inode、写数据块。

| 操作         | I/O |
| ------------ | --- |
| 读数据位图   | 1   |
| 写回数据位图 | 1   |
| 读 inode     | 1   |
| 写回 inode   | 1   |
| 写数据块     | 1   |
| 总计         | 5   |

创建文件的开销更大，还要分配 inode、修改父目录并更新相关元数据（原书给出了具体 I/O 次数，需验证）。

> [!question] 关键问题：如何降低文件系统的 I/O 开销
> 一次简单的文件操作就可能产生大量分散的磁盘访问，如何减少？

### 5.5.6 缓存与缓冲

答案是充分利用 DRAM。

- **读缓存**：把常访问的块保存在内存中，再次访问同一文件时，目录 inode 与目录数据可直接命中。早期系统用固定大小缓存（LRU 替换），有浪费；现代系统把文件缓存与虚拟内存统一为**页缓存**（page cache），动态分配；
- **写缓冲**：延迟写入可以带来三个好处：**合并**对同一元数据的多次修改；**调度优化**，缓冲多个写请求后统一安排顺序；**避免无效写入**，如文件刚创建就删除，创建可能根本不必落盘。

现代文件系统通常把写缓冲数秒到数十秒。代价是：性能提高与崩溃时可能丢失未持久化数据互为取舍。需要强持久性的程序（如数据库）需要用 `fsync()` 主动控制落盘。

### 5.5.7 小结

| 数据结构     | 作用                          |
| ------------ | ----------------------------- |
| Superblock   | 描述整个文件系统              |
| Inode        | 保存文件元数据及数据块位置    |
| Directory    | 保存文件名与 inode 编号的映射 |
| Inode Bitmap | 管理 inode 空闲空间           |
| Data Bitmap  | 管理数据块空闲空间            |
| Data Region  | 保存实际文件内容              |

## 5.6 FFS：利用局部性提高文件系统性能

> [!question] 关键问题：如何组织磁盘数据以提高性能
> 如何安排 inode、目录和数据块的位置，使相关数据尽可能靠近，减少寻道？

### 5.6.1 早期文件系统的问题

早期 UNIX 文件系统布局很简单：超级块、inode 区、数据区依次排开，把磁盘当作随机访问存储器。问题有二：

1. **inode 与数据块距离过远**：读取文件先读 inode、再读数据块，两者相隔很远就会产生额外寻道；
2. **磁盘碎片化**：删除文件后空闲空间不连续。例如 A、B、C、D 各占 2 块，删除 B 和 D，空闲空间被分成两段；新文件 E 需要 4 块，只能分散存放，读取时就要在两段之间移动磁头。这是**外部碎片**（external fragmentation）带来的问题。

早期文件系统的块大小也很小（512 B），虽然减少了块内浪费，但增加了访问次数和定位开销。

### 5.6.2 FFS：磁盘感知的文件系统

伯克利的 **FFS**（Fast File System）保留 `open()` / `read()` / `write()` 等接口，重新设计内部组织。核心思想：

> 将相关的数据放在一起，将不相关的数据分开。

FFS 把磁盘划分为**柱面组**（cylinder group）：柱面由不同盘面上距主轴相同的磁道组成，柱面组由若干连续柱面构成。现代磁盘不向文件系统暴露几何结构，因此现代文件系统改用**块组**（block group）：把连续的逻辑块划分成若干组。

每个组内都有超级块副本（提高可靠性）、独立的 inode 位图与数据位图、inode 表和数据块。

### 5.6.3 分配策略

原则：经常一起访问的内容放在一起。

| 对象 | 策略                                                               |
| ---- | ------------------------------------------------------------------ |
| 目录 | 选择目录数量较少、空闲 inode 较多的组，把目录 inode 与数据放入该组 |
| 文件 | 数据块尽量与其 inode 在同一组；同一目录下的文件尽量放在目录所在组  |

例如 `/a/c`、`/a/d`、`/a/e` 会被放在同一组，而 `/b/f` 放在另一组。这依赖一个假设：**目录结构反映访问相关性**（如编译时连续访问同一目录下的多个源文件）。原书的访问轨迹分析也显示了明显的目录局部性。

但 FFS 无法捕获所有局部性：编译时可能交替访问 `src/foo.c` 与 `obj/foo.o`，这两个文件的共同祖先是 `project`，不在同一目录，简单的目录分组策略利用不到这种局部性。

### 5.6.4 大文件的处理

若把大文件的所有块都放在文件所在组，会迅速占满该组，妨碍同组内其他相关文件。FFS 的策略是：

- 前 12 个直接块放在 inode 所在组；
- 此后，**每个间接块及其指向的数据块**放入其他组。

这就带来一个问题：块分散在各组会增加寻道。FFS 通过**摊销**（amortization）解决：让每个连续放置的块组足够大，使传输时间占主导。这与 5.8.2 的段大小推导是同一个形式。设要达到峰值带宽的 $F$ 倍，则每次连续传输量为

$$
D=\frac{F}{1-F}\,R_{\text{peak}}\,T_{\text{position}}
$$

原书的例子：寻道时间 10 ms、传输率 40 MB/s、$F=0.5$ 时，每块应约 409.6 KB（参数需验证）。

### 5.6.5 其他 FFS 优化

原书（第 41 章）列出的其他改进：

| 改进                | 说明                                                                               |
| ------------------- | ---------------------------------------------------------------------------------- |
| **更大的块 + 子块** | 使用 4 KB 大块提升传输效率，同时用 512 B 子块（sub-block）存放小文件，减少内部碎片 |
| **参数化布局**      | 针对磁盘旋转特性优化连续块的排布，避免读完一块后下一块刚好转过去                   |
| **长文件名**        | 取消早期的文件名长度限制                                                           |
| **符号链接**        | 引入符号链接，可指向其他文件系统或目录                                             |
| **原子 `rename()`** | 提供文件重命名的原子操作                                                           |

> [!note] 延迟分配等机制不是 FFS 的内容，属于 ext4、XFS 等后继文件系统，此处不展开。

### 5.6.6 小结

FFS 的重要贡献是认识到文件系统不能忽略底层设备的物理特性：它通过柱面组 / 块组、目录局部性和大文件策略改善 HDD 上的访问性能，影响了后续文件系统的设计。

#### 关键术语

- **超级块**、**inode 表**、**位图**（bitmap）。
- **直接 / 间接指针**、**多级索引**、**extent**。
- **外部碎片**（external fragmentation）。
- **柱面组**（cylinder group）/ **块组**（block group）。

# 第四部分 文件系统的可靠性

文件系统的一次操作往往需要更新多个磁盘块，而磁盘无法保证这些更新整体原子完成。本部分讨论系统在更新过程中崩溃时如何保持一致。

## 5.7 崩溃一致性：fsck 与日志

> [!question] 关键问题：如何保证崩溃一致性
> 一次文件操作要更新多个磁盘块，若在更新过程中断电，磁盘上只保存了部分更新，文件系统如何恢复到一致状态？

### 5.7.1 一个具体例子

向文件追加一个数据块 $D_b$（放在块 5），需要更新三个结构：数据块 $D_b$、inode（大小改为 2，新增指向块 5 的指针）、数据位图（块 5 标记为已分配）。三者要分别写盘，崩溃时可能只完成其中一部分：

| 已写入的部分    | 结果                                                              |
| --------------- | ----------------------------------------------------------------- |
| 只写数据块      | 没有 inode 指向它，如同从未发生，元数据仍一致（但用户数据丢失）   |
| 只写 inode      | inode 指向块 5，但数据未写入，读到垃圾；且 inode 与位图**不一致** |
| 只写位图        | 块 5 被标记已分配，但无人使用，**空间泄漏**（space leak）         |
| 写 inode + 位图 | 元数据一致，但块 5 中是**垃圾数据**                               |
| 写 inode + 数据 | 内容存在，但 inode 与位图**不一致**                               |
| 写位图 + 数据   | 块 5 已分配但无 inode 指向，**空间泄漏**                          |

我们希望文件系统能从一个一致状态原子地转换到另一个一致状态，但磁盘只保证单次写入的原子性。这就是**崩溃一致性问题**（crash-consistency problem）。

### 5.7.2 方案一：fsck

早期做法是允许不一致发生，**重启时再修复**。`fsck`（file system checker）在挂载前扫描磁盘：

| 检查项      | 内容                                                   |
| ----------- | ------------------------------------------------------ |
| Superblock  | 检查全局参数是否合理                                   |
| Free blocks | 根据 inode 与间接块重新计算已分配的数据块（修复位图）  |
| Inode state | 检查类型与状态是否合法                                 |
| Inode links | 检查链接计数是否正确，无引用的 inode 放入 `lost+found` |
| Duplicates  | 检查是否有多个 inode 指向同一数据块                    |
| Bad blocks  | 检查指针是否越界                                       |
| Directories | 检查目录结构与目录项是否合法                           |

缺点：需扫描整个文件系统，随着磁盘与 RAID 容量增大，可能耗时数分钟甚至数小时。此外，fsck 只能修复**结构不一致**；如果 inode 与位图完全一致、但 inode 指向的数据是垃圾，fsck 无能为力。

### 5.7.3 方案二：日志（Journaling）

> [!question] 关键问题：如何避免崩溃后扫描整个磁盘
> 能否在修改文件系统之前先记录将要做的修改？崩溃后据此恢复，而不是扫描整个磁盘？

方案来自数据库的**预写日志**（write-ahead logging，WAL），在文件系统中称为 journaling：**在原地修改之前，先把更新记录到日志中**。日志中一个事务的格式为：

| 记录              | 内容                                         |
| ----------------- | -------------------------------------------- |
| `TxB`（事务开始） | 事务标识符，以及将要写入的块地址等信息       |
| 中间部分          | 更新后的 inode、位图、数据块（**物理日志**） |
| `TxE`（事务结束） | 同一事务标识符                               |

**物理日志**（physical logging）直接记录块的内容；**逻辑日志**（logical logging）记录操作本身（如"向文件 X 追加块 $D_b$"），更紧凑，但恢复时需重新解释并执行，复杂度更高。

### 5.7.4 数据日志的协议

完整的**数据日志**（data journaling）协议分**三步**：

1. **日志写**（journal write）：写入 `TxB`、inode、位图、数据块，**不含 `TxE`**，等待这些写入完成；
2. **日志提交**（journal commit）：单独写入 `TxE`，等待完成，此后事务才算已提交；
3. **检查点**（checkpoint）：把日志中的更新写回文件系统原位置。

**为什么必须把提交单独成一步**：磁盘内部可能重排写入顺序。若 `TxB … TxE` 一次发出，磁盘可能先写 `TxB`、inode、位图和 `TxE`，而数据块尚未落盘，此时断电，恢复程序会因为 `TxB` 与 `TxE` 匹配而把事务当作完整，**重放出垃圾数据**。因此 `TxE` 必须在前面各块都落盘之后再写。

> [!note] 优化
> 在 `TxB` 和 `TxE` 中加入整个事务的**校验和**，恢复时重新计算校验和，若不匹配则忽略该事务。这样前两步可以合并为一次发出，减少一次等待。

**恢复**：崩溃后读取日志，已提交（`TxE` 完整落盘）的事务被**重放**（redo）；未提交的事务忽略。因为只需扫描日志而不是整个磁盘，恢复比 fsck 快得多。

### 5.7.5 批量日志更新与有限大小的日志

**批量更新**：若每次更新都单独写日志并等待落盘，开销太大。例如连续创建两个文件，会反复修改同一个 inode 位图与目录块。所以日志系统把多个**更新**缓冲在内存中，合并成**一个全局事务**，一起提交，既减少了磁盘写入次数，也避免了对同一结构的重复写入。

**有限日志**：日志空间有限，通常组织成**循环结构**。事务检查点完成后，其日志空间才可以回收，使用**日志超级块**标记哪些事务已经被检查点，以便在恢复时只重放未完成的事务。

### 5.7.6 元数据日志

数据日志要把每个数据块写两次（日志一次、最终位置一次），开销大。**元数据日志**（metadata journaling）只把元数据写入日志，用户数据直接写到最终位置。ext3 提供三种模式：

| 模式        | 日志内容      | 说明                                        |
| ----------- | ------------- | ------------------------------------------- |
| data        | 数据 + 元数据 | 完整数据日志，最安全，最慢                  |
| **ordered** | 仅元数据      | 数据**先于**元数据写盘（ext3 默认，需验证） |
| writeback   | 仅元数据      | 不保证数据与元数据的顺序，最快              |

元数据日志的协议（五步）：

1. **数据写**：把数据写到最终位置（可与第 2 步并行发出，但必须在第 3 步之前完成）；
2. **日志元数据写**：写入 `TxB` 与元数据块；
3. **日志提交**：写入 `TxE`；
4. **检查点元数据**：把元数据写到最终位置；
5. **释放**：在日志超级块中标记该事务空闲。

规则是：**数据必须先于相关元数据落盘**。否则可能出现：元数据已提交，指向的数据块却还没写，崩溃后文件结构一致，内容却是垃圾。

### 5.7.7 块重用问题

日志引入一个微妙的问题：**块重用**（block reuse）。设目录 `foo` 的数据块（属于**元数据**，因此记入日志）已写入日志；随后 `foo` 被删除，其数据块被释放，并重新分配给文件 `bar` 存放**用户数据**。若此时崩溃，恢复程序**重放旧的日志**，会把该块覆盖成旧目录内容，`bar` 的数据就被破坏了。（用户数据不在元数据日志里，所以不是用户数据被重放覆盖。）

对策：

- **撤销记录**（revoke record）：删除目录时在日志中写入撤销记录，恢复时遇到被撤销的块就跳过；
- 或者在删除操作所在事务被检查点之前，不重用该块。

### 5.7.8 其他方案

| 方案                   | 核心思想                                   | 特点                        |
| ---------------------- | ------------------------------------------ | --------------------------- |
| fsck                   | 崩溃后扫描并修复                           | 实现直接，恢复慢            |
| Journaling             | 修改前先记录日志                           | 恢复快，增加写入开销        |
| 写时复制（COW）        | 不覆盖旧数据，把新版本写到别处再切换引用   | 避免直接覆盖（如 LFS、ZFS） |
| 软更新（Soft Updates） | 精心安排元数据写入顺序，避免某些不一致状态 | 依赖复杂的依赖关系管理      |

## 5.8 LFS：日志结构文件系统

传统文件系统直接覆盖旧数据，更新大量分散的元数据时需频繁寻道。LFS 的思路是：**不覆盖，而是把所有更新顺序追加到新位置**。

> [!question] 关键问题：如何把所有写入变为顺序写入
> 磁盘随机写入很慢。如果能把所有更新集中起来、一次性顺序写入，能否显著提高写入性能？

### 5.8.1 顺序写入与段

LFS 把更新（数据块与新 inode 等）缓存在内存中，积累到一定数量后，作为一个较大的连续写入区域——**段**（segment）一次性写入磁盘。仅仅顺序写还不够：两次写即使相邻，磁盘也可能已经转过，使第二次需等待接近一圈。所以必须先**缓冲**足够的数据再写。

**段大小的选取**：设 $T_{\text{position}}$ 为定位时间，$R_{\text{peak}}$ 为峰值传输率，$D$ 为一次写入量。有效写入速率为

$$
R_{\text{effective}}=\frac{D}{T_{\text{position}}+D/R_{\text{peak}}}
$$

要达到峰值的 $F$ 倍（$R_{\text{effective}}=F\,R_{\text{peak}}$），解得

$$
D=\frac{F}{1-F}\,R_{\text{peak}}\,T_{\text{position}}
$$

例：定位时间 10 ms，峰值 100 MB/s，$F=0.9$：$D=\frac{0.9}{0.1}\times100\ \text{MB/s}\times0.01\ \text{s}=9\ \text{MB}$。

### 5.8.2 inode 映射表与检查点区域

传统文件系统的 inode 位于固定位置，可直接计算；LFS 的 inode 不断写到新位置，所以需要 **inode 映射表**（inode map，imap）：

$$
\text{inode number}\longrightarrow\text{最新 inode 的磁盘地址}
$$

imap 的更新与数据、inode 一起写入当前段，不需要寻道到固定位置修改。但 imap 本身也分散在磁盘上，所以 LFS 在固定位置保存**检查点区域**（Checkpoint Region，CR），记录最新 imap 各部分的位置。定位关系为：

| 层次              | 作用                  |
| ----------------- | --------------------- |
| Checkpoint Region | 指向 imap 各部分      |
| Inode Map         | inode 号 → inode 地址 |
| Inode             | 指向数据块            |
| Data Blocks       | 文件内容              |

CR 只**定期**更新（如每 30 秒），不是每次写入都更新，避免频繁更新固定位置带来的性能损失。

**读文件**：先读 CR，找到并读入 imap（之后缓存在内存），再据 inode 号查得 inode 地址，读 inode，按指针读数据。imap 已缓存时，过程与传统文件系统相近。

### 5.8.3 目录与递归更新问题

目录项保存的是 **inode 号**，而非 inode 的物理地址。若保存物理地址，inode 每移动一次，就要更新目录项；目录自身移动后又要更新其父目录……沿树向上产生**递归更新问题**（recursive update problem）。imap 的间接层消除了这个问题：inode 位置变化时只需更新 imap。

### 5.8.4 垃圾回收（清理）

LFS 不断写新版本，旧版本留下**垃圾**。**清理**（cleaning）以段为单位：

1. 读入若干旧段；
2. 找出其中仍然**存活**的块；
3. 把存活块复制到新段；
4. 释放旧段。

**如何判断块是否存活**：每个段中有**段摘要块**（segment summary block），记录该段每个数据块所属的 inode 号及块偏移。清理时读取摘要，据此查 imap 得到该 inode 的最新版本，检查其对应指针是否仍指向这个块：指向则存活，否则是垃圾。LFS 还可以用**版本号**加速：文件被删除或截断时递增版本号，摘要中版本号不匹配就可直接判为垃圾。

**清理策略**：有效数据比例低的段回收代价小，应优先；原书还区分**冷热**数据：冷段（内容很少变化）可以较早清理，因为其中的存活数据在较长时间内都不会变成垃圾；热段（内容经常被覆盖）应晚一些清理，让更多块自己变成垃圾。清理开销直接影响写入放大与整体性能。

### 5.8.5 崩溃恢复

CR 有**两份**，分别位于磁盘两端，**交替**更新。每份的首尾各写一个时间戳；更新时若崩溃，首尾时间戳不一致，就知道这份 CR 不完整，恢复时使用另一份。

恢复从最近的有效 CR 出发，但 CR 之后可能已有新的段写入。LFS 因此通过**向前滚动**（roll forward）读取 CR 之后的段，找出崩溃前完整提交的更新，并应用到文件系统。

### 5.8.6 小结

| 机制              | 作用                          |
| ----------------- | ----------------------------- |
| Segment           | 把多个更新合并成连续写入      |
| Inode Map         | 把 inode 号映射到最新物理位置 |
| Checkpoint Region | 定位最新的 imap               |
| Cleaning          | 回收不再使用的旧版本数据      |
| Roll forward      | 崩溃后从最近 CR 恢复          |

LFS 用额外的空间管理与垃圾回收开销，换取高效的顺序写入。

#### 关键术语

- **崩溃一致性**（crash consistency）、**fsck**。
- **预写日志**（WAL）/ **日志**（journaling）、**检查点**（checkpoint）、**元数据日志**。
- **块重用**（block reuse）、**撤销记录**（revoke record）。
- **日志结构文件系统**（LFS）、**段**（segment）、**清理**（cleaning）。
- **写入放大**（write amplification）：实际写入量大于用户请求量。

# 第五部分 现代存储与数据完整性

## 5.9 SSD：闪存与闪存转换层

> [!question] 关键问题：如何利用闪存构建高性能存储设备
> 闪存与磁盘有何不同？为什么 SSD 不能像磁盘那样直接覆盖写入？如何通过闪存转换层提供统一的块接口？

### 5.9.1 闪存的结构与基本操作

SSD 的存储介质是 NAND 闪存，用存储单元中的电荷状态表示数据。每个单元的比特数：SLC 1、MLC 2、TLC 3；（QLC 为 4，是笔记补充，非原书内容）。比特越多，密度越高，但可靠性与耐久性通常越低。

组织层次：Chip → Die → Plane → **Block**（擦除的基本单位）→ **Page**（读取和编程的基本单位）。典型页大小为几 KB，一个块包含多个页。

| 操作    | 作用     | 单位  | 相对开销             |
| ------- | -------- | ----- | -------------------- |
| Read    | 读取数据 | Page  | 最快（数十微秒量级） |
| Program | 写入数据 | Page  | 较慢（数百微秒量级） |
| Erase   | 擦除数据 | Block | 最慢（毫秒量级）     |

具体数值依类型而异（需验证），重要的是量级关系：读 ≪ 编程 ≪ 擦除。

**关键限制**：页必须先擦除才能编程，而擦除以**整个块**为单位。要修改块内的一个页，必须先把块里仍有效的页复制走、擦除整块、再重新编程。页的状态为：INVALID（尚未有效写入）、ERASED（已擦除，可编程）、VALID（有有效数据）。

### 5.9.2 性能与可靠性

没有机械结构，随机读性能很好。可靠性问题有两类：

- **磨损**（wear out）：一次编程与擦除称为 **P/E Cycle**，次数增加后块逐渐失效，每个块的擦写寿命有限；
- **干扰**（disturbance）：读取或编程某个页可能影响同块中邻近页的比特。

### 5.9.3 从闪存到 SSD：FTL

闪存只能"按页编程、按块擦除"，而上层期望块设备接口 `Read(LBA)` / `Write(LBA, Data)`。所以 SSD 内部有一个控制层——**闪存转换层**（Flash Translation Layer，FTL），负责逻辑块到物理页的转换。SSD 含 NAND 闪存、易失性内存（缓存与映射表）、控制器与 FTL。

**直接映射**（逻辑页 $N$ 对应物理页 $N$）是个糟糕的方案：改一个页需要读整块、改内存、擦整块、重写所有页，小写入代价巨大，且反复擦同一个块造成磨损集中。

### 5.9.4 日志结构 FTL

现代 FTL 采用日志结构思想：写入逻辑块 $N$ 时，不覆盖原位置，而是写到一个新的空闲物理页，再更新**映射表**（逻辑块 → 物理页）；旧页变成垃圾，之后回收。读取时查映射表找到最新版本。这避免了读-修改-写，也把写入分散到不同物理块。

### 5.9.5 垃圾回收与过量预留

和 LFS 类似，SSD 也需要**垃圾回收**（GC）：

1. 选择一个物理块，找出其中仍有效的页；
2. 把有效页复制到其他位置；
3. 擦除整个块，重新加入空闲空间。

有效页越少，回收代价越低。**过量预留**（overprovisioning）：SSD 实际闪存容量大于用户可见容量，多出的空间供 FTL 做垃圾回收与映射，使 GC 可以在后台进行。

**TRIM**：文件系统通过 TRIM 命令告诉 SSD 哪些逻辑块已被删除，FTL 就可以把对应物理页直接视为垃圾，不必在 GC 时复制，减轻 GC 负担。

### 5.9.6 映射表的开销与映射方案

1 TB SSD、4 KB 页、每项 4 B：映射项数为 $1\ \text{TB}/4\ \text{KB}=2^{28}$，映射表为 $2^{28}\times4\ \text{B}=1\ \text{GB}$，仅映射就占 1 GB 内存。因此需要减小映射表：

| 方案              | 做法                                                                             | 优点           | 缺点                                     |
| ----------------- | -------------------------------------------------------------------------------- | -------------- | ---------------------------------------- |
| **块级映射**      | 每个物理块一个映射项                                                             | 映射表很小     | 小写入昂贵：改一页需把块内其余页一起重写 |
| **混合映射**      | 块级映射的 Data Table + 页级映射的 Log Table；保留一部分物理块作日志块接收新写入 | 兼顾灵活与内存 | 日志块需定期合并                         |
| **页映射 + 缓存** | 仍用页级映射，只把活跃映射项放内存                                               | 内存占用小     | 映射项不在缓存时需额外读取               |

混合映射的日志块合并有三种：

| 合并类型      | 情形                                           | 开销 |
| ------------- | ---------------------------------------------- | ---- |
| Switch merge  | 日志块的页恰好能完整替换原数据块，直接切换映射 | 最小 |
| Partial merge | 仅需从旧数据块复制部分有效页                   | 中等 |
| Full merge    | 需从多处收集页，重新组成完整块                 | 最大 |

### 5.9.7 磨损均衡

闪存块寿命有限，需要把擦写尽量分散到所有块（**磨损均衡**，wear leveling）。日志结构写入自然分散了一部分写入，但某些块可能长期存放**不再修改的数据**，很少被擦除，而其他块被反复使用。所以 FTL 需要主动把这类长期数据迁移走，让原来的块重新参与写入。这会增加额外复制，即**写入放大**。

### 5.9.8 SSD 与 HDD 比较

| 比较         | HDD                  | SSD                    |
| ------------ | -------------------- | ---------------------- |
| 随机读取     | 受寻道与旋转延迟限制 | 无机械寻道，速度高     |
| 顺序读取     | 较好                 | 通常更快               |
| 随机写入     | 需要机械定位         | 受编程、擦除与 GC 影响 |
| 寿命         | 无闪存 P/E 限制      | 存在有限 P/E Cycle     |
| 单位容量成本 | 较低                 | 较高                   |

SSD 的随机 I/O 性能远高于 HDD，且 **SSD 的顺序与随机性能之间的差距比 HDD 小得多**；但文件系统仍倾向于大块顺序写入，因为这有利于 SSD 的 FTL。成本与内部复杂度也更高。

### 5.9.9 小结

| 问题                 | 机制                |
| -------------------- | ------------------- |
| 逻辑块与物理页不一致 | 地址映射            |
| 不能直接覆盖写入     | 日志结构写入        |
| 旧版本占据空间       | 垃圾回收（含 TRIM） |
| 映射表过大           | 块级 / 混合映射     |
| 闪存擦写寿命有限     | 磨损均衡            |

## 5.10 数据完整性与保护

存储设备即使正常响应，也不能保证返回的数据正确。可靠的存储系统不仅要保存数据，还要**检测损坏**并尽可能恢复。

> [!question] 关键问题：如何保证持久化数据的完整性
> 如果磁盘返回了错误数据，或者写入的数据没有真正保存，操作系统如何发现？如何利用冗余恢复？

### 5.10.1 磁盘故障模式

5.3 的 fail-stop 模型过于简化。现代磁盘还存在 **fail-partial** 故障：整盘仍然工作，但部分块出问题。两类典型情形：

| 类型                                         | 说明                                                             | 是否被设备发现 |
| -------------------------------------------- | ---------------------------------------------------------------- | -------------- |
| **潜在扇区错误**（Latent Sector Error，LSE） | 某个扇区无法读取，设备返回错误                                   | 是（显式错误） |
| **数据损坏**（corruption）                   | 设备能返回数据，但内容已变化（比特翻转、被错误覆盖、控制器错误） | **否**（静默） |

静默数据损坏更危险：设备报告读取成功，上层却拿到错误数据。

### 5.10.2 处理潜在扇区错误

LSE 容易处理，因为设备已明确报告。RAID 1 可以读另一个副本；RAID 4/5 可以用同条带上的其他数据与校验重新计算。但如果一整块盘已经损坏，重建过程中又在其他盘上遇到 LSE，就可能无法恢复。解决办法是增加第二份校验，例如 NetApp RAID-DP 的双校验，代价是额外的存储空间。

### 5.10.3 校验和：检测静默损坏

**校验和**（checksum）是一个函数 $C(D)$，把一个数据块（如 4 KB）压缩为一个很小的摘要（如 4 B 或 8 B）。写入时同时保存 $C_s(D)$；读取时重新计算 $C_c(D)$，比较两者：

$$
C_s(D) \stackrel{?}{=} C_c(D)
$$

不等则说明数据损坏；此时若有冗余副本可以恢复，否则只能向上层返回错误。校验和只**检测**损坏，不能自己恢复数据。

### 5.10.4 常见校验和算法

| 算法     | 做法                                                                       | 特点                                           |
| -------- | -------------------------------------------------------------------------- | ---------------------------------------------- |
| XOR      | 把数据分成相同大小的单元，逐位异或 $C=D_0\oplus D_1\oplus\cdots\oplus D_n$ | 简单快速；同一位置的两个比特同时翻转时检测不出 |
| 加法     | 对数据单元做补码加法，忽略溢出                                             | 快；对数据整体移动等变化不敏感                 |
| Fletcher | 两个累积值：$s_1=(s_1+d_i)\bmod255$，$s_2=(s_2+s_1)\bmod255$               | 能检测单比特、双比特及许多突发错误             |
| CRC      | 把数据视为二进制多项式，除以约定的生成多项式，余数即校验值                 | 在网络与存储中广泛使用，检测能力强             |

不存在完美的校验和：输入远大于输出，必然存在不同数据产生相同校验值的**碰撞**（collision）。好的校验和需要碰撞概率低、计算开销小。

### 5.10.5 校验和的布局

最简单的做法是把校验和与数据放在一起：`| C(D0) | D0 | C(D1) | D1 | …`。但磁盘以 512 B 扇区为单位读写，校验和只有几个字节：

- 一种方案是使用 **520 B 扇区**，多出的 8 B 存校验和（要磁盘支持）；
- 另一种是把多个校验和集中存放：更新某个数据块时需读取校验和所在扇区、修改、写回，再写数据块，**多出额外 I/O**。

### 5.10.6 错误位置写入与丢失写入

校验和对另外两种故障不够：

| 故障                                  | 描述                                                                   | 对策                                                                            |
| ------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| **错误位置写入**（misdirected write） | 本应写到地址 $X$ 的数据被写到了 $Y$，数据本身正确，校验和无法发现      | 在校验信息中加入**物理位置标识**（Disk ID、Block ID），读取时一并核对           |
| **丢失写入**（lost write）            | 设备报告写入成功，实际没有落盘，仍是旧内容；旧数据的校验和与位置都正确 | **写后验证**（read-after-write），但会使写入 I/O 翻倍；或在其他位置保存校验信息 |

后一种方案的例子是 ZFS：在 inode 与间接块中保存数据块的校验和，丢失写入使旧数据的校验和与 inode 中的新校验和不一致，从而被发现。局限在于：若数据块与存放其校验和的 inode 的写入**同时丢失**，就无法检测。

### 5.10.7 巡检

长期没有被访问的数据，其校验和也长期没有被检查。存储系统会定期**巡检**（scrubbing）：顺序读取各块、重新计算校验和并与已保存的比较，发现错误则用冗余恢复。巡检通常在夜间或负载较低时按日或按周执行，目的是尽早发现损坏，避免所有副本同时损坏。

### 5.10.8 校验和的开销

**空间**：4 KB 数据块配 8 B 校验和，开销约 $8/4096\approx0.2\%$，很小。**时间**：写入时计算、读取时重新计算、访问校验和本身的额外 I/O、后台巡检的 I/O。一种优化是**在数据复制时同时计算校验和**（如内核把数据从页缓存复制到用户缓冲区时），避免单独再遍历一遍数据。

### 5.10.9 小结

| 故障                 | 处理方式                     |
| -------------------- | ---------------------------- |
| 磁盘整体故障         | RAID 冗余                    |
| 潜在扇区错误         | 副本或奇偶校验恢复           |
| 静默数据损坏         | 校验和检测                   |
| 错误位置写入         | 校验信息加物理位置标识       |
| 丢失写入             | 写后验证或跨位置保存校验信息 |
| 长期未访问数据的损坏 | 定期巡检                     |

#### 关键术语

- **闪存转换层**（FTL）、**垃圾回收**（GC）、**磨损均衡**（wear leveling）、**P/E Cycle**、**过量预留**（overprovisioning）、**TRIM**。
- **潜在扇区错误**（LSE）、**静默数据损坏**（silent corruption）、**校验和**（checksum）、**巡检**（scrubbing）。

## 5.11 小结：从磁盘到可靠存储

持久化系统可以抽象为如下层次：

| 层次              | 内容                   |
| ----------------- | ---------------------- |
| 应用程序          | 通过文件与目录接口访问 |
| 文件系统          | inode、位图、日志      |
| 块设备接口        | 逻辑块地址             |
| RAID / 存储控制器 | 条带化、镜像、奇偶校验 |
| HDD / SSD / 闪存  | 物理存储介质           |

| 领域         | 核心机制                 | 解决的问题                     |
| ------------ | ------------------------ | ------------------------------ |
| I/O          | 中断、DMA                | 降低 CPU 参与设备交互的开销    |
| HDD          | 寻道、旋转延迟、磁盘调度 | 理解并优化磁盘访问性能         |
| RAID         | 条带化、镜像、奇偶校验   | 提高容量利用率、性能和容错能力 |
| 文件接口     | fd、inode、目录、链接    | 提供持久化数据的抽象           |
| 文件系统实现 | 位图、多级索引、页缓存   | 组织数据并减少 I/O             |
| FFS          | 柱面组 / 块组、局部性    | 优化磁盘数据布局               |
| 崩溃一致性   | fsck、日志（journaling） | 处理多块更新中途崩溃           |
| LFS          | 段、imap、清理           | 把随机更新转换为顺序写入       |
| SSD          | FTL、垃圾回收、磨损均衡  | 管理闪存的读写限制和有限寿命   |
| 数据完整性   | 校验和、巡检             | 检测并恢复数据损坏             |

持久化系统始终围绕三个目标：**性能**（DMA、缓存、磁盘调度、FFS、LFS、SSD 内部优化）、**可靠性**（RAID、日志、冗余、垃圾回收）、**数据完整性**（校验和、位置标识、巡检）。

> [!important] 并发与持久化的对照
>
> - 虚拟化通过抽象隐藏底层资源的复杂性；
> - 并发通过同步原语保证多个执行流之间的正确协作；
> - 持久化通过数据结构、写入顺序、日志与冗余，保证数据能够跨越系统重启与设备故障而存在。

> [!important] 个人总结
> 持久化的主线可以概括为五步：**先把数据送上设备**（中断、DMA、磁盘调度），**再用冗余换可靠性**（RAID），**用抽象和布局换性能**（文件接口、inode、FFS），**用日志与顺序写入换崩溃一致性**（journaling、LFS），**最后用 FTL 与校验和换现代设备的可用性**。每一层都在容量、性能、可靠性与复杂度之间取舍，没有一种机制能同时把四者做到最好。

> [!important] 持久化是跨层的纪律
> 与并发类似，持久化的难点不在单个机制，而在**跨层的契约**：文件系统依赖磁盘的写入顺序，日志依赖屏障与提交记录，SSD 依赖 FTL 维持逻辑块的假象，校验和只有配合冗余才能真正从损坏中恢复。任何一层悄悄违背契约，上层精心设计的正确性都会失效。
