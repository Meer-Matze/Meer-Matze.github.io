# 第一部分 控制流与异常控制流

## 8.1 控制流

从处理器加电开始，到断电为止，程序计数器（PC）形成的值序列可以表示为

$$a_0,\; a_1,\; a_2,\; \cdots,\; a_{n-1}$$

其中 $a_k$ 表示第 $k$ 条指令 $I_k$ 的地址。每次从 $a_k$ 到 $a_{k+1}$ 的过渡称为一次**控制转移**（control transfer），这样的序列称为处理器的**控制流**（control flow）。

如果每条指令的地址都按顺序推进，那么控制流是最简单的"平滑"控制流。控制流的突变通常由跳转、调用、返回或异常引起。

## 8.2 异常控制流

除了程序自身的执行路径，计算机系统还必须响应外部事件和系统状态变化，例如：

- 定时器周期性触发中断
- 网络适配器收到数据包
- 磁盘 I/O 完成
- 子进程终止

这些事件并不一定与当前程序的局部变量有关，但系统必须对它们做出反应。现代系统通过引入**异常控制流**（Exceptional Control Flow，ECF）来处理这类情况——ECF 是由异常、进程、信号和非本地跳转等机制引起的**控制流突变**。

理解 ECF 很重要，原因包括：

1. 它是操作系统实现 I/O、进程和虚拟内存的基本机制
2. 它解释了应用程序如何通过系统调用与操作系统交互
3. 它帮助我们编写 shell、服务器等依赖进程管理的程序
4. 它是理解并发、线程、信号与中断的基础
5. 它帮助我们理解 C++、Java 等语言中的软件异常如何实现

# 第二部分 异常

## 8.3 异常处理机制

在处理器中，状态由不同的位和信号编码。任何状态变化都可视为一个**事件**（event）。事件可能由正在执行的指令引起，也可能由外部设备引起。处理器检测到事件后，会从应用程序切换到异常处理程序；处理完成后，处理器可能返回应用程序，也可能终止它。

异常处理是硬件与软件协同完成的：硬件负责检测事件并完成控制转移，操作系统负责提供对应的处理程序。

处理器通过一张叫做**异常表**（exception table）的跳转表，将控制间接转移到某个专门的**异常处理程序**（exception handler）。异常表的起始地址通常保存在特殊寄存器中，系统启动时由操作系统初始化并加载。

异常处理与函数调用类似，但有三个关键区别：

1. 返回地址可能是当前指令，也可能是下一条指令
2. 处理异常时，处理器会保存额外状态，以便恢复现场
3. 如果进入内核，保存状态的是**内核栈**，不是用户栈

异常处理结束后，通常有三种可能的结果：

- 返回到当前指令 $I_{curr}$
- 返回到下一条指令 $I_{next}$
- 终止被中断的程序

## 8.4 异常类型

异常可以分为四类：中断（interrupt）、陷阱（trap）、故障（fault）和终止（abort）。

| 类别 | 原因                | 异步/同步 | 返回行为             |
| :--: | ------------------- | :-------: | -------------------- |
| 中断 | 来自 I/O 设备的信号 |   异步    | 总是返回到下一条指令 |
| 陷阱 | 人为设置的异常      |   同步    | 总是返回到下一条指令 |
| 故障 | 潜在可恢复的错误    |   同步    | 可能返回到当前指令   |
| 终止 | 不可恢复的错误      |   同步    | 不会返回             |

### 8.4.1 中断

中断由处理器外部的 I/O 设备产生，例如网络适配器、磁盘控制器和定时器芯片。设备通过处理器芯片上的引脚发信号，并把异常号放到系统总线上。处理器在当前指令完成后检测到中断，再从总线读取异常号，调用对应的中断处理程序。处理结束后，控制返回到下一条指令。

中断是**异步**的，因为它与当前正在执行的指令没有直接因果关系。

### 8.4.2 陷阱与系统调用

陷阱是**有意的同步异常**。最重要的用途是向操作系统内核请求服务，也就是**系统调用**（system call）。

例如，`read`、`fork`、`execve`、`exit` 等服务都需要通过系统调用完成。处理器提供一条特殊的 `syscall` 指令，用户程序执行该指令后会陷入内核，由内核解析参数并调用相应的服务例程。

### 8.4.3 故障

故障由错误情况引起，但它可能是可恢复的。发生故障时，处理器将控制转移给故障处理程序：

- 如果错误可修正，处理程序修正后返回到引起故障的指令，指令会重新执行
- 如果不能修正，处理程序转交给 abort 例程，由其终止程序

最典型的故障是**缺页异常**：当虚拟地址对应的页面不在内存中时，会触发故障。缺页处理程序从磁盘把页面调入内存，然后返回到原指令，原指令再次执行时就不会再故障。

### 8.4.4 终止

终止是不可恢复的致命错误，通常是硬件层面的严重问题，比如 DRAM 或 SRAM 位损坏引起的奇偶错误。终止处理程序不会返回，而是直接结束程序。

## 8.5 Linux/x86-64 系统中的异常

在 x86-64 系统中定义了 256 种异常类型。0\~31 号由 Intel 架构定义，32\~255 号由操作系统定义。

| 异常号 | 描述                     |     异常类别     |
| :----: | ------------------------ | :--------------: |
|   0    | Divide Error             |      Fault       |
|   13   | General Protection Fault |      Fault       |
|   14   | Page Fault               |      Fault       |
|   18   | Machine Check            |      Abort       |
| 32~255 | OS-defined exceptions    | Trap / Interrupt |

### 8.5.1 常见故障与终止

- **除零错误**：应用试图除以零，或除法结果对目标操作数太大时触发异常 0。Unix 通常不尝试恢复，shell 往往报告为 `Floating exception`
- **一般保护故障**：程序引用未定义虚拟内存区域或试图写只读文本段时触发异常 13，shell 通常报告为 `Segmentation fault`
- **缺页异常**：异常 14 可恢复，处理程序将页面从磁盘调入内存后重新执行原指令
- **机器检查**：异常 18 表示检测到致命硬件错误，处理程序不返回

### 8.5.2 Linux/x86-64 系统调用

Linux 提供几百种系统调用，下面是常见的一部分（编号来自 CSAPP 原书，与实际 Linux x86-64 ABI 可能存在细微出入，实际编程时应以内核头文件为准）：

| 编号 | 名称    | 描述               | 编号 | 名称     | 描述             |
| :--: | ------- | ------------------ | :--: | -------- | ---------------- |
|  0   | `read`  | 读文件             |  33  | `pause`  | 挂起直到信号到达 |
|  1   | `write` | 写文件             |  37  | `alarm`  | 发送定时器信号   |
|  2   | `open`  | 打开文件           |  39  | `getpid` | 获取进程 ID      |
|  3   | `close` | 关闭文件           |  57  | `fork`   | 创建新进程       |
|  4   | `stat`  | 获取文件信息       |  59  | `execve` | 执行新程序       |
|  9   | `mmap`  | 将内存页映射到文件 |  60  | `_exit`  | 终止进程         |
|  12  | `brk`   | 调整堆顶           |  61  | `wait4`  | 等待进程终止     |
|  32  | `dup2`  | 复制文件描述符     |  62  | `kill`   | 发送信号         |

系统调用通过 `syscall` 指令进入内核，参数通过寄存器传递：

- `%rax`：系统调用号
- `%rdi`、`%rsi`、`%rdx`、`%r10`、`%r8`、`%r9`：最多 6 个参数
- `%rcx`、`%r11`：返回时会被内核破坏，调用前如有需要应自行保存
- `%rax`：返回值；返回值在 $-4095$ 到 $-1$ 之间时表示出错，对应负的 `errno`

一个简单的 hello world 可以直接使用系统调用：

```c
int main() {
    write(1, "hello, world\n", 13);
    _exit(0);
}
```

对应的汇编实现：

```asm
.section .data
string:
  .ascii "hello, world\n"
string_end:
  .equ len, string_end - string
.section .text
.globl main
main:
  # First, call write(1, "hello, world\n", 13)
  movq $1, %rax                 # write is system call 1
  movq $1, %rdi                 # Arg1: stdout has descriptor 1
  movq $string, %rsi            # Arg2: hello world string
  movq $len, %rdx               # Arg3: string length
  syscall                       # Make the system call

  # Next, call _exit(0)
  movq $60, %rax                # _exit is system call 60
  movq $0, %rdi                 # Arg1: exit status is 0
  syscall                       # Make the system call
```

# 第三部分 进程

## 8.6 进程

异常是操作系统内核提供**进程**（process）概念的基本构造块。一个进程是一个执行中程序的实例，每个进程都运行在某个**上下文**（context）中。上下文包含程序正确运行所需的状态：代码、数据、栈、通用寄存器、程序计数器、环境变量以及打开文件描述符等。

> [!tip] shell中的进程
> 在 Unix shell 中，每条命令都运行在一个独立的进程中。

进程向程序提供两种关键抽象：

- 一个独立的逻辑控制流，好像它独占了 CPU
- 一个私有的地址空间，好像它独占了整个内存系统

## 8.7 逻辑控制流与并发流

如果我们跟踪一个程序的 PC 值，就会看到一个只属于该程序的 PC 序列，这就是**逻辑控制流**（logical control flow）。多个逻辑流在时间上重叠时，就是**并发流**（concurrent flows）。

处理器只有一个物理控制流，但内核会把它分成多个逻辑流，每个进程分到自己的**时间片**（time slice）——进程交替运行，看上去像是独占 CPU，其实只是被快速轮换调度。

> [!tip] 并发与并行
>
> 并发（concurrent）是逻辑上的同时执行，只要求多个逻辑流同时处于Running状态（包括挂起），从这个角度看并行（parallel）是更严格的并发。
>
> - 在单核处理器上，多个进程通过时间片轮换实现并发（逻辑上并行，物理上串行）
> - 在多核处理器上，运行在不同核心上的流才是真正的**并行流**（parallel flows），物理上同时执行。

## 8.8 私有地址空间

进程为每个程序提供一个私有地址空间，好像它独占了整个内存系统。一般而言，一个进程中的地址对应的内存字节不能被其他进程直接读写。

## 8.9 用户模式和内核模式

处理器通过**模式位**（mode bit）限制进程可以执行的指令和访问的地址范围：

- **内核模式**：可以执行任意指令并访问任意内存
- **用户模式**：不能执行特权指令（priviledged instruction），也不能直接访问内核区地址

应用程序初始运行在用户模式中，只能通过中断、故障或系统调用进入内核模式。处理完毕后，处理器会切回用户模式。

Linux 提供 `/proc` 文件系统，让用户程序以文本形式读取一些内核数据结构，例如 `/proc/cpuinfo`、`/proc/<pid>/maps`、`/proc/loadavg` 等。

## 8.10 上下文切换

操作系统使用**上下文切换**（context switch）实现多任务。内核会保存当前进程的上下文，并恢复另一个进程的上下文，然后把控制传递给新进程。

**上下文**（context）通常包括：

- 通用寄存器和浮点寄存器、程序计数器
- 用户栈、状态寄存器，以及内核栈
- 页表、进程表、文件表等内核数据结构。

系统调用和中断都可能触发上下文切换。例如，`read` 调用如果需要等待磁盘数据，内核可以切换去运行别的进程；定时器中断也可以让内核抢占当前进程，把 CPU 分给新的进程。

## 8.11 系统调用错误处理

Unix 系统级函数出错时，通常返回 `-1` 并设置全局变量 `errno`。程序员应始终检查错误：

```c
void unix_error(char *msg)
{
    fprintf(stderr, "%s: %s\n", msg, strerror(errno));
    //strerror(errno) 将 errno 转换为可读的错误信息
    exit(0);
}
```

## 8.12 进程控制

Unix 提供了一组用于操作进程的重要系统调用。

### 8.12.1 获取进程 ID

每个进程都有一个唯一的进程 ID（PID）：

```c
#include <sys/types.h>
#include <unistd.h>
typedef int pid_t;

pid_t getpid(void);
pid_t getppid(void);

// 返回：调用者或其父进程的 PID。
```

### 8.12.2 创建和终止进程

从程序员角度看，进程通常处于三种状态之一：

- **运行**：进程在 CPU 上执行或等待被调度
- **停止**：进程被挂起，直到收到 `SIGCONT`后恢复运行
- **终止**：进程永远地停止。进程可通过三种方式终止：
  - 收到默认行为为终止的信号
  - 从主程序返回
  - 调用 `exit`。

```c
#include <stdlib.h>

void exit(int status);

// 该函数不返回。
```

`fork` 是最重要的创建进程接口：

```c
#include <sys/types.h>
#include <unistd.h>

pid_t fork(void);
```

`fork` **调用一次，返回两次**：

- 在父进程中返回子进程 PID
- 在子进程中返回 `0`

子进程获得父进程用户态地址空间的副本，也继承打开的文件描述符。父子进程拥有独立的私有地址空间，但共享打开文件，因此它们都可以向同一个 `stdout` 输出。

```c
int main()
{
    pid_t pid;
    int x = 1;

    pid = Fork();
    if (pid == 0) {  /* Child */
        printf("child : x=%d\n", ++x);   /* 子进程：x = 2 */
        exit(0);
    }

    printf("parent: x=%d\n", --x);       /* 父进程：x = 0 */
    exit(0);
}
```

父进程打印 `x=0`，子进程打印 `x=2`，这两个值是确定的；但**两行的输出顺序是不确定的**——调度器可能先运行父进程，也可能先运行子进程，每次执行的结果可能不同。

再看一个例子：

```c
int main(){
    Fork();
    Fork();
    printf("hello\n");
    exit(0);
}
```

它会打印 4 行 `hello`，因为第一次 `Fork` 产生的子进程也会执行第二次 `Fork`，共产生 $2^2 = 4$ 个进程，每个进程各打印一行。

> [!tip]
> `Fork` 生成的子线程会**继承父线程的状态**并从父线程的下一条指令开始**并发**执行，且生成该子线程的`Fork` 在父线程中返回子线程的 PID，在子线程中返回 `0`

### 8.12.3 回收子进程

当子进程终止后，内核不会立即删除它，而是保留其状态，直到父进程**回收**（reap）它。尚未被回收的终止进程称为**僵死进程**（zombie）。如果父进程先终止，`init` 进程（PID 为 1）会接管并回收这些孤儿进程。

`waitpid` 可以等待子进程终止或停止：

```c
#include <sys/types.h>
#include <sys/wait.h>

pid_t waitpid(pid_t pid, int *statusp, int options);
```

默认情况（`options = 0`）下，`waitpid` 会阻塞调用进程，直到等待集合（wait set）中的某个子进程终止，并返回该子进程的 PID。

- `pid > 0`：等待指定 PID 的子进程
- `pid = -1`：等待父进程的所有子进程

常见`options`（掩码）：

- `WNOHANG`：没有子进程终止时立即返回 0
- `WUNTRACED`：也报告被停止的子进程
- `WCONTINUED`：也报告收到 `SIGCONT` 后重新运行的子进程

`wait(&status)` 函数等价于 `waitpid(-1, &status, 0)`。

常用状态宏：`WIFEXITED`、`WEXITSTATUS`、`WIFSIGNALED`、`WTERMSIG`、`WIFSTOPPED`、`WSTOPSIG`、`WIFCONTINUED`。

如果没有子进程，`waitpid` 返回 `-1` 并设置 `errno = ECHILD`；如果被信号打断，则设置 `errno = EINTR`。

### 8.12.4 让进程休眠与装载程序

```c
#include <unistd.h>
unsigned int sleep(unsigned int secs);
// 返回：还要休眠的秒数。
int pause(void);
// 总是返回 -1。
```

- `sleep` 让进程休眠指定秒数，其可能被一个信号中断而过早地返回
- `pause` 让进程一直睡眠直到收到信号。

`execve` 在当前进程上下文中加载并运行一个新程序：

```c
#include <unistd.h>

int execve(const char *filename, const char *argv[], const char *envp[]);
```

`execve` 成功时不返回，失败时返回 `-1`。`argv` 是参数列表，`envp` 是环境变量列表。

例如命令`ls -lt /tmp`

- `*argv[0] = "ls", *argv[1] = "-lt", *argv[2] = "/tmp", *argv[3] = NULL`
- `envp` 为指向环境变量的指针数组，其中环境变量以`NAME=VALUE`的形式存储，包含了 PATH、HOME、USER 等信息。

# 第四部分 信号

## 8.13 信号概述

**信号**是通知进程系统中发生了某种事件的一条小消息，是一种更高层的软件异常控制流。

| 序号 | 名称    | 默认行为       | 相应事件                |
| :--: | ------- | -------------- | ----------------------- |
|  1   | SIGHUP  | 终止           | 终端挂断                |
|  2   | SIGINT  | 终止           | 键盘中断                |
|  3   | SIGQUIT | 终止并转储内存 | 键盘退出                |
|  4   | SIGILL  | 终止并转储内存 | 非法指令                |
|  5   | SIGTRAP | 终止并转储内存 | 跟踪陷阱                |
|  6   | SIGABRT | 终止并转储内存 | 来自 abort 的终止信号   |
|  7   | SIGBUS  | 终止           | 总线错误                |
|  8   | SIGFPE  | 终止并转储内存 | 浮点异常                |
|  9   | SIGKILL | 终止           | 杀死程序                |
|  11  | SIGSEGV | 终止并转储内存 | 无效内存引用            |
|  14  | SIGALRM | 终止           | 来自 alarm 的定时器信号 |
|  18  | SIGCONT | 忽略           | 继续已停止的进程        |

`SIGKILL` 和 `SIGSTOP` 不能被捕获、阻塞或忽略。

> [!note] 转储内存（dumping core）
> 将进程的内存映像写入磁盘文件，通常用于调试。Linux 系统中，转储文件通常命名为 `core`，但可以通过 `ulimit -c` 命令修改。

## 8.14 信号术语

信号的传送包括两个步骤：

**发送信号**：内核通过更新目的进程上下文中的状态递送信号。发送可能由系统事件触发，也可能由进程显式调用 `kill` 触发。

**接收信号**：目的进程被内核迫使对信号作出反应时，就接收了信号。进程可以忽略信号、终止，或通过信号处理程序（signal handler）捕获它。

一个发出而尚未被接收的信号称为**待处理信号**（pending signal）。同一类型的信号在任何时刻至多只保留一个待处理实例，后续同类型信号会被合并或丢弃。进程也可以阻塞某些类型的信号，直到解除阻塞后再接收。

## 8.15 信号的发送

### 8.15.1 进程组

每个进程只属于一个进程组。`getpgrp` 返回当前进程组 ID，`setpgid` 可以修改进程组。

### 8.15.2 用 /bin/kill 发送信号

```bash
/bin/kill -9 15213    # 向单个进程发送 SIGKILL
/bin/kill -9 -15213   # 向整个进程组发送 SIGKILL
```

### 8.15.3 从键盘发送信号

Unix shell 使用**作业**（job）表示为一条命令行创建的进程集合。前台作业至多一个，后台作业可以有多个。

- `Ctrl+C` 发送 `SIGINT` 给前台进程组
- `Ctrl+Z` 发送 `SIGTSTP` 给前台进程组

### 8.15.4 用 kill 函数发送信号

```c
#include <sys/types.h>
#include <signal.h>

int kill(pid_t pid, int sig);
```

`pid > 0` 时向指定进程发送信号；`pid = 0` 时向当前进程组发送信号；`pid < 0` 时向绝对值对应的进程组发送信号。

### 8.15.5 用 alarm 函数发送信号

```c
#include <unistd.h>
unsigned int alarm(unsigned int secs);
```

`alarm` 安排内核在若干秒后向调用进程发送 `SIGALRM`。若已有待处理闹钟，新的 `alarm` 会取消旧的安排并返回剩余秒数。

## 8.16 信号的接收与处理

当内核把进程从内核模式切回用户模式时，会检查该进程所有"未阻塞的待处理信号"。如果集合非空，内核会选择其中一个信号并强制进程接收。

进程可以用 `signal` 函数修改信号的默认行为：

```c
#include <signal.h>
typedef void (*sighandler_t)(int);

sighandler_t signal(int signum, sighandler_t handler);
```

- `SIG_IGN`：忽略信号
- `SIG_DFL`：恢复默认行为
- 其他函数地址：安装信号处理程序

捕获信号后，处理程序以信号编号作为参数被调用；处理程序返回后，控制通常回到被中断的那条指令。

> [!important]
> **信号处理程序之间也可能相互中断**，因此处理程序必须谨慎设计。

## 8.17 编写安全的信号处理程序

信号处理程序的设计有严格的约束，违反这些规则会引入难以复现的并发 bug。以下是核心准则：

**只调用异步信号安全的函数**（async-signal-safe function）。异步信号安全意味着函数要么是可重入的（只使用局部变量），要么不能被信号中断。常见的安全函数包括 `write`、`_exit`、`kill`、`getpid`、`sleep`；常见的不安全函数包括 `printf`、`sprintf`、`malloc`、`exit`——因为它们内部使用了全局数据结构和锁，被信号中断可能导致死锁或数据损坏。

如果需要输出，应使用基于 `write` 封装的异步安全的 I/O 函数（如 CSAPP 提供的 `sio_puts`）。

**保存和恢复 `errno`**。处理程序调用的系统函数可能修改 `errno`，若不在进入处理程序时保存、返回前恢复，就会悄悄破坏主程序的错误检测逻辑：

```c
void handler(int sig)
{
    int saved_errno = errno;
    /* ... 处理逻辑 ... */
    errno = saved_errno;
}
```

**用 `sigprocmask` 阻塞信号来保护共享数据结构**。主程序与处理程序共享的全局数据，在主程序访问期间应阻塞相关信号，避免处理程序在不一致的中间状态下介入。

**用 `volatile` 声明与处理程序共享的全局变量**。若不加 `volatile`，编译器可能把变量缓存在寄存器中，主程序看不到处理程序对它的修改：

```c
volatile int flag = 0;   /* 处理程序修改，主程序读取 */
```

**用 `sig_atomic_t` 声明原子读写的标志变量**。`sig_atomic_t` 类型的读写在大多数系统上是原子的，不会被中断到一半，适合用作处理程序和主程序之间通信的简单标志：

```c
volatile sig_atomic_t flag = 0;
```

## 8.18 阻塞和解除阻塞信号

Linux 提供隐式和显式的阻塞机制：

- **隐式阻塞**：当前正在执行某个信号的处理程序时，内核默认阻塞同类型信号的进一步递送
- **显式阻塞**：应用程序可以使用 `sigprocmask` 和辅助函数控制阻塞集合

```c
#include <signal.h>

int sigprocmask(int how, const sigset_t *set, sigset_t *oldset);
int sigemptyset(sigset_t *set);
int sigfillset(sigset_t *set);
int sigaddset(sigset_t *set, int signum);
int sigdelset(sigset_t *set, int signum);
int sigismember(const sigset_t *set, int signum);
```

`how` 的含义：

- `SIG_BLOCK`：把 `set` 中的信号加入阻塞集合
- `SIG_UNBLOCK`：从阻塞集合中移除 `set` 中的信号
- `SIG_SETMASK`：直接把阻塞集合设为 `set`

## 8.19 信号处理中的竞争条件与 sigsuspend

主程序与信号处理程序之间的竞争条件是信号编程中最微妙的问题。一个典型场景是 shell 的作业管理：父进程 `fork` 子进程后，需要在作业列表中 `addjob`；但如果子进程先终止，`SIGCHLD` 处理程序先调用 `deletejob`，此时 `addjob` 还没执行，就会导致逻辑错误。

正确的做法是在 `fork` 之前阻塞 `SIGCHLD`，`addjob` 完成后再解除阻塞：

```c
sigset_t mask_all, mask_one, prev_one;

Sigfillset(&mask_all);
Sigemptyset(&mask_one);
Sigaddset(&mask_one, SIGCHLD);

/* 阻塞 SIGCHLD，防止子进程在 addjob 前被处理 */
Sigprocmask(SIG_BLOCK, &mask_one, &prev_one);
if ((pid = Fork()) == 0) {
    Sigprocmask(SIG_SETMASK, &prev_one, NULL);  /* 子进程恢复信号 */
    Execve(...);
}

Sigprocmask(SIG_BLOCK, &mask_all, NULL);
addjob(pid);
Sigprocmask(SIG_SETMASK, &prev_one, NULL);      /* 解除阻塞 */
```

另一个常见问题是**等待信号时的竞争**。不能简单用 `pause` 等待处理程序设置标志：

```c
/* 错误示例：解除阻塞与 pause 之间存在窗口期 */
sigprocmask(SIG_UNBLOCK, &mask, NULL);
pause();   /* 若信号在这行之前已到达，pause 将永久挂起 */
```

正确的解法是使用 `sigsuspend`，它原子地**解除信号阻塞并暂停进程**，等到信号到来后才返回，消除了竞争窗口：

```c
#include <signal.h>
int sigsuspend(const sigset_t *mask);
```

`sigsuspend(mask)` 相当于原子地执行：

```c
sigprocmask(SIG_SETMASK, &mask, &prev);
pause();
sigprocmask(SIG_SETMASK, &prev, NULL);
```

但由于三步合为一个不可分割的操作，信号无法在中间到达，竞争条件被彻底消除。

## 8.20 非本地跳转

C 语言提供一种用户级异常控制流形式，称为**非本地跳转**（nonlocal jump），通过 `setjmp` 和 `longjmp` 提供：

```c
#include <setjmp.h>
int setjmp(jmp_buf env);
int sigsetjmp(sigjmp_buf env, int savesigs);

void longjmp(jmp_buf env, int retval);
void siglongjmp(sigjmp_buf env, int retval);
```

`setjmp` 在缓冲区 `env` 中保存当前调用环境（PC、栈指针和通用寄存器），以供之后的 `longjmp` 使用。`longjmp` 从 `env` 恢复调用环境，并使最近一次对应的 `setjmp` 返回一个非零值。

`setjmp` 调用一次却可能返回多次，`longjmp` 调用一次却从不返回。

非本地跳转常用于从深层嵌套调用中直接返回到统一的错误处理位置。但它会跳过中间函数的清理代码，如果中间过程分配了资源而没有显式处理，就可能造成泄漏。

`sigsetjmp` / `siglongjmp` 比普通 `setjmp` / `longjmp` 更适合与信号配合使用，因为它们可以选择性保存和恢复信号掩码。

示例：按下 `Ctrl+C` 时重启程序：

```c
#include "csapp.h"
// 为了简化代码示例，我们包含了一个称为 csapp.h 的头文件
// 它包括了本文中使用的所有函数的头文件。


sigjmp_buf buf;

void handler(int sig)
{
    siglongjmp(buf, 1);
}

int main()
{
    if (!sigsetjmp(buf, 1)) {
        Signal(SIGINT, handler);
        Sio_puts("starting\n");
    }
    else
        Sio_puts("restarting\n");

    while (1) {
        Sleep(1);
        Sio_puts("processing...\n");
    }
    exit(0);
}
```

注意这里使用了 `Sio_puts` 而非 `printf`——因为处理程序中调用的是 `siglongjmp`，不会直接输出，但主循环和跳转后的输出都应使用异步信号安全的函数以保持一致性。

> [!note] C++ 和 Java 中的软件异常
> C++ 和 Java 提供的异常机制是较高层次的，是 C 语言的 `setjmp` 和 `longjmp` 函数的更加结构化的版本。你可以把 `try` 语句中的 `catch` 子句看做类似于 `setjmp` 函数。相似地，`throw` 语句就类似于 `longjmp` 函数。
