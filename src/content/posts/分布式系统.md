# 第一部分 通信：分布式系统的基石

## 6.1 分布式系统的核心挑战

> [!question] 关键问题：如何在部件失效时构建可用的系统
> 机器、磁盘、网络、软件都会时不时失效，我们永远造不出"完美"的零件。如何用不可靠的零件构造出可靠的系统？

这与 RAID 的问题同源，但更复杂：RAID 假设 fail-stop（要么好、要么彻底坏，且易检测，见 5.3.1），而分布式系统中**故障与延迟不可区分**。

故障同时也是机会：单台机器失效不必导致整个系统失效。这正是分布式系统的价值所在。

| 挑战             | 内容                                           |
| ---------------- | ---------------------------------------------- |
| 故障（本篇重点） | 部件常态失效，系统仍需对外表现为可用           |
| 性能             | 网络成为瓶颈：减少消息条数、降低延迟、提高带宽 |
| 安全             | 认证远端身份；防止第三方窃听与篡改             |

### 6.1.1 通信本质上是不可靠的

> [!tip] 把通信视为天然不可靠的活动
> 无论广域互联网还是 Infiniband 这类高速局域网，丢包、损坏都是常态。
>
> | 丢包原因       | 说明                                                 |
> | -------------- | ---------------------------------------------------- |
> | 比特翻转       | 传输中电气干扰导致数据出错                           |
> | 部件损坏       | 链路、路由器、远端主机故障（网线真的会被挖断）       |
> | **缓冲区不足** | 交换机/路由器/端主机内存装不下同时到达的包，只能丢弃 |

第三条最根本：**即使所有链路和部件都完好无损，只要并发到达的包超过缓冲容量，就必然丢包。** 丢包因此不是可以彻底消除的缺陷，而是网络的固有属性。问题只在于：上层如何应对。

## 6.2 不可靠通信层：UDP

一种合理的应对是"不应对"：有些应用自己知道怎么处理丢包，就让它们直接使用不可靠的消息层——这是**端到端论证**的一个体现（见 6.5 末尾）。

UDP/IP 就是这样的层：进程用 sockets API 创建通信端点，其他进程向它发送**数据报**（datagram）——一条**变长**消息，长度上限由底层 IP 决定，IPv4 下为 $65535-20-8=65507$ 字节。

```c
// client
int sd = UDP_Open(20000);
struct sockaddr_in addrSnd, addrRcv;
UDP_FillSockAddr(&addrSnd, "cs.wisc.edu", 10000);
char message[BUFFER_SIZE];
sprintf(message, "hello world");
if (UDP_Write(sd, &addrSnd, message, BUFFER_SIZE) > 0)
    UDP_Read(sd, &addrRcv, message, BUFFER_SIZE);

// server
int sd = UDP_Open(10000);
while (1) {
    struct sockaddr_in addr;
    char message[BUFFER_SIZE];
    if (UDP_Read(sd, &addr, message, BUFFER_SIZE) > 0) {
        char reply[BUFFER_SIZE];
        sprintf(reply, "goodbye world");
        UDP_Write(sd, &addr, reply, BUFFER_SIZE);
    }
}
```

封装库只是 `socket` / `bind` / `sendto` / `recvfrom` 的薄包装。有这点代码，就可以开始写分布式系统了。

| UDP 提供               | UDP 不提供                       |
| ---------------------- | -------------------------------- |
| 校验和（检测部分损坏） | 丢包通知：发送方永远不知道包丢了 |
| 端口复用、尽力投递     | 顺序、去重、重传                 |

> [!tip] 回顾
> sockets 接口（`socket`、`bind`、`sendto` / `recvfrom` 的语义）：[[csapp-11#114-套接字接口|CSAPP 11.4]]；UDP 与 TCP 的区别：[[cn-top-down-3|计算机网络 传输层]]。

> [!tip] 校验和：有效性 vs 性能
> 发送前算 $C(D)$，随消息一起发出；接收方重算并比对。校验和越强，越难漏检，但计算越贵——与 5.10.4 完全相同的权衡（加法、CRC、Fletcher）。

## 6.3 可靠通信层：确认、超时重传与序列号

> [!question] 关键问题：如何在不可靠网络上构建可靠通信
> 发送方如何知道接收方真的收到了消息？没收到时又该怎么办？

### 6.3.1 确认与超时重传

| 机制                        | 作用                                           |
| --------------------------- | ---------------------------------------------- |
| 确认（acknowledgment，ack） | 接收方回一条短消息，告知已收到                 |
| 超时（timeout）             | 发送后启动定时器，超时未收到 ack 即判定丢失    |
| 重传（retry）               | 重发同一条消息，因此**发送方必须保留消息副本** |

三者合称 timeout/retry。但它还不够。

> [!tip] 回顾
> 可靠数据传输的完整机制（停等、滑动窗口、TCP 的确认与超时）见 [[cn-top-down-3|计算机网络 传输层]]；本节只取其中与分布式系统直接相关的部分。

### 6.3.2 重复消息与"恰好一次"

若丢的是 **ack** 而不是原消息，发送方看到的现象完全一样（超时），于是重传——接收方却收到了两份相同消息。下载文件时多出重复数据显然是错的。可靠消息层通常要求 **恰好一次**（exactly-once）语义。

去重需要发送方唯一标识消息、接收方记住是否见过：

| 方案                                         | 代价                                |
| -------------------------------------------- | ----------------------------------- |
| 每条消息一个唯一 ID，接收方记录所有见过的 ID | 需要**无界内存**，不可行            |
| **序列计数器**（sequence counter）           | 每个通信对端一个计数器，$O(1)$ 内存 |

序列计数器：双方约定初值（如 1），发送方把当前值 $N$ 随消息发出并自增；该计数值即消息的**序列号**（sequence number）。接收方为每个对端维护一个期望值。

```
接收方收到消息 N（停等式：同一时刻只有一条在途消息）：
    if N == expected:        // 首次收到
        ack(N); 交付应用; expected++
    else:                    // N < expected，是重复
        ack(N);              // 只确认，绝不交付应用
```

关键在于**重复消息也要回 ack**（否则发送方会永远重传），但不向上交付。

> [!important] 去重不变式
> 停等式下，设接收方 `expected = k`。则序号小于 $k$ 的消息均已被交付**恰好一次**。
>
> 证明：初始 $k=1$，不变式空真。`expected` 只在首次收到序号等于 `expected` 的消息时加 1，且交付与加 1 同时发生，故每个序号至多交付一次。重复消息序号小于 `expected`，只触发 ack，不交付。若发送方持续重传且网络最终能投递，则每个序号至少被交付一次。$\square$

> [!note] 这里隐含了停等假设
> 发送方收到 ack 前不发下一条，因此不会出现 $N > \text{expected}$ 的跳号或乱序。一旦允许多条请求在途（滑动窗口），去重就要按窗口逐项维护状态——这正是 TCP 复杂度的来源之一。

最常用的可靠层是 TCP/IP，它在此之上还处理拥塞控制、多个未完成请求等大量细节。

> [!tip] 超时值的设定
>
> | 情形               | 后果                                |
> | ------------------ | ----------------------------------- |
> | 超时过小           | 无谓重传，浪费发送方 CPU 与网络资源 |
> | 超时过大           | 迟迟不重传，感知性能下降            |
> | 单客户端的"正确值" | 刚好够检测丢包，不多等              |
>
> 多客户端场景下，丢包可能是**服务器过载**的信号，此时应自适应退避：第一次超时后把超时值加倍，即**指数退避**（exponential back-off）$T_k = T_0\cdot 2^k$。它源自 Aloha 网络、被早期以太网采用，目的是避免重传风暴加剧过载。

## 6.4 通信抽象：DSM 为什么失败

有了消息层，下一个问题是：给程序员什么抽象？

一条路线是把 OS 抽象扩展到分布式环境，代表是**分布式共享内存**（Distributed Shared Memory，DSM）：不同机器上的进程共享一个巨大的虚拟地址空间，看起来像多线程程序，只是线程跑在不同机器上。

实现依赖虚拟内存：访问本地页则快速完成；页在远端则触发缺页，缺页处理程序发消息把页取回、装入页表、继续执行。

| 致命问题 | 说明                                                                                                                  |
| -------- | --------------------------------------------------------------------------------------------------------------------- |
| 故障     | 机器崩溃后，它上面的页消失。若数据结构横跨整个地址空间，链表 `next` 可能指向已不存在的地址空间——无法收拾              |
| 性能     | 程序员默认"访存很便宜"，而 DSM 中部分访问是昂贵的远程缺页。为了性能必须精心组织计算以几乎不通信，这就抵消了抽象的意义 |

结论：DSM 研究很多、实际影响很小，今天没人用它构建可靠分布式系统。**OS 层抽象不合适，编程语言层抽象更合适。**

## 6.5 RPC：把远程调用伪装成本地调用

> [!question] 关键问题：如何让远程执行像本地函数调用一样简单
> 最主流的抽象是**远程过程调用**（Remote Procedure Call，RPC）：客户端发起调用、稍后拿到结果；服务器只需导出若干例程，其余细节由 RPC 系统承担。

RPC 系统由两部分组成：**桩生成器**（stub generator，又称协议编译器）与**运行时库**（run-time library）。

### 6.5.1 桩生成器

输入是服务器希望导出的接口：

```
interface {
    int func1(int arg1);
    int func2(int arg1, int arg2);
};
```

自动生成客户端桩与服务器桩，消除手写打包代码的错误，还可能被优化。客户端调用 `func1(x)` 看起来就是普通函数调用，内部却做了：

| 客户端桩                                                | 服务器桩                                                   |
| ------------------------------------------------------- | ---------------------------------------------------------- |
| 1. 创建消息缓冲区（连续字节数组）                       | 1. **解包**：取出函数标识与参数（unmarshaling / 反序列化） |
| 2. **打包**：函数标识 + 全部参数（marshaling / 序列化） | 2. 调用真正的函数                                          |
| 3. 发送消息（细节交给运行时库）                         | 3. 把返回值打包进回复缓冲区                                |
| 4. 等待回复（同步调用）                                 | 4. 发送回复                                                |
| 5. 解包返回值与输出参数                                 |                                                            |
| 6. 返回调用者                                           |                                                            |

### 6.5.2 复杂参数与服务器并发

- **复杂参数**：`write(fd, buf, size)` 里的指针在远端毫无意义。RPC 必须知道该序列化哪些字节：提供 well-known 类型（如"带长度的缓冲区"），或让程序员标注数据结构。
- **服务器并发**：单循环逐个处理请求时，一次阻塞 I/O 就浪费整台服务器。常见做法是**线程池**，主线程收请求并分派，工作线程执行并回复（同步问题见并发篇）。

### 6.5.3 运行时库

| 问题          | 处理方式                                                                                              |
| ------------- | ----------------------------------------------------------------------------------------------------- |
| 命名/定位服务 | 最简单方案沿用主机名（或 IP）+ 端口号；更完整的讨论见 DNS 与域名解析资料                              |
| 传输协议选择  | 见下表                                                                                                |
| 长时间调用    | 先回一个显式 ack 表示"已收到"；客户端随后周期性询问"还在做吗"，只要回答是就继续等，避免误判失败而重传 |
| 超大参数      | 分片（fragmentation）与重组（reassembly）；底层不提供就由 RPC 运行时自己做                            |
| 字节序        | 消息格式规定统一字节序（Sun RPC 的 XDR）；本机字节序不同则逐字段转换，有小额性能开销                  |
| 异步调用      | 发出请求立即返回，客户端可继续计算或发起更多 RPC；之后调用 RPC 层等待未完成的调用并取回结果           |

传输协议的选择反直觉：

| 方案                                            | 优点       | 代价                                                   |
| ----------------------------------------------- | ---------- | ------------------------------------------------------ |
| 建在 TCP 上                                     | 可靠性现成 | 请求/响应本已自带回复，TCP 的 ack 变成**两条额外消息** |
| 建在 UDP 上 + 自己实现 ack/timeout/retry/序列号 | 高效       | 可靠性责任上移到 RPC 层                                |

因此许多 RPC 包建在 UDP 之上，自己用 ack + timeout/retry + 序列号补齐可靠性。文献中常见的表述是：无故障时恰好一次，有故障时至多一次（该表述的出处需验证）。这句话要按下面的口径读，否则会与 NFS 的幂等性冲突。

> [!warning] 三种调用语义
>
> | 语义          | 含义                               | 靠什么实现                             |
> | ------------- | ---------------------------------- | -------------------------------------- |
> | at-least-once | 至少执行一次，可能重复             | 超时重传（发送方不放弃）               |
> | at-most-once  | 至多执行一次，失败则报错，绝不重复 | 序列号 + 接收方去重记录                |
> | exactly-once  | 恰好一次                           | 两者叠加，且**去重记录必须能跨越崩溃** |
>
> 关键在最后一行：去重记录一旦随服务器崩溃丢失，重传就会被再执行一次，语义退回 at-least-once。"持久发送方保证 at-least-once，去重保证 at-most-once"的拆分，来自 Saltzer & Kaashoek 的讲法（补充，需验证）。
>
> **NFS 的情形更彻底**：无状态服务器根本不保存任何去重记录，客户端重试 = 服务器**再执行一遍**（6.8 Case 3）。所以幂等性不是 RPC 语义的补充，而是它的**前提**——正因为下层挡不住重复执行，上层才必须让重复执行无害。

> [!note] 端到端论证（End-to-End Argument）
> 某些功能只能在系统的最高层（"端"上的应用）真正实现。以可靠文件传输为例：即使通信协议保证每个字节按序可靠到达，仍可能在**发送前内存中就被损坏**，或**接收方写盘时出错**——网络可靠不等于文件传输可靠。真正的保证只能端到端做：传完后读回接收方磁盘上的文件，算校验和与源文件比对。
>
> 推论并非"底层不该提供功能"：底层的额外机制常常能显著提升性能（如 TCP 的重传让 RPC 少走弯路），只是**不能把正确性的责任全押在底层**。这与 5.10 的结论一致：校验和只有配合冗余与端到端检查才有意义。

# 第二部分 NFS：无状态与幂等

## 6.6 分布式文件系统的基本结构

> [!question] 关键问题：如何构建分布式文件系统
> 关键设计点是什么？哪里容易出错？能从现有系统学到什么？

基本形态是多客户端 + 单（或少量）服务器：服务器持有磁盘，客户端通过协议消息访问目录与文件。

| 好处     | 说明                                           |
| -------- | ---------------------------------------------- |
| 数据共享 | 在 Client 0 上改完，换到 Client 2 看到同一视图 |
| 集中管理 | 备份只需在少数服务器上做                       |
| 安全     | 服务器集中放在上锁的机房                       |

两个软件部件决定系统行为：

| 部件           | 职责                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------- |
| 客户端文件系统 | 接收应用的 `open` / `read` / `write` / `close` / `mkdir`，翻译成协议消息；维护客户端状态与缓存 |
| 文件服务器     | 响应协议消息，读写磁盘或自身缓存                                                               |

目标是**透明访问**：应用用的还是本地那套 POSIX API，除了性能之外察觉不到差别。

> [!note] 服务器为什么会崩溃
> 断电；软件 bug；内存泄漏最终耗尽内存；以及网络分区——客户端与服务器都活着却无法通信，**看起来**就像对方崩了。

## 6.7 NFSv2：无状态协议

Sun 的 NFS 选择了**开放协议**而非封闭实现：只规定消息格式，各家可做自己的服务器并互相兼容。开放市场是 NFS 普及的重要原因。

NFSv2 的首要设计目标：**简单、快速的服务器崩溃恢复**。多客户端单服务器下，服务器停一分钟，所有人都停一分钟。

### 6.7.1 状态为什么是负担

> [!question] 关键问题：如何定义无状态的文件协议
> `open()` 这类调用天然有状态，服务器不能跟踪打开文件表；但应用又要用标准 POSIX API。协议该如何设计？

先看有状态的反例：客户端发"打开 foo 给我个描述符"，服务器本地打开并回传 fd，后续 `read(fd, ...)` 让服务器"读这个 fd 指向的文件"。fd 是客户端与服务器之间的**共享状态**（distributed state）。

| 崩溃场景       | 有状态协议的麻烦                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------- |
| 服务器崩溃重启 | fd 是内存中的易失信息，重启后服务器不知道 fd 指谁；需要专门的**恢复协议**，客户端得保存足够信息重建服务器状态 |
| 客户端崩溃     | 服务器上等不到 `close()`，必须自己察觉客户端已死才能释放资源                                                  |

**无状态**（stateless）：服务器不跟踪任何客户端行为（谁缓存了哪些块、谁打开了哪些文件、文件偏移到哪），**每个请求自带完成所需的全部信息**。于是恢复极简：服务器重启后直接开始服务，客户端最坏情况下需要重试请求（必要时反复重试，直到成功）。

### 6.7.2 文件句柄

**文件句柄**（file handle）唯一标识操作对象，是协议的核心：

| 组成                        | 作用                                                   |
| --------------------------- | ------------------------------------------------------ |
| 卷标识（volume identifier） | 指明哪个文件系统（服务器可导出多个）                   |
| inode 号                    | 指明该分区内的哪个文件                                 |
| 生成号（generation number） | inode 号被复用时自增，防止持旧句柄的客户端误访问新文件 |

生成号解决的是 inode 回收后编号被复用的问题（inode 与 i-number 见 5.5.2）；AFS 的 uniquifier 是同一思路的类似设计（6.12）。

### 6.7.3 协议要点

| 请求           | 参数                          | 返回                       |
| -------------- | ----------------------------- | -------------------------- |
| GETATTR        | 句柄                          | 属性                       |
| SETATTR        | 句柄、属性                    | 属性                       |
| LOOKUP         | 目录句柄、名字                | 句柄、属性                 |
| READ           | 句柄、**offset**、count       | 数据、属性                 |
| WRITE          | 句柄、**offset**、count、数据 | 属性                       |
| CREATE / MKDIR | 目录句柄、名字、属性          | 句柄、属性                 |
| REMOVE / RMDIR | 目录句柄、名字                | —                          |
| READDIR        | 目录句柄、字节数、cookie      | 目录项、cookie（用于续读） |

要点：

- **LOOKUP 用来获得句柄**，之后才能读写数据。根目录句柄由 **mount 协议**在建立连接时获得。
- 长路径逐级 LOOKUP：`/home/remzi/foo.txt` 需要三次（`home`、`remzi`、`foo.txt`）。
- **属性**（attributes）就是元数据：修改时间、大小、属主、权限等，即 `stat()` 的内容。
- READ/WRITE 显式携带 **offset**——这是幂等性的关键（6.8）。

### 6.7.4 状态都在客户端

客户端文件系统保存全部相关状态：`fd → 文件句柄` 的映射、当前文件偏移量。应用的 `read()` 不带偏移，客户端补上偏移形成完整协议请求，成功后推进偏移。

于是每个请求都自包含，服务器无需任何客户端状态即可作答——这正是快速恢复的前提。

## 6.8 幂等性与统一的失败处理

> [!tip] 幂等性是强大的工具
> 操作可重复执行，失败处理就简单：重试即可。不幂等的操作则麻烦得多。

**幂等**（idempotent）：执行多次的效果等于执行一次。"向内存某位置存值"幂等；"计数器自增"不幂等。只读操作天然幂等，更新操作要逐个分析。

> [!important] 形式化定义
> 设操作 $f$ 将系统状态 $s$ 映射为 $f(s)$。$f$ **幂等**当且仅当 $\forall s,\ f(f(s)) = f(s)$。
>
> **WRITE 幂等**：`WRITE(h, off, data)` 的效果是把文件 $h$ 的字节区间 $[\text{off},\ \text{off}+|\text{data}|)$ 置为 `data`，其余字节不变。执行一次后该区间已等于 `data`，再执行一次状态不变，故 $f(f(s)) = f(s)$。$\square$
>
> **反例**：自增满足 $f(f(s)) = s+2 \ne s+1 = f(s)$，不幂等。若 WRITE 只带 count 而不带 offset（"追加"语义），也会变得不幂等——这正是协议显式携带 offset 的原因。

| NFS 操作                | 幂等？ | 原因                                                    |
| ----------------------- | ------ | ------------------------------------------------------- |
| LOOKUP / READ / GETATTR | 是     | 只读                                                    |
| WRITE                   | 是     | 请求自带数据、count 与**确切 offset**，重复写入结果相同 |
| MKDIR                   | 否     | 首次成功但回复丢失，重试返回"已存在"（EEXIST）          |
| REMOVE / RMDIR          | 否     | 首次成功但回复丢失，重试返回"不存在"（ENOENT）          |

后两者的最终状态其实都不再改变，"不幂等"体现在**返回值不同**：客户端无法从错误码判断操作是没做成，还是早已做成。这正是统一重试机制覆盖不到的角落。

客户端因此可以用**一套统一机制**处理所有超时：发请求 → 起定时器 → 收到回复则取消定时器；超时则重发。

| 失败情形                         | 重试后的结果                         |
| -------------------------------- | ------------------------------------ |
| Case 1：请求丢失                 | 服务器执行，正常                     |
| Case 2：服务器当时宕机、现已重启 | 服务器执行，正常                     |
| Case 3：服务器已执行、回复丢失   | 服务器**再做一遍同样的事**，结果不变 |

消息丢失与服务器崩溃被同一手段掩盖，这是 NFS 设计最漂亮的地方。

> [!tip] 完美是好的敌人（伏尔泰定律）
> mkdir 不幂等：第一次成功但回复丢了，重试会收到"已存在"的失败。可以重新设计 mkdir 语义使其幂等，但何必？覆盖绝大多数重要情形、让失败处理整体保持简洁，就是好工程。

## 6.9 客户端缓存与缓存一致性

> [!question] 关键问题：如何提升分布式文件系统的性能
> 所有读写都过网络太慢。答案与 5.5.6 相同：**客户端缓存**。

NFS 客户端在内存中缓存读到的数据与元数据；缓存同时充当**写缓冲**：应用的 `write()` 立即成功（只是写进缓存），稍后才发往服务器——把应用延迟与实际写性能解耦。

但多客户端各有缓存，就引出**缓存一致性问题**。设 C1 读了文件 $F[v1]$ 并缓存，C2 改写为 $F[v2]$，C3 尚未访问过 $F$：

| 子问题                              | 现象                                                     |
| ----------------------------------- | -------------------------------------------------------- |
| **更新可见性**（update visibility） | C2 的写还缓冲在自己内存里，C3 从服务器读到的仍是 $F[v1]$ |
| **缓存陈旧**（stale cache）         | C2 已刷回服务器，但 C1 缓存里还是 $F[v1]$                |

NFSv2 的两个工程化对策：

| 对策                            | 解决       | 做法                                                                                              |
| ------------------------------- | ---------- | ------------------------------------------------------------------------------------------------- |
| flush-on-close（close-to-open） | 更新可见性 | 文件被写过且 `close()` 时，把所有脏页刷回服务器；于是别的节点随后 `open()` 能看到新版本           |
| 使用前校验                      | 缓存陈旧   | 用缓存块前先发 GETATTR 取属性，比较服务器修改时间与本地取回时间；更新过则**作废缓存**，否则直接用 |

GETATTR 随即淹没服务器——最常见的情形是文件只被一个客户端反复访问，却每次都要问"有人改过吗"。设有 $N$ 个客户端，若每次访问都校验，服务器的校验负载与总访问率成正比。于是再加一层**属性缓存**（attribute cache）：属性也缓存，超时 $T_{ac}$（如 3 秒）后才重新校验。这样每个（客户端，文件）对的校验频率不超过 $1/T_{ac}$，$T_{ac}$ 内所有访问零网络交互。

对这套设计的评价：

- flush-on-close 让**短命临时文件**也被迫写到服务器，本可完全在内存中消化；
- 属性缓存让"我到底读到哪个版本"变得难以推理：有时最新，有时因为属性缓存没超时而拿到旧版本。

> [!warning] 实现细节反过来定义了语义
> NFS 的一致性语义不是先定义后实现，而是由缓存超时这类实现细节决定的——这是"偶尔出现怪异行为"的根源。AFS 在语义上做了不同的选择（见 6.13）。

## 6.10 服务器端写缓冲

服务器读缓存无害（只是加速）。**写缓冲则有一条铁律：WRITE 未落稳定存储之前，绝不能回复成功。**

原因在客户端的失败假设。客户端连写三块：

```c
write(fd, a_buffer, size);   // 第 1 块填 a
write(fd, b_buffer, size);   // 第 2 块填 b
write(fd, c_buffer, size);   // 第 3 块填 c
```

若服务器把第 1、3 块落盘，第 2 块只缓冲在内存就回复成功，随后崩溃：

```
aaaaaaaa...
yyyyyyyy...   <--- oops，旧内容还在
cccccccc...
```

客户端认为三次写全部成功，文件却新旧混杂。因为客户端**收到成功就不会重试**，服务器的提前承诺直接变成数据丢失。落盘后再回复，客户端才能察觉失败并重试到成功——这与 5.2.4 的写回/写穿、5.4.6 的 `fsync()` 是同一条纪律。

代价是写性能成为主要瓶颈。NetApp 等公司的解法：先写入**电池备份内存**（battery-backed NVRAM）即可快速回复，再用专为快速写盘设计的文件系统落盘（受 LFS 影响，见 5.8）。

### 6.10.1 VFS / vnode

> [!note] 创新催生创新
> NFS 要接入 OS，Sun 顺手引入 **VFS/vnode 接口**：VFS 层是文件系统级操作（挂载、卸载、统计、同步脏数据），vnode 层是文件级操作（open、close、read、write…）。实现新文件系统只需定义这些"方法"，框架负责把系统调用接进来、集中处理通用功能（如缓存）。Linux、BSD、macOS 乃至 Windows（Installable File System）都有类似层次——正是 5.1.6 中"用抽象隐藏差异"的同一手法。NFS 或许会淡出，它的地基留了下来。

# 第三部分 AFS：可扩展性与回调

## 6.11 AFSv1：整文件缓存

AFS 由 CMU 的 Satya 等人于 1980 年代开发，首要目标只有一个：**规模**（scale）——一台服务器能支撑多少客户端？

影响可扩展性的因素很多，最关键的是**协议设计**。NFS 要客户端周期性向服务器校验缓存，每次校验都消耗服务器 CPU 与带宽，客户端数量因此受限。AFS 还把"用户可见行为是否合理"当作一等目标。

AFS 各版本的共同基石：**整文件缓存**（whole-file caching）在客户端本地磁盘上。

| 阶段                 | AFSv1 行为                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `open()`             | 客户端代码（**Venus**）发 **Fetch**，携带**完整路径名**；服务器（**Vice**）遍历路径、回传整个文件；客户端写入本地磁盘缓存 |
| `read()` / `write()` | 完全本地，重定向到本地副本（本地文件系统还会把它缓存进客户端内存），零网络通信                                            |
| `close()`            | 若被修改过，用 **Store** 把整个文件与路径名回传服务器                                                                     |
| 再次访问             | 先发 **TestAuth** 问服务器文件是否变了；没变就用本地副本                                                                  |

与 NFS 的两处鲜明对比：缓存**整文件**而非块；缓存在**本地磁盘**而非仅内存。AFSv1 只缓存文件内容，**目录仍只在服务器上**。

| AFSv1 协议                | 作用                   |
| ------------------------- | ---------------------- |
| TestAuth                  | 校验缓存副本是否仍有效 |
| Fetch / Store             | 取回 / 存回整个文件    |
| GetFileStat / SetFileStat | 读 / 写 stat 信息      |
| ListDir                   | 列目录                 |

> [!tip] 先测量，再动手（Patterson 定律）
> AFS 团队花大量时间测量原型，用实验证据而非直觉定位问题。好处有两层：证明你在解决真问题；顺手建立了衡量新系统的基准。

测出的两个主要问题（服务器 CPU 是瓶颈，每服务器仅能服务约 **20** 个客户端）：

| 问题              | 原因                                                                        |
| ----------------- | --------------------------------------------------------------------------- |
| 路径遍历开销过高  | Fetch/Store 传完整路径，服务器每次都要从根逐级走目录，大量 CPU 耗在走路径上 |
| TestAuth 消息过多 | 与 NFS 的 GETATTR 泛滥同病：服务器大部分时间在回答"没变，可以用"            |

另两个次要问题及解法：服务器间负载不均 → 引入 **volume**（管理员可整体迁移）；服务器为每个客户端维持一个独立进程，客户端一多就产生大量上下文切换开销 → AFSv2 改用**线程**。

## 6.12 AFSv2：回调与 FID

> [!question] 关键问题：如何设计可扩展的文件协议
> 既要减少交互次数（少发 TestAuth），又要让每次交互本身便宜（少走路径）。

两项改动分别对应这两个目标：

| 机制                 | 内容                                                           | 效果                                                                            |
| -------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| **回调**（callback） | 服务器对客户端的**承诺**：你缓存的文件被修改时我通知你         | 客户端不必再问，默认缓存有效直到被告知失效——正是**轮询 vs 中断**的翻版（5.1.3） |
| **文件标识**（FID）  | 卷标识 + 文件标识 + **uniquifier**（支持 ID 复用），取代路径名 | 路径由**客户端**逐级解析并缓存中间结果，服务器不再走路径                        |

注意：回调是**服务器上的状态**——AFS 为了扩展性主动放弃了 NFS 的无状态纯粹性。

访问 `/home/remzi/notes.txt`（`home` 是 AFS 挂载点）的过程：

1. Fetch 目录 `home` 的内容 → 存本地磁盘缓存 → 在 `home` 上建立回调；
2. Fetch 目录 `remzi` → 缓存 → 建立回调；
3. Fetch 文件 `notes.txt` → 缓存 → 建立回调 → 返回 fd。

首次访问消息很多，但**为路径上每一级都建立了回调**，因此后续访问完全本地、零服务器交互。常见情形（文件已被缓存）下，AFS 的表现几乎与本地文件系统一致。

## 6.13 AFS 的缓存一致性

有了回调与整文件缓存，一致性语义变得一句话可讲清：

| 场景                       | 语义                                                                                                                                                                                        |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **不同机器之间**           | 更新的可见与旧副本的失效**同时发生**，时机是写方 `close()`：新文件刷回服务器，服务器随即**打破**（break）所有缓存该文件的客户端的回调；这些客户端下次 `open()` 必须重新 Fetch（并重建回调） |
| **同一机器内的进程**       | 写入立即对其他本地进程可见（普通 UNIX 语义），不必等 `close()`                                                                                                                              |
| **不同机器同时写同一文件** | **最后写者胜**（last writer wins，其实是 last closer wins）：最后 `close()` 的客户端整文件覆盖服务器                                                                                        |

最后一条与 NFS 差别显著：NFS 按块刷回，两个客户端并发写可能得到**块级混合**的文件——想象一张 JPEG 被两台机器各改一半，结果很可能不是合法 JPEG。AFS 的结果至少是**某一个客户端产生的完整文件**。

> [!note] 缓存一致性不是万灵药
> 这类基线一致性只服务于"随便用用"的场景：换台机器登录，期望看到自己文件的一个合理版本。真正关心并发更新的程序（代码仓库的 check-in/check-out、事务数据库）必须自己加**显式文件锁**或冲突处理。指望文件系统替你做对，只会收获失望。

## 6.14 崩溃恢复

回调是有状态的，恢复因此比 NFS 复杂。核心风险是**漏收了失效通知**。

| 崩溃           | 问题                                                                 | 处理                                                                                                                                                    |
| -------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 客户端重启     | 重启期间服务器发来的 break 消息收不到，本地磁盘缓存可能已陈旧        | 重新加入系统后，把**全部缓存视为可疑**；下次访问先 TestAuth 校验，有效则用，无效则重新 Fetch                                                            |
| 服务器崩溃重启 | 回调保存在**内存**中，重启后服务器不知道谁缓存了什么，无法再承诺通知 | 每个客户端都必须及时察觉服务器崩溃，把全部缓存视为可疑并逐一重新校验。实现方式：服务器起来后广播"别信你的缓存"，或客户端用**心跳**（heartbeat）周期探活 |

代价清晰可见：NFS 客户端几乎察觉不到服务器崩溃，AFS 的服务器崩溃则是一次全局事件。**可扩展性与清晰语义，是用更复杂的恢复换来的。**

## 6.15 性能与可扩展性

新协议下每服务器可支持约 **50** 个客户端（原先 20），且常见情形下客户端性能接近本地。

定性比较的假设：小/中/大文件分别 $N_s$、$N_m$、$N_L$ 块；小、中文件可放进客户端内存，大文件放得进本地磁盘但放不进内存；首次访问不命中任何缓存；单位访问延迟满足

$$
L_{net} > L_{disk} > L_{mem}
$$

| #   | 负载             | NFS           | AFS            | 比值 AFS/NFS       |
| --- | ---------------- | ------------- | -------------- | ------------------ |
| 1   | 小文件顺序读     | $N_s L_{net}$ | $N_s L_{net}$  | 1                  |
| 2   | 小文件顺序重读   | $N_s L_{mem}$ | $N_s L_{mem}$  | 1                  |
| 3   | 中文件顺序读     | $N_m L_{net}$ | $N_m L_{net}$  | 1                  |
| 4   | 中文件顺序重读   | $N_m L_{mem}$ | $N_m L_{mem}$  | 1                  |
| 5   | 大文件顺序读     | $N_L L_{net}$ | $N_L L_{net}$  | 1                  |
| 6   | 大文件顺序重读   | $N_L L_{net}$ | $N_L L_{disk}$ | $L_{disk}/L_{net}$ |
| 7   | 大文件中只读一块 | $L_{net}$     | $N_L L_{net}$  | $N_L$              |
| 8   | 小文件顺序写     | $N_s L_{net}$ | $N_s L_{net}$  | 1                  |
| 9   | 大文件顺序写     | $N_L L_{net}$ | $N_L L_{net}$  | 1                  |
| 10  | 大文件顺序覆写   | $N_L L_{net}$ | $2N_L L_{net}$ | 2                  |
| 11  | 大文件中只写一块 | $L_{net}$     | $2N_L L_{net}$ | $2N_L$             |

四点观察：

1. **多数情形两者相当**。首次读由网络传输主导；AFS 写本地磁盘的开销被客户端页缓存吸收，读也多半命中客户端内存缓存——AFS 白蹭了本地文件系统的缓存基础设施。
2. **大文件重读 AFS 更快**（负载 6），快 $L_{net}/L_{disk}$ 倍：本地磁盘缓存装得下，NFS 只有内存缓存，装不下就得整份重取，还额外加重服务器负载、损害扩展性。
3. **顺序写新文件两者相当**（负载 8、9）：AFS 写本地副本同样先落页缓存、后台落盘，`close()` 时刷回；NFS 也在 `close()` 时刷回以满足 flush-on-close。
4. **AFS 的两处劣势**：覆写已有文件要先取回整份旧文件（负载 10，2 倍，那次读完全无用）；只访问大文件的一小块（负载 7、11）时，整文件取回 + 整文件写回，开销与实际 I/O 量完全脱钩，而 NFS 的 I/O 与读写大小成正比。

（负载 10、11 假设 NFS 的写是块大小对齐的，否则 NFS 也要先读；且未使用 `O_TRUNC`，否则 AFS 的 open 不会去取即将被截断的内容。）

> [!warning] 负载假设决定设计成败
> AFS 的设计基于测量得出的假设：**文件很少被共享，且被顺序、整份访问**。在此假设下整文件缓存 + 回调完全合理。但周期性向大日志追加几十字节、或事务数据库的随机更新，对 AFS 都是灾难。**没有普适最优的设计，只有匹配负载的设计。**

## 6.16 AFS 的其他改进

| 改进                            | 与 NFS 对比                                                                                                   |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 真正的**全局命名空间**          | 所有客户端看到相同路径；NFS 允许各客户端随意挂载，命名一致只能靠约定与管理成本                                |
| **安全**                        | 从一开始就认证用户、支持文件私密；早期 NFS 的安全极其松散（可轻易冒充他人），后来靠 Kerberos 等认证服务才补上 |
| **用户可管理的访问控制（ACL）** | 用户能细致控制谁可访问哪些文件，超出 owner/group/others 三组模型（5.4.12）                                    |
| **管理工具**                    | volume 可在服务器间迁移以均衡负载；系统管理上远超同期同行                                                     |

# 第四部分 小结

## 6.17 小结：从通信到分布式文件系统

三个层次的主线：

| 层次           | 核心机制                                       | 解决的问题                         |
| -------------- | ---------------------------------------------- | ---------------------------------- |
| 通信           | 校验和、ack、超时重传、序列计数器、指数退避    | 在天然不可靠的网络上做出可靠消息层 |
| 抽象           | RPC（桩生成器 + 运行时库）、序列化、异步调用   | 让远程执行像本地调用一样简单       |
| 分布式文件系统 | 无状态 + 幂等（NFS）；整文件缓存 + 回调（AFS） | 崩溃恢复、缓存一致性、可扩展性     |

NFS 与 AFS 是同一问题的两个答案（并发写结果、性能负载、命名与安全的差异分别见 6.13、6.15、6.16）：

| 维度            | NFSv2                              | AFSv2                                          |
| --------------- | ---------------------------------- | ---------------------------------------------- |
| 首要目标        | 简单快速的崩溃恢复                 | 可扩展性 + 可理解的一致性                      |
| 服务器状态      | 无状态                             | 有状态（回调）                                 |
| 缓存单位 / 位置 | 块 / 客户端内存                    | 整文件 / 客户端本地磁盘（+ 内存）              |
| 有效性检查      | 客户端轮询 GETATTR + 属性缓存      | 服务器主动 break 回调                          |
| 一致性语义      | 由实现细节（超时值）定义，偶有怪异 | close 时统一生效；同机 UNIX 语义；最后关闭者胜 |
| 崩溃恢复        | 客户端重试即可，几乎无感           | 客户端/服务器崩溃后都需重新校验全部缓存        |

> [!important] 个人总结
> 分布式的主线可以概括为三步：先承认通信不可靠，用 **ack + 超时重传 + 序列号**造出可靠消息；再把远程执行包装成 **RPC**，把打包、定位、字节序、分片等脏活交给桩与运行时；最后回答"状态放哪里"。
>
> **NFS 把状态全推给客户端**（无状态 + 幂等），换来最简恢复，代价是轮询流量与模糊语义。**AFS 在服务器留一点状态**（回调），换来更少交互、清晰语义与扩展性，代价是复杂的崩溃恢复。两者都在减少服务器交互，只是把"谁记住什么"划在了不同的位置。

> [!important] 正确性依然是跨层的契约
> 与持久化一样，分布式的难点在层与层之间的承诺：RPC 挡不住服务器崩溃后的重复执行，所以 NFS 必须让操作幂等；服务器提前回复 WRITE 成功，客户端"成功即不重试"的假设就变成数据丢失；缓存一致性的基线语义只够随便用用，真正的并发更新必须由应用自己加锁。
>
> **端到端论证**是这条纪律的总纲：底层的可靠性可以是性能优化，但正确性只能在端到端处兜底。

> [!note] 后续演化
> AFS 作为系统大概走向衰落（NFS 开放标准 + CIFS 占据市场），但思想活了下来：**NFSv4 引入了服务器状态（如 open 协议消息）**，越来越像 AFS 的基本协议。
