# 第一部分 进程：抽象与 API

第一章演示过一个现象：虽然机器上只有一个物理 CPU，同时运行四个只做忙等的程序，它们却**似乎都在同时运行**。操作系统借助硬件制造了这个假象——把一个物理 CPU 转换成看似无限多个**虚拟 CPU**。

> [!question] 关键问题：如何虚拟化 CPU
> 物理 CPU 数量有限，操作系统如何在它们之上制造出"有许多个 CPU 可用"的错觉，而且要让这种错觉既高效、又安全？

答案是**时分共享**（time sharing）：让一个进程只运行一小段时间，随即切换到另一个进程，如此反复轮换。由于切换得非常快，用户感知到的就是多个程序在并行推进。借助时分共享实现 CPU 虚拟化，是操作系统最基本的技术之一。代价是性能：CPU 被共享，每个进程都会跑得更慢。

> [!note] 时分共享与空分共享
> **空分共享**（space sharing）把资源在空间上切开、同时分给多个使用者（如磁盘空间）；**时分共享**则让一个使用者在某一时刻独占资源，用完再交给下一个。CPU 属于后者：同一时刻只有一个进程真正在跑。

## 2.1 进程与它的机器状态

轮换需要一个被轮换的对象，这个对象就是**进程**（process）。对它的非正式定义是：

> 进程就是一个正在运行的程序。

程序本身只是磁盘上的静态字节——一组指令和静态数据，没有生命周期，也不会自己动。操作系统把这些字节加载到内存、让处理器开始执行，静态的程序才"活"过来，成为可以运行、暂停、切换、退出的进程。

要让一个进程能被暂停、之后再恢复，操作系统必须能记录并重建它"此刻的状态"。这些状态合称**机器状态**，主要包括三类：

| 类别                | 具体内容                                                                    | 直觉                             |
| ------------------- | --------------------------------------------------------------------------- | -------------------------------- |
| **内存 / 地址空间** | 代码段、静态数据段、堆、栈                                                  | 进程"看到"的整个世界             |
| **寄存器**          | 程序计数器（PC / IP）、栈指针（SP）、帧指针（FP）、通用寄存器、标志寄存器等 | 进程"想到"哪里、"手头"算到哪一步 |
| **I/O 状态**        | 打开的文件列表（文件描述符）                                                | 进程与外部世界建立的联系         |

PCB 中还会记录当前工作目录、等待的事件等信息，见 2.2。

其中**程序计数器**尤为关键：它记录进程下一条要执行的指令地址。暂停进程时，操作系统首先保存这些寄存器；进程重新获得 CPU 时再把它们恢复，进程就能从被打断处无缝继续。

> [!tip] CSAPP 回顾
> CSAPP 8.6 给出的定义更形式化：进程是一个执行中程序的实例，运行在自己的**上下文**中，它向程序提供两样抽象——一个独立的逻辑控制流（好像独占 CPU），一个私有的地址空间（好像独占内存）

## 2.2 进程的创建、状态与 PCB

把一个磁盘上的程序变成可运行的进程，操作系统大致要做以下工作：

1. 把程序的代码和静态数据从磁盘读入内存，并分配地址空间（早期系统一次性全部加载；现代系统按需**惰性加载**，借助分页与交换，见虚拟化内存部分）；
2. 创建运行时**栈**（stack），用于函数调用、局部变量和返回地址；
3. 视需要初始化 `main(argc, argv)` 的参数；
4. 初始化**堆**（heap），供 `malloc` 一类动态分配使用；
5. 设置 I/O 状态，例如默认赋予标准输入、输出、错误三个文件描述符；
6. 跳转到程序入口，进程开始执行。

进程在运行中不断在三种基本状态之间迁移：

| 状态        | 含义                          |
| ----------- | ----------------------------- |
| **Running** | 正在 CPU 上执行               |
| **Ready**   | 已准备好运行，但暂时没被调度  |
| **Blocked** | 在等待某个事件，例如 I/O 完成 |

```mermaid
stateDiagram-v2
    [*] --> Ready: 创建进程
    Ready --> Running: 被调度
    Running --> Ready: 时间片用完 / 被抢占
    Running --> Blocked: 发起 I/O / 等待事件
    Blocked --> Ready: I/O 完成 / 事件发生
    Running --> Zombie: 进程退出
    Zombie --> [*]: 父进程 wait() 回收
```

只有 **Running** 态占用 CPU；**Ready** 与 **Blocked** 的区别在于前者"只差 CPU"，后者"在等别的东西"——即使立刻给它 CPU 也跑不下去。当有进程阻塞时，CPU 可以被交给别的进程，系统利用率因此提高。

两个术语：Ready → Running 称为**被调度**（scheduled），Running → Ready 称为**解除调度**（descheduled）。另外，进程退出后先进入**终止**（final / zombie）状态，保留返回码等待父进程 `wait()` 取回，之后操作系统才清理它。

操作系统用一张**进程列表**（process list）维护所有进程，每个进程对应一个数据结构，通常称为**进程控制块**（Process Control Block，PCB）。下面是简化示意：

```c title="proc.h"
// 取自 xv6-x86
// 保存上下文切换时的寄存器，不包含由调用者保存的如 eax、ecx、edx
struct context {
  uint edi;
  uint esi;
  uint ebx;
  uint ebp;
  uint eip;
};

enum proc_state { UNUSED, EMBRYO, SLEEPING, RUNNABLE, RUNNING, ZOMBIE };

// Per-process state
struct proc {
  uint sz;                     // Size of process memory (bytes)
  pde_t* pgdir;                // Page table
  char *kstack;                // Bottom of kernel stack for this process
  enum proc_state state;       // Process state
  int pid;                     // Process ID
  struct proc *parent;         // Parent process
  struct trap_frame *tf;        // Trap frame for current syscall
                               // 陷阱帧：保存用户态 CPU 状态
  struct context *context;     // swtch() here to run process
                               // 内核态执行上下文
  void *chan;                  // If non-zero, sleeping on chan （sleep channel）
  int killed;                  // If non-zero, have been killed
  struct file *ofile[NOFILE];  // Open files
  struct inode *cwd;           // Current directory
  char name[16];               // Process name (debugging)
};
```

后续讲的上下文切换涉及两套保存：`tf` 记录陷入时存于内核栈的**用户寄存器**，`context` 记录切换时由操作系统保存的**内核寄存器**，见 2.5.1。

## 2.3 进程 API：fork、wait 与 exec

CSAPP 8.12 已系统讲过 UNIX 的进程控制接口，这里我们复习一下三大核心调用：

| 调用                   | 作用                     | 关键行为                                                                             |
| ---------------------- | ------------------------ | ------------------------------------------------------------------------------------ |
| `fork()`               | 创建新进程               | **调用一次、返回两次**：父进程得到子进程 PID，子进程得到 0                           |
| `wait()` / `waitpid()` | 等待并回收子进程         | 阻塞到某个子进程结束，返回被回收子进程的 PID                                         |
| `exec*()`              | 用新程序替换当前进程映像 | 覆盖代码与静态数据，堆、栈重新初始化；成功则**从不返回**；PID 与打开的文件描述符不变 |

> [!tip] CSAPP 回顾
> 父子进程共享打开文件、`fork` 的两处返回、僵死进程与回收、`waitpid` 的选项与状态宏，见 CSAPP 8.12。本节的 `fork` 与 CSAPP 8.12.2 中"打印 `x=0` 和 `x=2`、但两行顺序不定"是同一现象：输出顺序由调度器决定，是不确定的。

原书还介绍了几组周边接口：

| 接口           | 作用                                                                         |
| -------------- | ---------------------------------------------------------------------------- |
| `kill()`、信号 | 向进程发送信号：不只是终止，也可暂停、继续；进程可用 `signal()` 注册处理函数 |
| `ps`、`top`    | 查看进程列表与资源占用                                                       |

### 2.3.1 为什么把 fork 和 exec 分开

既然总是先 `fork` 再 `exec`，为什么不合成一个"创建并运行"的调用？答案是——**在两者之间**，shell 还有机会做准备工作，例如重定向标准输入 / 输出、建立管道、设置环境变量。合并成一个调用，这些操作就无处安放。

以最简单的重定向为例：

```bash
wc p3.c > newfile.txt
```

shell 可以这样安排：先 `fork()` 出子进程；在子进程中**关闭标准输出**、打开 `newfile.txt` 占据空出的位置；再 `exec()` 运行 `wc`。落到代码上：

```c title="p4.c"
if (rc == 0) {
    close(STDOUT_FILENO);                                       /* 关闭 fd 1 */
    open("./p4.output", O_CREAT | O_WRONLY | O_TRUNC, S_IRWXU); /* 打开新文件 */
    /* 随后 execvp 运行 wc，它的输出即写入 p4.output */
}
```

它之所以有效，依赖两条规则：

1. **文件描述符总是从最小的可用编号开始分配**：标准输出是文件描述符 1，关闭它之后编号 1 空闲，接着 `open` 新文件时内核把 1 分给它。
2. **`exec` 之后打开的文件描述符保持不变**：于是 `wc` 继承了这个"被改造过的" fd 1，它对标准输出的写入实际都进了文件。

管道同理：shell 用 `pipe()` 把前一个进程的输出接到后一个进程的输入，如 `grep -o foo file | wc -l`。

> [!tip] CSAPP 回顾
> 文件描述符、打开文件表与 `dup2`、重定向与管道的完整机制见 CSAPP 10.1~10.4、10.7、10.8；`close` + `open` 顶替标准输出的写法，正式的等价物是 `dup2`。

# 第二部分 机制：受限直接执行

策略（该运行哪个进程）的前提，是操作系统能随时**切换**进程，这就落到机制问题上。此时操作系统面对一对互相拉扯的目标：

1. **性能**：程序要尽可能直接在硬件上快速运行；
2. **控制**：操作系统必须能随时夺回 CPU，不能让用户程序为所欲为。

若操作系统每条指令都介入，控制有余而性能尽失；若完全放手，性能好却失去控制。解决办法叫**受限直接执行**（Limited Direct Execution，LDE）：

- 直接执行：直接在 CPU 上运行用户程序
- 受限：借助硬件提供的少量限制保住操作系统的控制权。

接下来，我们就将看到“受限”的部分具体是如何实现的。

## 2.4 用户模式、系统调用与陷阱

LDE 的硬件基础是 CPU 的两种模式：

- 普通程序运行在**用户模式**：受限，不能直接执行 I/O、修改页表等特权操作
- 内核运行在**内核模式**：不受限，能执行任意指令、访问任意内存

处理器用**模式位**标记当前模式，用户程序只能通过中断、故障或系统调用进入内核模式，处理完毕再切回用户模式。用户程序若尝试执行特权操作，硬件会触发异常，操作系统通常会终止该进程。

用户程序需要特权操作（读写文件、创建进程、分配内存、网络通信）时，通过**系统调用**（system call）请求内核代劳。在硬件上，这表现为一条特殊指令，触发一个**陷阱**（trap），CPU 切到内核模式，跳转到**陷阱表**指定的入口。

进入内核时现场保存在**内核栈**上（`trap_frame`），处理完成后执行**陷阱返回**（return-from-trap）指令回到用户模式。系统调用号与参数经约定的寄存器传递，返回值也经寄存器带回。出错的表示因层次而异：Linux 内核返回负的 `errno`，libc 包装函数则返回 $-1$ 并设置全局变量 `errno`。

> [!tip] CSAPP 回顾
> 模式位与特权指令、陷阱作为"有意的同步异常"、`syscall` 指令与参数 / 返回值寄存器约定，见 CSAPP 8.4.2、8.5.2、8.9。区别普通过程调用与系统调用的关键，是系统调用的跳转目标由操作系统**预先指定**，用户程序不能自选入口。

### 2.4.1 陷阱表

启动时，内核将各类陷阱处理程序的入口地址填入**陷阱表**（trap table），告知硬件在系统调用、时钟中断、缺页异常、非法指令等事件发生时跳转到哪里。

用户程序既无法设置陷阱表，也无法直接跳转到内核入口。它只能传递**系统调用号**，陷阱处理程序据此在**系统调用表**中分派到对应的内核函数。

> [!warning] 内核必须校验用户传入的参数
> 参数中的指针（如 `write` 的缓冲区地址）可能指向内核内存或非法地址。内核在使用前必须检查，否则用户程序可借系统调用读写内核数据。

## 2.5 协作式与抢占式调度

好了，现在我们可以开始考虑如何切换进程了。此时，我们不得不面对一个棘手的问题：

在一个单核 CPU 上，CPU 同时只能运行一个进程，执行一个逻辑流。也就是说，当一个普通进程运行时，内核事实上停止运行了！

> [!question] 关键问题：如何重获 CPU 的控制权？

早期有些系统采用**协作式**（cooperative）调度，等进程主动发起系统调用、显式让出 CPU（`yield`）或做出非法操作时才收回控制权。它的致命缺陷是：只要有一个进程进入无限循环、又从不发起系统调用，操作系统就再也拿不回 CPU，只能重启整台机器。

现代系统改用**抢占式**（preemptive）调度，依靠**时钟中断**（timer interrupt）：时钟设备每隔若干毫秒触发一次中断，硬件强制把控制权交还操作系统。操作系统由此获得一个不受用户程序摆布、可以定期收回 CPU 的支点。

### 2.5.1 上下文切换

当操作系统决定从进程 A 切换到进程 B 时，执行**上下文切换**（context switch）。它保存 A 的上下文并恢复 B 的上下文，发生在不同层次：

| 次序 | 执行者                    | 保存/恢复                           | 存放位置                                             |
| ---- | ------------------------- | ----------------------------------- | ---------------------------------------------------- |
| ①    | 硬件 + 陷阱入口汇编代码   | 保存 A 的用户态执行现场             | A 的内核栈中的 `trap_frame`（`tf`）                  |
| ②    | 操作系统的 `swtch()` 例程 | 保存 A 的内核执行上下文             | A 的内核栈中的 `context`，由 `proc(A)->context` 指向 |
| ③    | 操作系统的 `swtch()` 例程 | 恢复 B 的内核执行上下文             | 从 B 的 `context` 恢复                               |
| ④    | 陷阱返回汇编代码 + CPU    | 恢复 B 的用户态执行现场并返回用户态 | 从 B 的内核栈中的 `trap_frame`（`tf`）恢复           |

"陷入内核"与"切换进程"是两件事。系统调用或时钟中断会先让当前进程陷入内核，但此时未必发生切换；只有调度器决定换人时，才真正执行上下文切换。

上下文切换的**代价**远不止保存 / 恢复寄存器：切换会污染 CPU cache、TLB、分支预测器等片上状态，使新进程一开始就大量缺失，性能损失比"存几条寄存器"大得多。

> [!note] 用户寄存器与内核寄存器
> 进程请求内核服务时，需要区分用户寄存器和内核寄存器：
>
> - 用户寄存器：CPU 执行用户程序时，寄存器里保存的状态。
> - 内核寄存器：CPU 执行内核代码时，寄存器里保存的状态。
>
> 不同进程可能请求不同的内核服务，所以具有不同的内核寄存器状态

把启动、运行、陷入、切换、退出串起来，LDE 协议可以概括为下表：

| 阶段       | 操作系统动作                                           | 硬件动作                                     | 用户进程动作      |
| ---------- | ------------------------------------------------------ | -------------------------------------------- | ----------------- |
| 启动       | 初始化陷阱表，启动时钟                                 | 记住陷阱处理程序地址                         | —                 |
| 创建进程   | 分配内存，加载程序，设置用户栈，在内核栈填入初始寄存器 | —                                            | —                 |
| 开始运行   | 从陷阱返回                                             | 从内核栈恢复寄存器，切到用户模式，跳到入口   | 运行 `main`       |
| 系统调用   | 处理特权请求，完成后陷阱返回                           | 保存寄存器到内核栈，陷入内核                 | 经库函数触发 trap |
| 时钟中断   | 进入处理程序，决定是否切换                             | 保存用户寄存器到内核栈，进入内核模式         | 被暂停            |
| 上下文切换 | 保存旧进程内核寄存器到 PCB，恢复新进程的，切换内核栈   | 陷阱返回时恢复新进程用户寄存器，切到用户模式 | 新进程继续运行    |
| 进程退出   | 清理资源                                               | —                                            | 调用 `exit`       |

# 第三部分 调度：挑选一个进程

运行进程的底层机制回答了"如何切换进程"，但它并没有回答**选择哪个进程运行**。操作系统必须在多个就绪进程之间做出选择，这就是**调度策略**（scheduling policy）的工作了。

本部分从最简单的算法开始，逐步加入现实约束，观察每个算法在什么指标上表现好、在什么指标上会吃亏；随后进入无需预知任务长度的 MLFQ、按比例分配的彩票与步长调度，最后扩展到多处理器。

整条路线可以概括为"放宽假设 → 暴露问题 → 引出新算法"：

| 放宽的假设 / 新增的指标  | 暴露的问题                        | 引出的算法                  |
| ------------------------ | --------------------------------- | --------------------------- |
| 运行时间不再相同         | FIFO 的护航效应                   | SJF                         |
| 不再同时到达，并允许抢占 | 非抢占的 SJF 仍被先到的长任务堵住 | STCF                        |
| 新增指标：响应时间       | STCF 对交互不友好                 | RR                          |
| 允许任务发起 I/O         | CPU 与磁盘无法重叠                | 把每段 CPU 突发视为独立任务 |
| 运行时间事先未知         | SJF / STCF 无法实施               | MLFQ                        |

## 2.6 工作负载假设与衡量指标

### 2.6.1 工作负载假设

为了让分析有共同基础，先做一组刻意简化的**工作负载假设**：

1. 每个工作运行相同的时间；
2. 所有工作同时到达；
3. 一旦开始，工作一直运行到完成；
4. 所有工作只使用 CPU，不发起 I/O；
5. 每个工作的运行时间事先已知。

这些假设当然不现实，但它们构成了我们讨论的起点。

### 2.6.2 周转时间与公平性

最常用的指标是**周转时间**（turnaround time），衡量一个工作从到达到完成的全部耗时：

$$
T_{\text{周转时间}} = T_{\text{完成时刻}} - T_{\text{到达时刻}}
$$

如果所有任务同时到达，令 $T_{\text{到达时刻}} = 0$，于是 $T_{\text{周转时间}} = T_{\text{完成时刻}}$。周转时间是**性能指标**，越小越好。

另一个常被提及的指标是**公平性**（fairness）。这是个难以下定义的指标，不过我们可以从它的反面——不公平开始。当任务长时间得不到 CPU，或是得到的太少，就是不公平的。

麻烦在于，性能与公平经常互相冲突：一味压低平均周转时间，可能让某些长任务长期得不到运行；一味追求公平，又可能拖慢整体完成速度。

## 2.7 基本的调度算法

### 2.7.1 先进先出

**FIFO**（First In First Out，也叫 FCFS，First Come First Served）最朴素：谁先到谁先运行。三个任务 A、B、C 同时到达、各需 10 秒时：

```mermaid
gantt
    title FIFO：三个等长任务，每个 10s
    dateFormat X
    axisFormat %s
    section CPU
    A :0, 10
    B :20
    C :30
```

完成时间为 10、20、30，平均周转时间 $20$。

现在我们放宽假设 1：设 A 需 100 秒、B 和 C 各需 10 秒且同时到达：

```mermaid
gantt
    title FIFO：A=100s，B=10s，C=10s
    dateFormat X
    axisFormat %s
    section CPU
    A :a1, 0, 100s
    B :b1, after a1, 10s
    C :c1, after b1, 10s
```

完成时间为 100、110、120，平均周转时间骤升至 $110$。两个只需 10 秒的短任务被前面 100 秒的长任务死死堵住，这个现象称为**护航效应**（convoy effect）：一些耗时较少的潜在资源消费者被排在重量级的资源消费者之后。

### 2.7.2 最短任务优先

要缓解护航效应，自然想到**先运行最短的任务**，即 **SJF**（Shortest Job First）。同样用 A=100s、B=10s、C=10s 同时到达的例子：

```mermaid
gantt
    title SJF：先运行短任务
    dateFormat X
    axisFormat %s
    section CPU
    B :b1, 0, 10s
    C :c1, after b1, 10s
    A :a1, after c1, 100s
```

完成时间变为 10、20、120，平均周转时间 $\frac{10 + 20 + 120}{3} = 50$，相比 FIFO 的 110 大幅下降。

> [!important] SJF 的最优性
> 在"所有任务同时到达、任务长度已知"的假设下，SJF 是**最优**的，能最小化平均周转时间。由排序不等式可直接证明。
>
> 不过，现实中任务长度通常未知，任务也不一定同时到达。

### 2.7.3 抢占式最短完成时间优先

现在我们放宽假设 2。设 A 在 $t=0$ 到达、需 100 秒，B 和 C 在 $t=10$ 到达、各需 10 秒。若采用非抢占的 SJF，A 一旦开始就不能被打断，B、C 只能等它跑完，平均周转时间约 $103.33$，依然很差。

问题出在"非抢占"：要让短任务优先，必须允许调度器在新任务到达时**打断**当前任务。**STCF**（Shortest Time-to-Completion First），即抢占式 SJF，每当有新任务到达就比较所有任务的**剩余时间**，让剩余时间最短者运行：

```mermaid
gantt
    title STCF：抢占式最短完成时间优先
    dateFormat X
    axisFormat %s
    section CPU
    A :a1, 0, 10s
    B :20
    C :30
    A :120
```

A 在 $t=10$ 被抢占，B、C 先跑完，A 再继续剩余的 90 秒。平均周转时间为 $\frac{(20-10) + (30-10) + (120-0)}{3} = 50$，大大提高了。

> [!important] STCF 的最优性
> 在任务长度可知、且只考虑周转时间的假设下，STCF 是最优的抢占式调度算法。代价是**对响应时间不友好**：为了让平均完成时间最小，它会尽可能让长时间运行的任务等待，交互式体验因此很差。

## 2.8 轮转调度

### 2.8.1 响应时间

分时系统出现后，用户坐在终端前等待反馈，"多久第一次看到反应"变得与"多久完成"同样重要，于是引入**响应时间**（response time）：

$$
T_{\text{响应时间}} = T_{\text{首次运行时刻}} - T_{\text{到达时刻}}
$$

周转时间关注"多久做完"，响应时间关注"多久**第一次**被轮到"。用 STCF 处理三个同时到达的任务时，第三个任务可能要等前两个都跑完才第一次运行，平均周转时间漂亮，交互体验却很糟。

### 2.8.2 轮转调度

**RR**（Round Robin）专门优化响应时间：每个任务运行一个**时间片**（time slice，也叫 scheduling quantum），然后切换到下一个任务。时间片长度必须是定时器中断周期的整数倍，因为调度决策只能发生在中断时刻。

设 A、B、C 同时到达、各需 5 秒、时间片 1 秒，运行序列为（每格 1 秒）：

| A   | B   | C   | A   | B   | C   | A   | B   | C   | A   | B   | C   | A   | B   | C   |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

响应时间分别是 A=0、B=1、C=2，平均为 $1$；同样任务若用 SJF，平均响应时间为 $\frac{0 + 5 + 10}{3} = 5$。RR 明显对交互更友好。

但代价落在周转时间上：RR 的完成时间 A=13、B=14、C=15，平均周转时间 $14$；SJF 为 $5, 10, 15$，平均 $10$。

对一般情形，设 $N$ 个任务同时到达、长度同为 $L = kq$（$q$ 为时间片），则：

|     指标     |            RR            |         SJF         |
| :----------: | :----------------------: | :-----------------: |
| 平均响应时间 |   $\dfrac{(N-1)q}{2}$    | $\dfrac{L(N-1)}{2}$ |
| 平均周转时间 | $LN - \dfrac{(N-1)q}{2}$ | $\dfrac{L(N+1)}{2}$ |

容易发现

- 时间片**太短**：响应时间好，但切换过于频繁，上下文切换开销大；
- 时间片**太长**：切换少，但响应变差，退化得越来越像 FIFO。

不仅如此，上下文切换的代价远不止保存 / 恢复寄存器，cache、TLB 等状态的失效往往才是大头。

> [!note] RR 的"平均"陷阱
> 用平均值评价 RR 会令人意外：一种"公平"的算法，平均周转时间竟如此之差。原因不难理解——RR 把 CPU 在任务之间来回分，导致**每一个**任务都尽量晚完成。目标是周转时间时，这类"公平"算法都很糟糕；目标是响应时间时，它们又几乎是必需的。

## 2.9 I/O 与预测未来

我们已经开发了两种调度程序。第一种类型（SJF、STCF）优化周转时间，但对响应时间不利。第二种类型（RR）优化响应时间，但对周转时间不利。不过，我们还有两个假设需要放宽：假设4（作业没有I/O）和假设5（每个作业的运行时间是已知的）。接下来我们就来解决这些假设。

### 2.9.1 兼顾 I/O

现实进程会发起 I/O。进程发起 I/O 时进入阻塞，CPU 空闲，调度器本应把 CPU 交给别人；I/O 完成时中断把进程从阻塞态拉回就绪态，调度器再决定何时运行它。

设想 A 是 I/O 密集型（每运行 10ms 就发起 10ms I/O，共需 50ms CPU），B 是 CPU 密集型（连续占用 50ms）。若调度器把 A 的每个 CPU 片段都当成独立的短任务，用 STCF 就会优先运行这些短片段，从而**把 CPU 和磁盘重叠起来**：

| CPU  |  A  |  B  |  A  |  B  |  A  |  B  |  A  |  B  |  A  |
| :--: | :-: | :-: | :-: | :-: | :-: | :-: | :-: | :-: | :-: |
| 磁盘 |     |  A  |     |  A  |     |  A  |     |  A  |     |

- 交互式和 I/O 密集型任务获得更好的响应
- 实现重叠（overlap）以提高系统整体利用率

这也说明，区分 CPU 密集与 I/O 密集对调度很有价值。

### 2.9.2 无法预知的任务长度

现在来到最后一个假设：任务长度已知。这可能是最糟糕的假设，因为它在现实中几乎从不成立。

出路是：

> 用**历史行为**预测**未来行为**。

一个进程过去的运行模式往往能预示它将来会面对什么。这个朴素的想法，正是 MLFQ 的核心。

## 2.10 多级反馈队列

抛弃"已知任务长度"的前提后，问题变成：

> 如何设计一个调度器，既照顾短任务（低响应时间），又不饿死长任务，还能自动区分交互式与 CPU 密集型进程？

**多级反馈队列**（Multi-Level Feedback Queue，MLFQ）为此而生。它使用**多个优先级队列**：高优先级队列先运行，同一队列内部用 **RR** 轮转，并按进程的**实际行为**动态调整优先级。

**最朴素**的 MLFQ 由四条规则定义：

> **规则 1**：如果 A 的优先级高于 B，运行 A。
>
> **规则 2**：如果 A 和 B 优先级相同，用 RR 轮流运行。
>
> **规则 3**：新任务进入系统时，放入最高优先级队列。
>
> **规则 4**：
>
> - 任务用完自己这一层的整个时间片就降一级
> - 若主动让出 CPU（例如发起 I/O），则保持当前优先级不变。

> [!note] 时间片与配额
> **时间片**（time slice）是同层 RR 的运行单位；**配额**（time allotment）是任务在某一层被降级前允许累计消耗的 CPU 时间。初版规则 4 中二者等同，但后续会区分开。

### 2.10.1 MLFQ 如何近似 SJF

新任务进系统时会被放进最高优先级，好像它是个"短任务"。如果它确实很快完成，就获得类似 SJF 的低周转时间；如果它持续占用 CPU、用完了最高层的整个时间片，就会被降级，逐渐暴露出"长任务"的真面目，最终沉到最底层。这一动态过程可以概括为：

```mermaid
flowchart LR
    New[新任务到达] --> Top[放入最高优先级队列]
    Top --> Run[运行一个时间片]
    Run --> Check{是否用完当前层 CPU 配额?}
    Check -- 是 --> Demote[降低到下一级队列]
    Check -- 否 --> Keep[留在当前层，继续记账]
    Demote --> Run
    Keep --> Run
```

直观上，A 若是早已降到低优先级的长任务，而短交互任务 B 在 $t=100$ 到达，B 会先进入最高层、很快跑完，A 之后再继续——这正是 STCF 想要的"短任务优先"效果。同理，交互式任务经常运行一小会儿就去等待 I/O，从而主动释放 CPU；规则 4 初版会让它们一直留在高优先级，响应时间因此很好。

### 2.10.2 饥饿与周期性优先级提升

朴素 MLFQ 有两类问题。**饥饿**：高优先级队列一直有新任务进来时，低优先级的长任务可能**永远**得不到 CPU。**行为变化**：一个进程可能先表现为 CPU 密集型、后来又变成交互式，但此刻优先级已很低，无法及时回到高优先级。

为此加入规则 5——**周期性优先级提升**（priority boost）：

> **规则 5**：经过一段时间 S，把所有工作重新提升到最高优先级队列。

饥饿消失，行为变化也能被及时反映。但 S 又成了难题：S **太大**，长任务仍可能长时间得不到运行；S **太小**，交互式任务得不到足够连续的 CPU。没有万能取值。

资深的研究员 John Ousterhout 把这种需要凭借经验调试的参数称为**巫毒常量**（voo-doo constant），使用黑魔法才能正确设置。

### 2.10.3 愚弄调度器与 CPU 记账

规则 4 初版还有一个漏洞：它把"主动让出 CPU"直接当作"这是交互式任务"的证据。于是一个纯 CPU 密集型进程只要**故意在时间片用完前发起一次 I/O**，就能一直骗过调度器、赖在最高优先级。

修正办法是**记账**：记录一个进程在其当前优先级层级上累计消耗的 CPU 时间，只要累计用量达到该层配额就降级，**不管它中途让出过多少次**。这样，频繁发起 I/O 也无法再"洗白"一个 CPU 密集型任务。

> 规则 4：：一旦工作用完了其在某一层中的时间配额（无论中间主动放弃了多少次CPU），就降低其优先级。

综合以上修正，MLFQ 的最终形态为：

| 规则 | 内容                                  |
| :--: | ------------------------------------- |
|  1   | 高优先级任务先运行                    |
|  2   | 同优先级任务按 RR 轮转                |
|  3   | 新任务进入最高优先级队列              |
|  4   | 用完当前层的累计 CPU 配额就降级       |
|  5   | 每隔 S 时间把所有任务提升到最高优先级 |

### 2.10.4 MLFQ 的调优与真实系统

MLFQ 留出大量参数需要调：用多少个优先级队列？每层时间片多长？每隔多久做一次优先级提升？

常见做法各有取法：高优先级队列配**短时间片**以利交互，低优先级队列配**长时间片**以减少切换，再加周期性 boost 防止饥饿。

尽管参数细微差别会导致行为差异很大，MLFQ 及其变体在真实系统中被广泛采用，例如 BSD UNIX、Solaris 以及 Windows NT 及其后继版本。

以 Solaris 的 TS（time-sharing）调度类为例，队列数量、每层时间片、优先级提升周期都可配置，方便管理员针对性调整；FreeBSD 某些版本还用公式根据 CPU 使用量动态计算优先级。

最后，还有一些额外的优化：有些调度程序总是将最高优先级留给操作系统，而用户进程只能在剩余的队列中竞争；有些调度程序允许用户提出优先级建议（advice），例如命令行工具 `nice`，调度器会参考这些建议，但不一定遵守。

> [!note] 调度的"没有免费午餐"
> MLFQ 是"经验驱动"的调度器：它不追求某个指标上的理论最优，而是用一套启发式规则在各种工作负载下取得不错的**综合**表现。这也解释了为什么真实系统的调度器往往复杂得"不优美"——它们是无数权衡与补丁叠加的结果。

## 2.11 比例份额

前面几类算法围绕周转时间、响应时间打转，还有一类换了个出发点：

> [!question] 如何确保每个任务（或每个用户）获得**约定比例**的 CPU 时间？

这类调度器称为**比例份额**（proportional share）调度器，也叫**公平份额**（fair-share）调度器。

此类调度程序的最终目标，是确保每个工作获得一定比例的CPU时间，而不是优化周转时间和响应时间。

### 2.11.1 彩票调度

**彩票调度**（lottery scheduling）用一个很巧妙的类比实现比例份额：每个进程持有一定数量的**彩票**，每次调度时随机抽取一张中奖彩票，持有者获得 CPU。彩票数占比越高，获得 CPU 的概率越大。例如 A 有 75 张、B 有 25 张，长期看 A 约获得 75% 的 CPU。选择过程如下：

```mermaid
flowchart LR
    Total[统计总彩票数] --> Random[随机抽取中奖号]
    Random --> Scan[遍历进程并累加彩票数]
    Scan --> Found{累计值是否大于中奖号?}
    Found -- 是 --> Win[调度该进程]
    Found -- 否 --> Next[检查下一个进程]
    Next --> Scan
```

用随机性做调度有三点好处：避免传统算法难以处理的极端情形；轻量，几乎不需要记录每个进程的状态；快速，每次只需一个随机数。

实现极其简洁：先取一个 $[0, \text{总彩票数})$ 范围内的随机数作为中奖号，再线性扫描进程列表累加彩票数，第一个使累计值超过中奖号的进程即为中奖者。

```c
int counter = 0;
int winner = get_random(0, total_tickets - 1);   /* 抽取中奖号 */

node *current = head;
while (current) {
    counter += current->tickets;                  /* 累加彩票数 */
    if (counter > winner)
        break;                                    /* 命中 */
    current = current->next;
}
schedule(current);                                /* 调度中奖进程 */
```

彩票调度还提供了三个灵活的扩展：

- **彩票货币**（ticket currency）：不同用户使用各自的局部彩票，再按比例兑换成全局彩票，用户不必关心全系统总票数；
- **彩票转让**（ticket transfer）：进程可临时把彩票转给另一个进程，例如客户端把票转给服务端以加速自己的请求；
- **彩票通胀**（ticket inflation）：在可信环境中，进程可临时增减自己的彩票数，表达"我现在更需要 CPU"。

#### 彩票调度的缺陷：短期不公平

彩票调度是**概率性**的。随机抽签保证了长期比例，但短时间内实际分配可能明显偏离期望。考虑两个运行时间同为 $R$、彩票数相同的任务，用**不公平指标**比较它们完成时间的先后：

$$
U = \frac{T_{\text{先完成者}}}{T_{\text{后完成者}}}
$$

完全公平意味着两者同时完成，此时 $U = 1$。任务越长，实际比例越接近期望，$U$ 越接近 1；任务越短，随机波动越大，$U$ 往往越差。换言之，彩票调度在**长时间尺度**上公平，在**短时间尺度**上可能相当不公平。

### 2.11.2 步长调度：确定性的比例份额

要消除随机波动，可用**步长调度**（stride scheduling）：

- 每个进程有一个**步长**（stride），与彩票数成反比：彩票越多，步长越小；
- 每个进程还有一个**行程值**（pass），初始为 0；
- 每次调度**行程值最小**的进程，它运行一个时间片后 `pass += stride`。

取大常数 $10000$，则 A（100 票）stride=100、B（50 票）stride=200、C（250 票）stride=40。初始行程值都为 0，调度过程如下（每行选出当前最小者运行并更新其行程值）：

| A pass | B pass | C pass | 本次运行 |
| -----: | -----: | -----: | -------- |
|      0 |      0 |      0 | A        |
|    100 |      0 |      0 | B        |
|    100 |    200 |      0 | C        |
|    100 |    200 |     40 | C        |
|    100 |    200 |     80 | C        |
|    100 |    200 |    120 | A        |
|    200 |    200 |    120 | C        |
|    200 |    200 |    160 | C        |
|    200 |    200 |    200 | （持平） |

结果 C 运行 5 次、A 运行 2 次、B 运行 1 次，比例恰为 $250 : 100 : 50$，与彩票数完全一致。

> [!important] 比例性
> 设任务 $i$ 有 $t_i$ 张彩票，运行 $n_i$ 次后 $\text{pass}_i = n_i \cdot \frac{10000}{t_i}$。每次总是选 $\text{pass}$ 最小者，故任意时刻最大与最小的 $\text{pass}$ 之差不超过最大步长，因此各 $\frac{n_i}{t_i}$ 近似相等，即 $n_i \propto t_i$。

```mermaid
flowchart LR
    Init[初始化 pass=0, stride=C/tickets] --> Select[选择最小 pass 的进程]
    Select --> Run[运行一个时间片]
    Run --> Update[pass += stride]
    Update --> Insert[重新放入优先队列]
    Insert --> Select
```

彩票与步长的取舍如下：

| 特性       | 彩票调度 | 步长调度                 |
| ---------- | -------- | ------------------------ |
| 基本性质   | 概率性   | 确定性                   |
| 实现复杂度 | 很低     | 较低，但需维护行程值     |
| 新进程加入 | 容易     | 需要设置合适的初始行程值 |
| 短期公平性 | 可能偏离 | 更精确                   |
| 全局状态   | 少       | 多                       |

新进程若取 $\text{pass} = 0$，会在追上其他进程之前长期独占 CPU，所以初值必须设置得当，常见做法是取当前最小 $\text{pass}$。

### 2.11.3 比例份额的适用场景

比例份额调度有一个绕不开的难题：**彩票数（或权重）该由谁、按什么来定**？浏览器该分多少、编译器该分多少、I/O 密集型任务如何折算，都没有自然答案。因此在通用 CPU 调度中，MLFQ 一类调度器更为常见。

比例份额真正的用武之地，是那些**份额需求本来就明确**的场景：虚拟机之间的资源分配、容器的 CPU 份额、数据中心的资源管理——在这些地方，租户花钱购买了确定的资源比例，调度器只需保证它。

## 2.12 多处理器调度

直到这里，讨论都默认只有一个 CPU。当机器拥有多个核 / 多个处理器时，单处理器策略需要重新审视，还会冒出一批新问题：缓存一致性、同步开销、**缓存亲和性**、负载均衡、可扩展性。

多 CPU 共享内存时，每个 CPU 带自己的缓存再接总线：

```mermaid
flowchart LR
    subgraph CPU0[CPU 0]
        Core0[核心]
        Cache0[L1/L2 Cache]
        Core0 <--> Cache0
    end
    subgraph CPU1[CPU 1]
        Core1[核心]
        Cache1[L1/L2 Cache]
        Core1 <--> Cache1
    end
    Cache0 <--> Bus[总线 / 一致性协议]
    Cache1 <--> Bus
    Bus <--> Mem[共享内存]
```

这带来了**缓存一致性**（cache coherence）问题：如果 CPU0 修改了地址 A 对应的数据，而其他 CPU 的缓存中也保存着该数据的副本，那么这些副本必须按照硬件规定的一致性规则进行协调，否则不同 CPU 可能观察到不一致的数据。

这类问题通常由硬件的**缓存一致性协议**解决，例如总线窥探（bus snooping）或基于目录的协议。硬件会根据协议更新或失效其他缓存中的副本，不要求每次修改都立即写回主存。

即使硬件保证了缓存一致性，多个 CPU 并发访问**共享数据结构**时仍需要互斥或其他同步机制。缓存一致性解决的是缓存副本之间的一致性问题，并不保证“读—改—写”这一复合操作的原子性，也不自动保证所有内存访问都按照程序源代码的顺序对其他 CPU 可见。在并发部分我们会深入讨论这一点。

### 2.12.1 缓存亲和性

一个进程在某个 CPU 上运行过后，会在该 CPU 的缓存与 TLB 里留下状态。如果下次仍在**同一个** CPU 上运行，这些状态大多还能命中，性能更好；如果被迁移到**另一个** CPU，就要重新建立，性能下降。

> [!note] 缓存丢失的程度
> 迁移并不意味着所有缓存状态都会丢失：某些缓存可能由多个核心共享，实际代价还取决于处理器的缓存层级、内存拓扑和工作负载。

因此，多处理器调度需要同时考虑两个目标：

> - 缓存亲和性：尽可能让进程继续在上次运行的 CPU 上运行，以利用已有的缓存状态。
> - 负载均衡：尽可能让各 CPU 都有足够的工作，避免部分 CPU 忙碌而另一些 CPU 空闲。

亲和性与均衡是一对张力：太强调亲和，CPU 之间可能忙闲不均；太强调均衡，又频繁迁移、损失缓存。

### 2.12.2 单队列多处理器调度：SQMS

最直接的扩展是**单队列多处理器调度**（Single Queue Multiprocessor Scheduling，SQMS）：所有进程共用一个**全局就绪队列**，各 CPU 都从中取任务。

```mermaid
flowchart TD
    RQ[全局就绪队列] --> Lock[队列同步与互斥]
    Lock --> CPU0[CPU 0]
    Lock --> CPU1[CPU 1]
    Lock --> CPUn[CPU n]
```

优点是结构简单、容易复用单处理器策略、天然负载均衡（谁有空谁取，忙闲自动拉平）。

缺点也明显：

- 同步开销：多个 CPU 需要协调对全局队列的并发访问，通常需要锁或其他同步机制。随着 CPU 数量增加，全局队列上的争用可能加剧。
- 可扩展性受限：队列操作可能成为所有 CPU 共享的性能瓶颈。
- 缓存亲和性差：进程两次被调度未必落到同一个 CPU 上。

SQMS 调度器通常会附带亲和性机制：例如 5 个任务、4 个 CPU 时，让其中 4 个任务各自尽量留在原 CPU，只让第 5 个在各 CPU 间迁移，以此兼顾亲和性与均衡，但会增加调度策略的复杂度。

### 2.12.3 多队列调度、负载均衡与工作窃取

**多队列多处理器调度**（Multi-Queue Multiprocessor Scheduling，MQMS）给每个 CPU 配一个**独立就绪队列**：

```mermaid
flowchart LR
    subgraph Q0[CPU 0 队列]
        A[Job A]
        C[Job C]
    end
    subgraph Q1[CPU 1 队列]
        B[Job B]
        D[Job D]
    end
    Q0 --> CPU0[CPU 0]
    Q1 --> CPU1[CPU 1]
    Balance[负载均衡 / 工作窃取] -.->|迁移任务| Q0
    Balance -.->|迁移任务| Q1
```

每个 CPU 主要操作自己的队列，因此能够减少对全局共享队列的竞争，同时更容易保持缓存亲和性。

代价是**负载可能不均**，必须额外引入任务迁移。最简单的负载不均：一个队列只有 A，另一个队列有 B 和 D，各自用 RR 轮转时，A 独占 CPU0 的全部时间，实际获得了**两倍**于其它进程的 CPU。

**一次迁移不够**。把 D 挪到 CPU0 后变成 $\{A, D\}$ 和 $\{B\}$，B 又比别人多拿一倍 CPU。正确的做法是**持续迁移**（continuous migration）：让任务在 CPU 之间轮换"独占"的位置。以 3 个任务共享 2 个 CPU 为例，每个时间片换一个任务独占一个 CPU，另外两个共享另一个 CPU。三个时间片后，每个任务得到 $1 + \frac{1}{2} + \frac{1}{2} = 2$ 个"CPU·时间片"，即各得 $\frac{2}{3}$ 个 CPU。

迁移可以采用**工作窃取**（work stealing）：空闲或负载较轻的队列定期偷看其它队列，若发现自己明显空闲、而某队列明显更长，就"窃取"其中一个任务：

```mermaid
flowchart LR
    Idle[某 CPU 负载较轻] --> Check[检查其他 CPU 的负载]
    Check --> Compare{是否存在明显更繁忙的 CPU?}
    Compare -- 是 --> Steal[尝试迁移一个任务]
    Compare -- 否 --> Wait[继续运行或等待]
    Steal --> Run[在本地 CPU 上运行]
```

窃取频率又成了一个巫毒常数：检查**太频繁**，迁移开销大且损害缓存亲和性；检查**太少**，负载可能长期不均。

### 2.12.4 现实中的多处理器调度

Linux 社区历史上尝试过多种方案，恰好体现了单队列与多队列两条路线：

| 调度器 | 队列结构 | 特点                                      |
| ------ | -------- | ----------------------------------------- |
| O(1)   | 多队列   | 基于优先级，类似 MLFQ（随时间调整优先级） |
| CFS    | 多队列   | 确定性比例份额，类似步长调度              |
| BFS    | 单队列   | 比例份额，基于 EEVDF 思路                 |

- O(1)调度程序是基于优先级的（类似于之前介绍的MLFQ），随时间推移改变进程的优先级，然后调度最高优先级进程，来实现各种调度目标。交互性得到了特别关注
- CFS是确定的比例调度方法，类似之前介绍的步长调度
- BFS作为三个算法中唯一采用单队列的算法，也基于比例调度，但采用了更复杂的方案，称为最早合格虚拟截止时间优先（EEVDF）

单队列与多队列**都能成功**，关键在于如何在可扩展性、缓存亲和性、负载均衡与交互性之间权衡。

> [!note] 现代 Linux 的公平调度机制则已逐步转向 EEVDF

# 第四部分 小结

## 2.13 小结

本篇沿着"抽象 → 机制 → 策略"的路线走完了 CPU 虚拟化的全貌：

- **进程**是基本抽象，其状态由内存、寄存器与 I/O 三部分构成
- **受限直接执行**是让用户程序高效运行、又让操作系统保持控制的机制，靠模式位、陷阱表、时钟中断与上下文切换共同实现
- **调度策略**则在周转时间、响应时间、公平性之间反复权衡，从 FIFO、SJF、STCF、RR，到无需预知任务长度的 MLFQ，再到按比例分配的彩票与步长调度；到了多核时代，缓存亲和性与负载均衡又成了新的核心矛盾。

#### 调度算法一览

| 算法    | 是否抢占 | 是否需预知长度 | 主要优化           | 主要缺点                    |
| ------- | -------- | -------------- | ------------------ | --------------------------- |
| FIFO    | 否       | 否             | 简单               | 护航效应，平均周转时间差    |
| SJF     | 否       | 是             | 最小化平均周转时间 | 需预知长度，响应差          |
| STCF    | 是       | 是             | 最优平均周转时间   | 需预知长度，响应差          |
| RR      | 是       | 否             | 响应时间好         | 周转时间差，上下文切换开销  |
| MLFQ    | 是       | 否             | 兼顾响应与周转     | 参数难调，可能饥饿 / 被愚弄 |
| Lottery | 是       | 否             | 比例共享，实现简单 | 短期不公平                  |
| Stride  | 是       | 否             | 确定性比例共享     | 需维护全局行程值状态        |

#### 两个关键指标

$$
T_{\text{周转时间}} = T_{\text{完成时刻}} - T_{\text{到达时刻}}
\qquad
T_{\text{响应时间}} = T_{\text{首次运行时刻}} - T_{\text{到达时刻}}
$$

#### MLFQ 五条规则速记

| 规则 | 内容                                                |
| ---- | --------------------------------------------------- |
| 1    | 高优先级先运行                                      |
| 2    | 同优先级按 RR 轮转                                  |
| 3    | 新任务进入最高优先级队列                            |
| 4    | 用完当前层累计 CPU 配额就降级（不因主动让出而豁免） |
| 5    | 每隔 S 时间把所有任务提升到最高优先级               |

#### 多处理器调度对比

| 方案 | 结构            | 优点                 | 缺点                         |
| ---- | --------------- | -------------------- | ---------------------------- |
| SQMS | 单全局队列      | 简单，天然负载均衡   | 锁争用，扩展性差，缓存亲和差 |
| MQMS | 每 CPU 一个队列 | 扩展性好，缓存亲和好 | 负载不均，需要持续迁移       |
